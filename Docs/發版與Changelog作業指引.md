# 發版與 Changelog 作業指引（一站式免跳轉手冊）

> **性質**：官網發版與更新日誌作業的唯一標準手冊（單一真相來源）。  
> **核心原則**：本檔為**完全閉環的作業清單**。執行發版任務時，歷史版本視為不可變之凍結狀態，**嚴禁沿超連結向外遞迴追溯無關之歷史文件（Max Depth = 1）**。  
> **最後更新**：2026-09-15（下載目標搬到 `Src/shared/downloads.ts`）  

---

## 0. 邊界與防遍歷守則 (Boundary & Scope)

1. **歷史視為凍結（Freeze）**：過去的日誌記錄、已結案的歷史缺口與既有依據皆為不可變事實。發版時專注於**本次增量更新**，不翻查歷史前因後果。
2. **單一入口、零外部跳轉**：發版所需的 5 處檔案路徑、撰寫規格、翻譯順序與檢核指令全收錄於本檔，無需額外檢索其他 BRD、快照或架構文件。
3. **MDC 語法防呆**：PromptBox 核心功能常涉及 `{{變數}}` 與 `{{@prompt:N}}`。寫入 Markdown 段落時，**嚴禁裸露花括號**，必須包在行內代碼 `` `{{...}}` `` 或代碼塊內，否則 Nuxt Content 會將其求值為空字串（`check:content` 護欄會強制阻擋）。

## 1. 發版必改 5 處一站式檔案清單 (What & Where)

每次發布新版本時，必定依序連動以下 5 處位置（本清單即為全部範圍，無需擴散至其他檔案）：

| # | 項目 | 檔案路徑 | 說明與注意事項 |
|---|---|---|---|
| **1** | **日誌 Markdown 正文** | `Src/content/changelog/vX.X.X.md` | 一版一檔。最新版由 `date` 與 SemVer 數字動態推導，**不手動標記 `latest`**。撰寫風格遵循 [§3 規範](#3-changelog-內容撰寫規範-style-guide)。 |
| **2** | **日誌頁三語 Meta** | `Src/i18n/locales/{zh-TW,en,ja}/changelog.json` | 同步 `meta.description`（例：「從 v1.0 到 vX.X.X…」）與 `cta.body`（例：「vX.X.X 現已推出…」）。 |
| **3** | **下載頁三語 Meta** | `Src/i18n/locales/{zh-TW,en,ja}/download.json` | 同步 `meta.description`（免費下載版號）與 `hero.badge`（「✨ 最新版本 vX.X.X」）。 |
| **4** | **下載安裝檔與校驗碼** | `Src/shared/downloads.ts` | 🔴 **紅線 5**：`win`／`win-zip`／`mac` 三組的 `href` 與實算 `sha256` 必須成對更新，`DOWNLOAD_VERSION` 一併改（確認 Cloudflare R2 已上架）。下載頁、會員專區、`/dl` 端點都讀這一份，**不要在別處另寫網址**（`check:release` 會擋）。若手冊第 9 章校驗範例含版號亦連動。 |
| **5** | **規格文件鏡像回寫** | `Docs/webspec/PageDescription/05_changelog.md`<br>`Docs/webspec/PageDescription/02_download.md` | 回寫「當前發行版本」表格與最新版聲明。若涉及產品能力或重要名詞更動，回寫 `Docs/webspec/主張與依據.md`。 |

## 2. 兩階段標準作業流程 (SOP)

為避免中文文案反覆推敲時導致外語翻譯白做工，一律採**「中文定稿 ➔ 外語衍生」**兩階段推進：

### 階段一：繁中定稿與下載核對 (Phase 1)
1. **撰寫日誌正文**：於 `Src/content/changelog/` 新增 `vX.X.X.md`，參照 [§3 範本](#4-標準-markdown-範本-standard-template) 撰寫繁中條目。
2. **同步繁中版面**：修改 `Src/i18n/locales/zh-TW/changelog.json` 與 `download.json` 的最新版號。
3. **核對下載檔與校驗碼（紅線 5）**：確認 Cloudflare R2 上安裝檔（`.exe` / `.zip` / `.dmg`）已可存取（HEAD 200），於 `Src/shared/downloads.ts` 填入 `href`、`size` 與創辦人實算之 SHA-256，並更新 `DOWNLOAD_VERSION`。
4. **人工確認繁中品質（關卡）**：檢視繁中文案流暢度、使用者效益是否清楚，確認無誤後**宣告 Phase 1 正式定稿**。

### 階段二：外語衍生與護欄驗證 (Phase 2)
5. **外語衍生翻譯**：以定稿後的 `zh-TW` 為單一基準，將版號與文案同步翻譯至 `en` 與 `ja` 的 `changelog.json` 及 `download.json`。
6. **規格文件鏡像回寫**：同步更新 `PageDescription/05_changelog.md` 與 `02_download.md` 之最新版號記錄。
7. **執行四道護欄驗收**：在 `Src/` 目錄下執行完整檢查，全綠才可提交：
   ```bash
   cd Src
   npm run check:content   # 1. 檢查 Markdown 是否有未包裹的 {{ }}
   npm run check:i18n      # 2. 檢查三語 key 是否完整對齊
   npm run check:docs      # 3. 檢查文件內部連結與錨點
   npm run check:release   # 4. 檢查最新發布版號全站一致性（防缺口 7、9）＋ 下載目標是否只有一份
   npm run build           # 整合編譯測試（自動依序跑完上述 4 支護欄）
   ```

## 3. Changelog 內容撰寫規範 (Style Guide)

### 3.1 核心原則
1. **由外向內（使用者視角）**：專注描述「使用者看得到的改變」或「操作行為的影響」，不記錄底層架構細節（如演算法參數、資料庫欄位名稱、內部變數名）。
2. **動詞開頭、效益結尾**：每條項目標題皆以明確動詞開頭（**新增 / 優化 / 修復 / 調整**），內文點出帶來的直接好處或修正的具體問題。
3. **客觀陳述、拒絕自我辯解**：刪除開發團隊的內部心路歷程、情緒抒發或歷史檢討（例如：「誠實記帳：這是防護下降」、「它從第一天起就是壞的」）。
4. **不陳述「未改變的事實」**：避免花篇幅保證「這裡一個字元都沒動」、「設定檔完全不變」，只記錄真正發生變化的部分。
5. **誠實揭露但力求精煉**：若有使用者須知的邊界限制或行為改變（如逾時鎖定機制調整），客觀條列重點即可，不必長篇大論。

### 3.2 規格與篇幅限制
| 項目 | 建議規格 | 上限標準 |
| :--- | :--- | :--- |
| **單條項目長度** | 1 ～ 2 句話（約 30 ～ 60 字） | 不超過 80 字 |
| **單版條目數量** | 3 ～ 5 條核心變更 | 最多不超過 7 條 |
| **單版總字數** | 150 ～ 300 字 | 不超過 450 字 |
| **Frontmatter Summary** | 一句話點出該版核心主題（約 20 ～ 40 字） | 不超過 60 字 |

### 3.3 圖示分類建議 (Emoji Taxonomy)
統一清單前綴的 Emoji 意涵，維持視覺節奏：
- 🚀 / ✨ / 🌐 ：**新功能／多語系支援**（例：**新增支援**、**擴展語系**）
- 🔐 / 🛡️ / 🔑 ：**安全性與機密保護**（例：**強化加密保護**、**優化金鑰機制**）
- 🛠️ / 🐞 / 🔧 ：**問題修復與防呆**（例：**修復異常**、**排除卡死狀況**）
- 🎨 / 💬 / 👁️ ：**視覺介面與文案優化**（例：**介面微調**、**文案用語釐清**）
- ⏱️ / ⚡ / 📊 ：**效能、計時與配額限制**（例：**調整逾時鎖定**、**優化配額提示**）
- ⚠️ / ℹ️ ：**重要須知與操作邊界**（例：**注意事項**、**系統綁定說明**）

### 3.4 標準 Markdown 範本 (Standard Template)
每篇檔案命名為 `vX.Y.Z.md`，存放於 `Src/content/changelog/`：
```markdown
---
version: "v3.9.5"
date: "YYYY-MM-DD"
summary: "功能核心主題 —— 一句話說明本版最重要的改變與使用者效益。"
major: true # 若為重大版本（版號進位或重大架構躍進）才加上
---

- <span class="text-lg">🌐</span><span>**多語系支援擴展**：設定頁面新增英文與日文支援，各步驟說明將自動依系統語言呈現。</span>
- <span class="text-lg">🛡️</span><span>**強化變數安全機制**：機密卡的變數預設值現在納入密碼保護範圍，避免明文留存。</span>
- <span class="text-lg">🐞</span><span>**修復存檔狀態異常**：修正卡片存檔被規則阻擋時編輯視窗意外關閉的問題，確保輸入內容不遺失。</span>
- <span class="text-lg">🎨</span><span>**操作按鈕視覺優化**：調整狀態開關為中性色系，僅保留高風險警告使用琥珀色提示。</span>
```

### 3.5 常見反面模式 (Anti-patterns to Avoid)
| ❌ 應避免的寫法（內部/開發者視角） | ✅ 建議改寫方式（使用者視角） |
| :--- | :--- |
| **機密卡的變數與型別定義一併加密**：一張機密卡現在有三份密文（內容、變數、型別定義），共用一次派生的金鑰、各自獨立的 IV... | **全面保護機密卡變數**：機密卡的變數名稱與預設值現在與內文同步受密碼加密保護。 |
| **切換視窗不再是上鎖條件（誠實記帳：這是防護下降）**：解鎖後切到別的視窗，明文會留在記憶體上... | **調整自動鎖定機制**：取消「切換視窗立即上鎖」，改以閒置逾時（10 分鐘）與系統鎖定為主，提升多工操作順暢度。 |
| **複製到客戶端的設定檔內容一個字元都沒有變**：那是你貼進 Claude 的內容，被動到會失效，所以翻譯完全不碰它。 | （直接省略不提；或僅提新功能：設定指引支援多語系。） |
| **設定頁的「官方網站」按鈕真的打得開**：它從第一天起就是停用狀態。同時修正了撞到配額時那顆升級按鈕... | **修復外部連結問題**：修復設定頁官網按鈕無法點擊的問題，並校正配額升級按鈕的目標連結。 |

## 4. 歷史事故防呆與發版 Checklist

### 4.1 歷史事故避坑備忘
- **避坑 1（歷史缺口 7）**：日誌更新不可超前下載頁面！嚴禁出現日誌宣稱 v3.9.x 但下載頁停留在舊版的狀況。
- **避坑 2（歷史缺口 9）**：三語 Meta 與下載檔案必須同步完成。不可只更新 `zh-TW` 漏掉 `en/ja`，且 R2 安裝檔必須上架確認有二進位檔案後才能宣稱發版。

### 4.2 發版驗收勾選表（發版時可直接複製引用）
```markdown
- [ ] 1. 新增 `Src/content/changelog/vX.X.X.md`（無裸露 {{ }}、採使用者視角、動詞開頭）
- [ ] 2. 更新 `Src/i18n/locales/zh-TW/changelog.json` 與 `download.json`
- [ ] 3. 確認 R2 安裝檔可下載（HEAD 200），並更新 `shared/downloads.ts` 三組的 href 與 sha256、`DOWNLOAD_VERSION`
- [ ] 4. 人工審查繁中文案與版號（Phase 1 定稿關卡）
- [ ] 5. 同步翻譯 `en` 與 `ja` 的 `changelog.json` 與 `download.json`（Phase 2）
- [ ] 6. 回寫 `Docs/webspec/PageDescription/05_changelog.md` 與 `02_download.md`
- [ ] 7. 跑完四道護欄全綠：`check:content`、`check:i18n`、`check:docs`、`check:release` 與 `build`
```
