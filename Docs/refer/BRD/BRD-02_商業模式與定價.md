## 1. 商業模式：open-core + 本地優先 freemium

最貼近的實務對照是 **Obsidian**：核心 app 完全免費（本地優先、資料是使用者的檔案），營收來自選配服務與**選配（非強制）的商業授權**。

Obsidian 證明了三件對 PromptBox 極重要的事：

1. **本地優先 + 免費核心，是可以賺錢的**，不必為了收費而背叛隱私定位。
2. **「榮譽制商業授權」真的收得到錢**——不需要伺服器強制驗證。
3. 一次性買斷與週期性收入可以並存，**反訂閱族群會用買斷投票**。

**PromptBox 的模式**：可驗證的免費開源核心（§7）＋ 四條收入線（§4），刻意設計成**不需要碰使用者資料就能收錢**。

## 2. 收費模型：買斷 + 更新權

> **付一次 → 永久可用當前版本。更新權到期只代表「不能再下載更新」，已安裝版本照常永久跑。App runtime 從不檢查到期。**

### 2.1 為什麼不是訂閱制

純訂閱需要 **App runtime 檢查到期日**。對一個離線、本地優先的桌面 App，這帶來兩個無解的問題：

| 問題                   | 說明                                                                                                                                                        |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **可被繞過**           | 使用者把系統時間往回調就過關                                                                                                                                |
| **要防它就得聯網驗真** | 而「不打電話回家」是本產品的品牌核心（[BRD-01 §2](BRD-01_定位與市場.md) 副標、[BRD-03 §6](BRD-03_授權與Free-Pro邊界.md)）。為了收費而聯網，等於用賣點換收入 |

**買斷 + 更新權把到期的把關點搬到「你的下載／購買伺服器」**，不在使用者執行中的 App：

- 年度收入來源 = **續訂更新權**（你想推新功能、使用者想拿 → 自然續）
- App 端 `updatesUntil` 只是**資訊欄位**，runtime 永不據此鎖功能，**永不 time-bomb**
- 「不打電話回家」成立——**v3.3.0 起 App 內已無任何更新檢查**，唯一的伺服器接觸是使用者**自己開瀏覽器**去官網下載安裝檔（[BRD-00 §5.1 U7](BRD-00_索引與決策狀態.md)、[ADR-000 A5](../ADR/ADR-000_索引與技術原則.md)）
  > ⚠️ 但**還不能對外說「完全不連網」**——字型仍從 Google CDN 載入，見 [ADR-000 C2-④](../ADR/ADR-000_索引與技術原則.md) 與 [BRD-03 §9 規則 5](BRD-03_授權與Free-Pro邊界.md)

### 2.2 這也解掉「訂閱正當性」的弱項

純本地軟體最大的變現障礙是「憑什麼每年收我錢」。逐項檢核：

| 要素                | PromptBox 現況                                           | 判定                                              |
| ------------------- | -------------------------------------------------------- | ------------------------------------------------- |
| 1. 長期穩定需求     | Prompt／密鑰庫是**持續累積的資產**，卡片越多轉換成本越高 | ✅ 成立，且有天然黏性                             |
| 2. 穩定可預期的交付 | 本地軟體「交付」的是更新，但更新對使用者是**不可見的**   | ✅ **已由商品定義解決**——使用者買的就是「更新權」 |
| 3. CLV > CAC + COC  | COC 近零（無伺服器、無 AI token 成本）                   | ✅ 但 CAC 是關鍵，見 §6                           |
| 4. 單次交付成本夠低 | 數位下載，近零                                           | ✅                                                |

**但紀律成本仍要付**（要素 2 的兌現方式）：

- 每月一則 release note，即使只有安全性修補也要發（**節奏本身就是交付**）
- 在 app 內顯示「你的更新權期間收到了 N 次更新、修補了 N 個安全問題」
- 公開 MCP 生態相容性追蹤頁（AI 生態每季在變，這是持續勞動的可見證據）

## 3. 價格表（單一真相）

| SKU                    | 價格                | 內容                                                    | 語意                                               |
| ---------------------- | ------------------- | ------------------------------------------------------- | -------------------------------------------------- |
| **Free**               | **$0**              | 見 [BRD-03 §2](BRD-03_授權與Free-Pro邊界.md) 完整邊界表 | 永久免費基底                                       |
| **Pro（首購）**        | **US$39**           | 解除全部配額 + 強型別 + 稽核匯出                        | **永久可用當前版本 + 含 12 個月更新權**            |
| **更新權續訂**         | **US$27 / 年**      | 繼續取得新版本                                          | 首購 7 折；**不續訂＝停在最後版本永久用**          |
| **永久更新權**         | **US$109 一次性**   | 永久授權 + 永久取得所有未來更新                         | ≈ 首購 + 2.6 年續訂（39 + 27×2.6）。免除年年續訂   |
| **商業授權（榮譽制）** | **US$69 / 人 / 年** | 功能**完全同 Pro**，加公司內使用授權                    | **純年費**（見 §3.1）；**App 端一樣不檢查到期**    |

**不提供月付。** 買斷模型下月付沒有語意。

### 3.1 商業授權為什麼是純年費

它賣的是「**合規**」與「**支持開發者**」，不是功能——功能與 Pro 完全相同。年費在這個語境下最自然：公司今年在用就今年付，而企業採購本來就是年度預算制。若改成買斷，等於告訴公司「付一次就永久合規」，直接消滅第二年的續購動機。

**但關鍵設計不變：App 端不做到期檢查。** 收不收得到第二年，靠的是公司的合規意願，不是技術鎖——這才是「榮譽制」的定義。

**這條線的開發成本近乎為零**（一個 `type: "commercial"` 的 token 值 + 一個價格選項，複用既有 token 結構），但單價是 Pro 的 1.77 倍。**首發即上，不等企業版。**

### 3.2 促銷

| 促銷                        | 對象            | 首發做嗎    | 說明                                                           |
| --------------------------- | --------------- | ----------- | -------------------------------------------------------------- |
| **連買 2 年送 1 年**        | 個人 Pro 更新權 | ✅ 做       | 一次付 2 年續訂（$46）得 36 個月更新權。零成本的前置現金流工具 |
| **團購優惠（如買 4 送 1）** | **商業授權**    | ✅ 做       | 一次付 4 席、發 5 把獨立 key。無額外架構成本                   |
| ~~買 4 送 1~~               | ~~個人 Pro~~    | ❌ 首發不做 | 沒有團購通路，且與商業授權的定位重疊、會互相打架               |

### 3.3 價格為什麼站得住

外部實查（2026-07）：

| 產品                    | 心理帳戶               | 換算年費  | 相對 PromptBox $39  |
| ----------------------- | ---------------------- | --------- | ------------------- |
| Bitwarden Premium       | 保險庫                 | $19.80/年 | 我們較貴            |
| Typinator               | 本地文字擴充           | $29.99/年 | 我們略貴            |
| **1Password 個人版**    | 保險庫                 | $47.88/年 | **我們較便宜**      |
| **Obsidian Sync**       | 本地優先工具的選配服務 | $48/年    | **我們較便宜**      |
| **SpacePrompts Pro**    | Prompt 工具            | $60/年    | **我們較便宜**      |
| **Keep My Prompts Pro** | Prompt 工具            | $120/年   | **我們便宜 3 倍**   |
| **PromptHub Pro**       | Prompt 工具            | $144/年   | **我們便宜 3.7 倍** |

**結論**：$39 在**保險庫**與 **prompt 工具**兩個參考群裡都不是最貴的一檔，在 prompt 工具同業群裡甚至是**最便宜的**。$69 ÷ $39 = 1.77 倍，落在商業授權的合理區間（Pro 的 1.5–2 倍，Obsidian 為 $50 對 $0）。**定價風險低。**

> 反過來的提醒同樣重要：**過低的價格會主動破壞信任定位。** $10/年 的產品在使用者眼中就是「一個小工具」，不會是「保管我密鑰的東西」。訂價一旦決定，市場定位也隨之確立。

### 3.4 永久更新權的兩個護欄

| #   | 護欄                   | 說明                                                                                                                                                  |
| --- | ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **佔累計營收 ≤ 30%**   | 超過就調價或限量。它會吃掉未來的經常性收入，而對收購方而言 ARR 遠比一次性收入值錢                                                                     |
| 2   | **「永久」範圍寫清楚** | 定義為「**永久使用 Pro 全功能 + 永久取得當前產品線的更新與安全修補**」。**重大新模組（未來的雲端／團隊／企業地端）另計。** 現在不寫清楚，兩年後會很痛 |

## 4. 四條收入線

刻意設計成**不需要碰使用者資料就能收錢**：

| 線                        | 對象                     | 為何不破壞中立／隱私                   | 現金流特性                        |
| ------------------------- | ------------------------ | -------------------------------------- | --------------------------------- |
| **A. Pro 首購 $39**       | 個人重度使用者           | 賣的是進階護欄與規模上限，不是資料託管 | 前置                              |
| **B. 更新權續訂 $27/年**  | 續留的 Pro 用戶          | 賣的是持續勞動的成果                   | **經常性、可預期**                |
| **C. 永久更新權 $109**    | 反訂閱的本地派           | 賣的是永久授權                         | **前置現金流加速器**（≤30% 紅線） |
| **D. 商業授權 $69/人/年** | 公司內使用者、小型工作室 | 只是一個更貴的授權碼，功能完全相同     | 高單價、零額外開發成本            |

### 明確排除的收入線（寫進公開文件，本身就是定位聲明）

- ❌ **雲端同步作為主要營收**——與隱私定位正面衝突，且會拖進 SaaS 的成本結構
- ❌ 廣告、資料變現、prompt 市集抽成
- ❌ AI 包（首發不做，見 [BRD-04 §3](BRD-04_版本路線與時序.md)）

## 5. 早鳥方案（✅ 已定案）

**兩批，永久鎖價**（創辦人 2026-07-31）：

| 階段   | 名額       | 價格         | 權益                       |
| ------ | ---------- | ------------ | -------------------------- |
| 第一批 | 前 150 名  | **$19 / 年** | 永保續訂權（鎖定此續訂價） |
| 第二批 | 151–300 名 | **$25 / 年** | 永保續訂權（鎖定此續訂價） |

| 之後 | — | 標準價 $39 + $27/年 | — |(7折)

**早鳥全滿的第一年營收上限**：150×$19 + 150×$25 = **$6,600**

### 5.1 五個細節的定案（2026-07-31）

| # | 議題 | 定案 |
|---|---|---|
| 1 | 「$19/年」與買斷+更新權模型怎麼對齊 | **首購 $19，且續訂永遠 $19**（不是純年費、也不是一次性）。首購同樣含「永久可用當前版本 + 12 個月更新權」，與標準版結構完全相同，只有數字不同 |
| 2 | 「永保續訂權」的範圍 | **鎖定價格終身**。涵蓋範圍對標當前的 Pro 功能；**不含未來的重大新模組**（呼應 §3.4 護欄 2）。「多大算重大」目前不易定義，以「當前 Pro 功能」為基準線 |
| 3 | 早鳥升「永久更新權 $109」 | **走原價，不補差價**。理由：補差價會讓金流設定變複雜，收益不值得 |
| 4 | 名額計數 | **人工分批換連結**。不需要即時計數機制，賣完一批就換 Paddle 連結 |
| 5 | 展示方式 | **與標準銷售頁同頁**，對標 Pro：Pro 價 ~~$39~~ 加刪除線，下方標早鳥價 |

### 5.2 ⚠️ 文案風險：「終身只要 $19」會被誤讀

創辦人原始構想的文案是「Pro 售價 ~~39~~，下面標**優惠前 150 終身只要 19**」。

**問題**：客戶看到刪除線的 $39 旁邊寫「終身只要 19」，第一直覺一定是「**付一次 $19 用到死**」。等一年後續訂帳單出現，感受就是被騙。

這對本產品特別貴——[BRD-01](BRD-01_定位與市場.md) 的定位、[BRD-03 §9](BRD-03_授權與Free-Pro邊界.md) 的誠實措辭硬規則、[BRD-05 §4](BRD-05_行銷與獲客.md) 的可驗證性裂變機制，**全部押在誠實上**。用一句模糊文案換來的轉換，會在第一個續訂週期還回去，而且是連本帶利。

**採用的文案（不誤讀、同樣有力）**：

> **前 150 名早鳥：$19／年，永久鎖價**
> 標準價：首購 $39 + 續訂 $27/年

「**永久鎖價**」本身就是強力賣點，而且是真的——早鳥用戶第 10 年仍然只付 $19，標準用戶付 $27（且可能已調漲）。

> **技術註**：價格鎖定由**金流平台（Paddle）**處理，不進 token——App 端完全不需要知道使用者付了多少錢。這也是為什麼 #3 走原價最省事。

### 5.3 菜單膨脹的護欄

二檔早鳥 + 四檔標準 = 六條價格線，與 [BRD-04 §3](BRD-04_版本路線與時序.md)「客戶菜單必須小」衝突。

**護欄：早鳥是限時活動的呈現方式，不是常駐 SKU。**

- 同一頁只會出現**當前有效的那一檔**早鳥（賣完換連結後，前一檔就消失）
- 使用者在任一時點看到的價格線是：**Free / Pro（早鳥價或標準價，二選一）/ 永久更新權 / 商業授權** = **四檔**
- 早鳥全部售完後自動回到標準四檔，不留痕跡

## 6. 財務目標與獲客上限

### 6.1 損益兩平（固定現金成本 $1,500/年）

邊際成本近零，所以損益兩平幾乎完全由**固定成本 ÷ 客單價**決定。

**M1–M3 里程碑（早鳥階段，$19）**

> **79 個早鳥付費用戶**（79 × $19 = $1,501）即覆蓋全年現金成本。

**標準價階段（$39）**

| 情境             | 年目標營收 | 需要**新購**數 | @5% 轉換所需免費用戶 | @3% 轉換 |
| ---------------- | ---------- | -------------- | -------------------- | -------- |
| 只求覆蓋現金成本 | $1,500     | 39             | 780                  | 1,300    |
| 兼職級收入       | $30,000    | 769            | 15,385               | 25,641   |
| 全職單人公司     | $60,000    | 1,539          | 30,769               | 51,282   |
| 可以請第二個人   | $150,000   | 3,846          | 76,923               | 128,205  |

> ⚠️ **買斷模型下的關鍵差別**：上表的數字是「**每年的新購數**」，不是「累積訂閱者數」。
> 實際年營收 = $39 × 新購 + $27 × 續訂（早鳥為 $19 / $25 鎖價）+ $109 × 永久更新權 + $69 × 商業授權席次。
> **續訂率因此是最關鍵的未知數**（見 §6.3）。

**這張表告訴你三件事**：

1. 覆蓋現金成本只需要 **39 個標準價用戶或 79 個早鳥用戶**——「先賺到第一筆錢」是非常近的目標。
2. 全職養活自己需要約 **3 萬名免費用戶**——這是行銷的真正門檻，也是為什麼 [BRD-05](BRD-05_行銷與獲客.md) 全押零付費獲客。
3. **永久更新權 $109 ≈ 2.8 個 Pro 首購**，在爬向 39 → 1,539 的路上是最有效的現金流加速器（但受 ≤30% 紅線約束）。

### 6.2 CAC 上限：付費廣告在數學上不成立

```
Pro 首購               $39
更新權續訂             $27/年
續訂率預期             40%  → 期望續訂年數 = 0.4/(1−0.4) ≈ 0.67 年
毛利率                 ≈ 100%（無伺服器、無 token 成本）
─────────────────────────────────────
CLV                    ≈ 39 + 27 × 0.67 ≈ $57
健康門檻 CLV/CAC       ≥ 3
─────────────────────────────────────
CAC 上限               ≈ $19（每個「付費用戶」）
免費用戶獲取成本上限   ≈ $0.95（@5% 轉換）／ $0.57（@3% 轉換）
```

**消費級軟體在 Google／Meta 上一個安裝的 CPI 通常在 $2–8**，一個付費轉換的 CAC 常在 $50–200。

> **所以：PromptBox 的成長必須是零付費獲客。** 付費廣告只能用在極晚期的 retargeting（對已下載未升級的用戶），且預算應該小到像實驗而非通路。
> 這不是限制，這是聚焦——**精準客群的流量，優於單純的大流量**。詳見 [BRD-05](BRD-05_行銷與獲客.md)。

### 6.3 事先寫下的預期值

> **紀律：先寫下你預期的數字，再看實際數字。沒有事先寫下預期，任何結果你都能自圓其說。**

| 指標                  | **預期值（2026-07-31 寫下）** | 對帳時點           |
| --------------------- | ----------------------------- | ------------------ |
| 更新權**續訂率**      | **40%**                       | M12 及每個續訂週期 |
| 免費 → 付費**轉換率** | **3–5%**                      | M7–M9              |
| 永久更新權佔累計營收  | ≤ 30%                         | 每季               |

續訂率 40% 的依據：獨立桌面工具的更新權續訂率通常遠低於 SaaS 訂閱續訂率（SaaS 常見 80–90%），業界粗略區間 30–50%。

### 6.4 轉換率判讀規則

| 觀察                 | 意義                           | 動作                                                                                                                            |
| -------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| 升級率 > 10%         | 定太低                         | 往上試（見 §6.5）                                                                                                               |
| **升級率 3–8%**      | **健康區間**                   | 維持，優化漏斗                                                                                                                  |
| 升級率 < 2%          | **價值沒講清楚，或付費牆放錯** | **先查文案與鉤子，不要先降價**。第一個要檢查的是 45 卡上限是否過早撞牆（見 [BRD-03 §2 重訪條件](BRD-03_授權與Free-Pro邊界.md)） |
| 永久更新權佔比 > 40% | 本地派偏好買斷                 | 確認單價足以覆蓋長期維護，考慮調高                                                                                              |

### 6.5 A/B 測價

- **時機**：**M7–M9**。M1–M6 樣本量不足，測了是雜訊。
- **區間**：**$39 / $49 / $59**
- **比較指標**：**營收 = 轉換率 × 價格**，不是轉換率
- **樣本門檻**：每組至少 **200 名新訪客**才看數據

## 7. open-core 界線（一旦公開就收不回，現在定死）

### 7.1 界線

| 模組                                              | 開源 / 閉源           | 理由                                                                                                  |
| ------------------------------------------------- | --------------------- | ----------------------------------------------------------------------------------------------------- |
| 儲存、加密原語、MCP 基本呼叫、變數、一般卡片 CRUD | **開源**              | 核心，可驗證性的基礎                                                                                  |
| **機密卡 consent 與釋放流程**                     | **開源**              | 見 §7.2                                                                                               |
| **釋放稽核「記錄」**                              | **開源**              | 記錄是安全需求，不能因為沒付錢就不記                                                                  |
| 釋放稽核「匯出」                                  | **閉源**              | 這才是屬於 Pro 的那一半                                                                               |
| 進階串聯（chain > 5 卡）                          | **閉源**              | 純 Pro 功能，免費版完全看不到                                                                         |
| 強型別 Strong Typing                              | **閉源**              | 同上，且 Free 完全隱藏                                                                                |
| **entitlement 驗章 + 配額判定邏輯**               | **閉源** ⚠️ **見 [U9](BRD-00_索引與決策狀態.md)** | 不是因為密碼學需要保密（Ed25519 公鑰公開是常態），而是為了不提供「刪掉這 12 行就好」的現成地圖給 fork。<br>🔴 **2026-08-07 發現與 §7.3 衝突**：v3.4.0 已把配額判定實作為 `electron/platform/quota.cjs`，而它在 **Build A** 裡，§7.3 又說 Build A 就是開源版雛形。**開源前必須擇一**，選項見 [BRD-00 U9](BRD-00_索引與決策狀態.md) |
| 配額數字本身（3 / 45 / 5 / 2）                    | **開源**（讀 config） | 藏數字沒意義，藏**判定**才有                                                                          |

### 7.2 為什麼 consent 與釋放流程必須開源

這是對原始草案的一次修正。原本把「機密卡 consent 與釋放流程」放進閉源，但它與三個已定案的決定衝突：

| 已定案                   | 衝突點                                                                      |
| ------------------------ | --------------------------------------------------------------------------- |
| Free 有 3 張機密卡       | consent 與釋放流程**會出貨在免費版、而且免費版天天在跑它**——它不是 Pro 功能 |
| 加密永遠免費（品牌護欄） | 對外口徑是「Pro 賣的是規模與釋放護欄」，但釋放護欄的程式碼卻不能看          |
| 裂變靠「可驗證性」當背書 | 這是唯一的背書機制，把它的標的閉源＝背書機制失效                            |

**具體後果**：一個懂行的使用者第一個問題就是「你說 AI 要用 key 時會先問我——那段程式碼在哪？」**答不出來時，比從來沒開源還糟**（沒開源至少沒開過這張支票）。

**根因**：Pro 賣的是**張數配額**，不是**流程本身**。原本是把界線畫在錯的位置，不是畫得太多。

### 7.3 啟動時機：第一筆營收之後

**界線現在定死，執行後置。** 理由：在願付意願未驗證前投入拆分，是對「會有人付」的投機下注；且機密卡片目前實作在同一份私有 codebase 內，拆分有真實工程成本。

**但架構縫線現在就要留**，否則到時拆不動：

- Pro 模組收斂到少數入口（例如 `main/pro/*`），core 只透過介面呼叫，**core 不 import Pro 的任何具體實作**
- **Pro 模組不存在時 core 要能正常建置與跑**——這正是 **Build A 的定義**（§7.6），等於首發那一版就是開源版的雛形，**零額外成本**
- 實體拆分方式：private submodule，或兩個 repo（core 公開 / app 私有，app 依賴 core）。後者對單人開發省事得多
  - 🔴 **2026-08-07 補**：這兩個選項的共同點是**機械關係**（submodule 綁 commit SHA、依賴綁版本號）。
    **「手工維護一份精簡副本」是第三種，不在此列** —— 它只靠人的記性，而漂移不會報錯。詳見 [BRD-00 U8](BRD-00_索引與決策狀態.md)。
  - ⚠️ 「Build A 就是開源版雛形」這句與 §7.1「配額判定邏輯閉源」衝突，見 [BRD-00 U9](BRD-00_索引與決策狀態.md)

> **雙 build 讓這件事的投報率翻倍**：`main/pro/*` 這條界線同時是**編譯期排除的邊界**（Build A vs Build B）與**開源/閉源的邊界**。
> 一次投資，兩個用途——這也是採用雙 build 的隱藏理由之一。

### 7.4 開源前的必要條件（都不阻擋首發，但都必須在開源當天之前完成）

| 條件                                            | 說明                                                                                                                                                                           |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **依賴授權盤點**                                | 閉源部分若用到 GPL / AGPL / LGPL 靜態連結的套件，你就被迫公開。Electron 生態多半 MIT/Apache，風險低；但 **SQLCipher 要單獨查**（BSD-style，商用情境有 Zetetic 的商業授權議題） |
| **對外口徑不能含糊**                            | 只能說「**核心開源**（open core）」，**絕不能說「PromptBox 是開源軟體」**。後者會被抓，而對信任型產品特別貴——它同時打掉定位與背書機制                                          |
| **CLA / DCO 必須 day 1 就有**                   | 最容易漏的一條。開源後只要收過**一個外部 PR**，那段程式碼的著作權就不再只屬於你——**日後想把那段搬進 Pro 閉源就搬不動了**                                                       |
| **商標不放進開源授權**                          | PromptBox 名稱 + logo 不隨程式碼授權。fork 可以存在，但不能叫 PromptBox 發行。**這是防 fork 最有效、成本最低的一招，比藏程式碼有用得多**                                       |
| **README 明講「本 repo 不含哪些模組、為什麼」** | 配合「我們不做什麼」頁一起上。誠實揭露本身就是行銷素材。同時要說明**可建置範圍**，否則第一個外部 contributor 的體驗會很差                                                      |

### 7.5 誠實的技術現實：藏起來其實藏不住

Electron 的 JS 會以打包形式進 `app.asar` 出貨在使用者磁碟上，`npx asar extract` 就看得到。

「不上傳到 GitHub」實際換到的**不是「別人看不到」**，只有兩件事：

1. 沒有乾淨的建置環境讓人一鍵編出「拔掉 gate 的 PromptBox」
2. 競品要抄得從 minify 過的 bundle 逆推，成本高一個量級

第 1 點是這條界線**唯一真正的商業價值**，而它成立的前提正是 §7.1 的設計：**Pro 功能不在 repo 裡，所以 fork 把 entitlement 檢查刪掉也解不出東西——沒有東西可以解。**

> **推論**：不要為了「保護」而過度擴大閉源範圍。**多藏的每一個模組都在扣信任分，卻不會多換到任何技術防護。**

### 7.6 打包方式：雙 build（✅ 2026-07-31 定案，取代先前的單一 binary）

> **這是一次決策反轉。** 先前依 FP04 §二 採「單一 binary + runtime 權益旗標（approach B）」；現改為**雙 build**。

| Build | 內容 | 誰拿得到 |
|---|---|---|
| **Build A（Free）** | 配額寫死 free 值（45/3/5/2）；**不含 entitlement / Ed25519 / 金鑰輸入 UI 的任何程式碼** | 公開下載 |
| **Build B（Paid）** | 含金鑰輸入口；貼 Ed25519 token → main 離線驗章 → 解除配額 + 開啟 Pro 能力 | 購買後給下載連結 |

**🔴 資料連續性紅線（必須在第一個 build 出貨前釘死）**

> **兩個 build 必須共用同一組 `appId` + `productName`**，只差一個編譯期常數。

原因：`db.cjs` 與 `services/keyService.cjs` 都吃 `app.getPath('userData')`，而該路徑由 `package.json` 的 **`productName` 決定**。若兩個 build 用不同 `productName`（PromptBox Free / PromptBox Pro），`promptbox.db` 與 `keystore.bin` 會留在舊資料夾，**付費版開起來是空的**——這正是先前否決分版 build 的那個災難。

釘住之後：升級 = 下載 Build B **覆蓋安裝**，userData 原地不動，**密碼鎖與機密卡完全不受影響**。
代價：兩版無法並存（本來也不該並存）。備案是明確 `app.setPath('userData', ...)` 釘死絕對路徑。

**一旦有使用者裝了 Free 版，這條路徑就動不得了。**

#### 為什麼改成雙 build

先前否決分版 build 的**唯一實質理由**是資料連續性，而上面的 appId 釘死已經解掉它。解掉之後，雙 build 換到的是：

| 收益 | 說明 |
|---|---|
| **免費版是真的乾淨** | 付費碼**不在 binary 裡**，不是被 `if` 關掉的閹割版，**且沒有 upsell 機制的程式碼** |
| **可驗證性更硬** | [BRD-05 §4](BRD-05_行銷與獲客.md) 的裂變完全靠「你不用信我，你可以自己驗證」。「聯網／付費碼根本不在裡面」比「程式都在但被旗標關掉」是強得多的宣稱 |
| **乾淨 build 機具可複用** | 同一套 build-tier 機制之後直接給企業地端版用（[BRD-04 §3.2](BRD-04_版本路線與時序.md)），不是一次性投資。**創辦人的理由：「乾淨的版本後期可以轉換成別的東西」** |
| **與 open-core 界線重合** | `main/pro/*` 同時是編譯期排除邊界與開源/閉源邊界（§7.3） |

**代價（已接受）**：build 矩陣變兩倍、QA 成本上升、CI 要改成 matrix、升級需重新下載安裝檔而非就地輸入金鑰。

#### ⚠️ 理由要換對，否則會投錯資

雙 build **不是防破解手段**。[BRD-03 §6](BRD-03_授權與Free-Pro邊界.md) 已明文接受弱驗證與一定比例的破解；且 core 開源後，破解者直接改 source 自己 build，**有沒有金鑰輸入框影響接近 0**。

**雙 build 成立的理由只有「可驗證性 + 產品定位」**。把理由記錯，後續就會為了「防破解」去投資混淆工具——那是純浪費（§7.5）。

同理，**加解密程式碼不該混淆**：AES-256-GCM + scrypt 的安全性建立在密碼與 salt，不在演算法保密。混淆它只製造安全假象。真正該保護的只有兩樣：① **Ed25519 私鑰**（本來就不該進 repo）② 差異化的商業邏輯放**私有 repo，CI 時才注入**。
