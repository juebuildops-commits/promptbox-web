## 1. 總綱

> **單一 local-first 核心 + 模組化版本，但版本逐一釋出、對外收斂為少數套餐。**
> **首發的對外菜單只有本地版本；雲端 / 團隊 / 企業地端 / 合規全部後置。**

拒絕兩種極端：

- ❌ **純本地、放棄成長**：定位最純，但市場天花板與護城河過低
- ❌ **全面轉雲端 SaaS / 強制帳號**：成長最大，但直接摧毀隱私品牌與使用者信任

---

## 2. 三軸分類（破除「並列版本」的誤會）

> **這是本冊最重要的觀念，也是防止小團隊燒錢的關鍵。**

先前討論裡提到的「雲端版 / 團隊版 / ISO27001 版 / 醫療版」**不是同一種生物**：

| 軸 | 定義 | 例 | 互斥？ |
|---|---|---|---|
| **部署模式 (mode)** | 改變拓樸（client/server 邊界） | 本地 / 雲端同步 / 團隊 / 地端 | **互斥**（一個 instance 只屬於一種） |
| **跨模式功能 (feature)** | 可加購能力 | AI 包、進階變數 | 可疊加 |
| **合規規範 (compliance)** | 控制項 + 流程 + 證據，**疊在 mode 上** | ISO27001 / SOC2 / HIPAA / IEC62304 | **不是「版本」** |

### 2.1 為什麼合規不是 edition

> **你不會「開發一個 SOC2 版本」，你是「營運一個通過 SOC2 稽核的服務」。**
> **你不會「fork 一份醫療 codebase」，你是「在某個 mode 上疊合規控制項 + 跑一套受監管的開發流程」。**

- **ISO 27001** = 你「組織」的資安管理體系（ISMS）認證
- **SOC2** = 對你「營運的服務」的稽核報告（Type II 要 6–12 個月證據累積）
- **關鍵**：**純本地桌面 App 幾乎沒東西可稽核**。ISO/SOC2 只在你跑了雲端／團隊後端後才有意義——**它們預設了雲端與團隊存在**
- 醫療級更深：若軟體參與臨床決策 = 受監管醫療裝置（SaMD），觸發 IEC 62304 / ISO 14971 / ISO 13485，**此時架構只佔總工作量約 20%**，其餘是 QMS、可追溯性、風險檔案、驗證文件

**把合規當成第 4、第 5 個 edition 去開發，是最容易燒掉小團隊的誤會。**

架構要做的只有一件事：**把控制項接縫（稽核日誌、RBAC、加密）留乾淨**，其餘 80% 是流程與證據。技術面的接縫設計見 [ADR-005 §三](../ADR/ADR-005.md)。

### 2.2 依賴關係

```
雲端同步 ──┐
           ├─→ 才談得上疊 ISO/SOC2 控制項
團隊     ──┘        └─→ 才談得上疊 HIPAA/醫療控制項
```

**雲端與團隊後置 ⇒ 合規自動後置。** 這不需要另外決定。

## 3. 首發菜單（12 個月內的唯一菜單）

| 套餐 | 模式 | 主要內容 | 價格 |
|---|---|---|---|
| **Free** | 本地 | 見 [BRD-03 §2](BRD-03_授權與Free-Pro邊界.md) | $0 |
| **Pro** | 本地 | 解除全部配額 + ~~強型別~~ + 稽核匯出<br>🔴 **強型別自 v3.7.0 全面停用、首發不含**（[BRD-03 §2.6 ②](BRD-03_授權與Free-Pro邊界.md)） | $39 首購 + $27/年更新權（早鳥 $19 / $25 永久鎖價） |
| **永久更新權** | 本地 | Pro + 永久更新 | $149 一次性（發表期階梯 $109→$129→$149，見 [BRD-02 §5.4](BRD-02_商業模式與定價.md)） |
| **商業授權** | 本地 | 功能同 Pro + 公司內使用授權 | $54/人/年（榮譽制） |

**四檔，全部本地，全部零伺服器成本。**

> **原則：「積木」是內部架構的設計手法；給客戶看的菜單必須小**，否則造成選擇癱瘓與計價/支援災難。
> ⚠️ 早鳥三階段（[BRD-02 §5](BRD-02_商業模式與定價.md)）若做成常駐選項，菜單會膨脹到 7 個 SKU——必須做成**限時活動頁**而非常駐 SKU。

### 3.1 明確不在首發菜單的東西

| 項目 | 本質 | 狀態 | 為什麼 |
|---|---|---|---|
| **AI 包** | feature 軸 | **移出首發** | 「中立（不綁任何 AI 廠商）」是要大幅拉高的差異化來源；AI 包即使自帶 key 也稀釋它。且它不在 Pro 的內容定義裡 |
| **雲端同步** | mode 軸 | **後置、不定價、不設計** | 已列入公開的「主動放棄」清單（不當賣點、不當主要營收）。它會拖進 SaaS 成本結構 |
| **團隊版** | mode 軸 | **後置** | 真正的大跳躍：多人 = 多租戶 + RBAC + 並發 + 衝突 + 稽核，你開始營運後端服務（on-call、安全面、SaaS 維運），與隱私品牌直接對撞 |
| **企業 / 醫療地端** | mode + compliance | **後置** | 企業級本地 LLM 落地仍偏早（估 2–4 年順風），適合「**設計時朝此靠**」，不適合現在投入 |
| **ISO27001 / SOC2 / HIPAA / IEC62304** | compliance 軸 | **後置** | 見 §2.1、§2.2 |

> **一句話**：這些**不是被否決，是被排序**。方向仍然成立（見 §3.2），但在付費留存被驗證前，**不定價、不設計、不承諾**。

### 3.2 保留的方向性判斷（不是當期投入）

若/當企業路線啟動，**優先走地端 / air-gapped + 本地 LLM**（資料留在客戶機房），而非雲端 SaaS。

**理由**：此路線**與隱私定位一致**，把「隱私」從成長天花板轉為進入高合規市場的門票；且對隱私敏感組織更好賣（你連碰都沒碰資料）。

**聰明的做法（技術上先留好）**：把未來的團隊領域寫成 **deployment-agnostic**——同一份 server code，配接器一換即可部署成雲端 SaaS **或** 客戶地端/air-gapped。於是「醫療版 = 團隊版 + 地端部署 + 醫療控制項 + 一套 IEC 62304 流程」，**而不是另一條 codebase**。

**但要認知**：內部多人共用仍需 RBAC / 稽核 / 加密——那是真實的工程量，不是換個包裝。

## 4. 執行順序：先收錢，不先重構

### 4.1 曾經的矛盾

| 主張 | 來源 |
|---|---|
| 先做 repository / MCP 收斂 / migrator / registry / entitlement（≈18 人天）→ 才掛第一個付費模組 | 重構規劃的隱含假設 |
| **先讓基礎版收到第一筆錢** | 商業化決策的明文 |

> **矛盾核心：18 人天的內部管線不產生任何使用者價值、不帶來一毛營收。**
> 在「真的有人付錢」被驗證**之前**就投資地基，是單人團隊最容易耗盡現金流與動力的方式。

### 4.2 裁決：走 Hybrid

矛盾的根源，是把「淨賺重構」和「投機重構」綁成同一包。**拆開後就沒有矛盾了**：

| 類別 | 定性 | 與營收的關係 | 動作 |
|---|---|---|---|
| **B1 / repository / migrator** | 「即使不賣插件也淨賺」（DRY + 可測 + DB 可維護） | **與營收解耦** | 本來就值得做，平行慢慢做，但**不記在「變現前置」帳上**、不卡變現 |
| **registry / 完整 entitlement / 多 edition** | 「看商業確定性才做」（投機） | **營收後置** | 等第一筆營收與轉換數據出來，用**真實數據**決定是否投資 |
| **第一筆營收的 gate** | 新增 | **最小接縫** | 種在「未來 registry 也會用的同一個 `entitlement` 接縫」上——**不是丟棄品，是 registry 的種子** |
| **server 側（雲端/團隊/合規）** | greenfield | **維持後置** | 不變 |

> **一句話：別讓漂亮架構擋在第一筆營收前面。** 先用最小接縫收到錢、驗證有人付，再回頭把地基蓋厚——而那條最小接縫，剛好是未來 registry 的種子，不浪費。

**第一筆營收的路徑**：解除容量限制（[BRD-03 §2](BRD-03_授權與Free-Pro邊界.md) 的配額 + 兩個布林能力）。
**併行的第二條**：商業授權 $54/人/年——開發成本近乎為零（一個 token type + 一個價格選項），可能是最快回本的一條。

### 4.3 為什麼可逆性重要

| 路徑 | 最大風險 | 可逆性 |
|---|---|---|
| 先重構後變現 | 做完 18 人天才發現**沒人願意付** → 投機部分幾乎白做；中途失去動力 | **低** |
| **Hybrid（採用）** | gate 短暫污染未重構的 code | **高**——沒人付就移除一個 `if`，近乎零沉沒成本 |

## 5. 首發版本內容

> **首發 = Build A（Free）**，**不含任何 entitlement / Ed25519 / 金鑰輸入 UI 的程式碼**（[BRD-02 §7.6](BRD-02_商業模式與定價.md)）。

| 項目 | 內容 |
|---|---|
| **首發內容** | MCP 活動紀錄（WL-009）+ 技術 Log（WL-010）+ UI 收尾 + [BRD-03](BRD-03_授權與Free-Pro邊界.md) 的配額（**Build A 直接寫死 free 值**） |
| **強型別** | 🔴 **v3.7.0 起全面停用（Free / Pro 皆不可用），首發不含**，之後版本更新再補（[BRD-03 §2.6 ②](BRD-03_授權與Free-Pro邊界.md)）。<br>U6「編譯期完全排除 vs 保留讀取路徑只關 UI」**已於 2026-08-05 結案**：保留讀取路徑、只關 UI + main 拒寫（[BRD-00 §5.1 U6](BRD-00_索引與決策狀態.md)） |
| **Pro 機制** | 驗章 + `licenseStore` + 授權區塊 → **只在 Build B**，等第一個付費價值 + 商業決心到位才做 |
| **升級出口** | Build A 仍保留「撞上限 Modal + 開系統瀏覽器到官網」的連結——**一個連結不是 entitlement 程式碼**，但沒有它漏斗會斷（[BRD-03 §4.1](BRD-03_授權與Free-Pro邊界.md)） |
| **不做的事** | 不做試用配額、不蓋整個 registry / 模組契約平台 |

**這一版同時是 open-core 的雛形**：Build A 的定義（Pro 模組不存在時 core 仍能正常建置與跑）與 open-core 的 `main/pro/*` 邊界**完全重合**（[BRD-02 §7.3](BRD-02_商業模式與定價.md)）——**一次投資，兩個用途**。

### 5.2 🔴 出貨前必須釘死的一件事

> **`appId` + `productName` 兩個 build 必須相同。**

`userData` 路徑由 `productName` 決定，而 `promptbox.db` 與 `keystore.bin` 都在那裡。若兩個 build 用不同名字，付費版開起來會是空的——**機密卡與密碼鎖全部解不開**。

**一旦有使用者裝了 Free 版，這條路徑就動不得了。** 完整說明見 [BRD-02 §7.6](BRD-02_商業模式與定價.md)。

### 5.1 界線畫在首發前，是最便宜的時機

**尚未公開發佈、無任何使用者**（2026-07-31 確認）→ 從第一個公開版就把 Free/Pro 線定死，**之後永遠不會踩 clawback（收回已免費的功能）**。

> 鐵律仍成立：**公開後就不能再收回已免費的功能。** 但因為尚未公開，現在可以乾淨設界、不傷任何人。
> 同樣的邏輯適用於 open-core 界線（[BRD-02 §7](BRD-02_商業模式與定價.md)）——**線一旦公開就收不回**。

## 6. 12 個月路線

| 期間 | 主要目標 | 關鍵動作 | 檢核指標 |
|---|---|---|---|
| **M1–M3**<br>打地基 | **收到第一筆錢** | 首發免費版上線；四檔 SKU + 早鳥開賣；landing page + 3 篇比較頁；GitHub README 改造；「我們不做什麼」頁 | **79 個早鳥付費用戶**（覆蓋全年現金成本） |
| **M4–M6**<br>發行 | 建立第一個穩定通路 | n8n community node + 模板庫；MCP 目錄全面登錄；Reddit 開始長期參與 | 免費裝機月增率；n8n 模板使用數 |
| **M7–M9**<br>驗價 | 找出正確價格 | 標準價 $39 全面上線；A/B 測 $39/$49/$59；in-app 密鑰偵測觸發上線 | **轉換率落在 3–8%**；每組樣本 ≥ 200 |
| **M10–M12**<br>放大 | 把有效通路加倍 | Product Hunt 發表；第三方安全稽核報告公開；模板分享功能上線 | 累計營收；永久更新權佔比 ≤ 30% |

**指標框架採 RARRA（存量思維）而非 AARRR**：對本地工具，留存（Retention）比獲取（Acquisition）重要——先確認第 30 天還在用的比例夠高，再花力氣衝裝機。

**open-core 的啟動點**：第一筆營收之後（約 M4 起可評估），詳見 [BRD-02 §7.3](BRD-02_商業模式與定價.md)。

## 7. 風險

| # | 風險 | 緩解 |
|---|---|---|
| **1** | **QA 組合爆炸**：多配額 gate × **雙 build** × 自動化測試不足 = 回歸風險 | **每個配額 gate 都必須有測試**，否則 G2 grandfather 鐵則無法保證。測試採分層：每模組契約測試 + **兩個 build 各一組端到端 smoke**，**不做全組合** |
| **1b** | **雙 build 的 CI 與升級路徑**：CI 要改 matrix；**產物命名要能區分，但安裝後的 `productName` 必須相同**——這兩件事分開設定，是最容易搞混的地方 | 見 [BRD-02 §7.6 / §9](BRD-02_商業模式與定價.md)。另與 [FP05](../Future%20plans/FP05.md) 的 repo 拆分**都會改 `release.yml`**，先後順序要協調，否則互相覆蓋 |
| **1c** | **升級漏斗斷裂**：Build A 無 auto-update，使用者不知道有新版、也找不到付費版 | ✅ **已解 2026-08-04**（[BRD-00 §5.1 U7](BRD-00_索引與決策狀態.md) 結案）：App 內更新檢查**完全移除**，改 **email 通知 + 官網手動下載**。<br>🔴 **風險轉移而非消失**——漏斗現在 100% 依賴 email 名單，**「下載頁 email 換連結」已升為首發硬前置**（BRD-00 §6） |
| **2** | **範圍蔓延**：手滑去蓋 server / 雲端 / 合規 | 違反本冊 §3.1，PR 應拒收 |
| **3** | **平行開發**：同時做三個版本是小團隊的陷阱 | **由真實付費客戶驗證、一次出一個 edition** |
| **4** | 早鳥三階段讓菜單膨脹到 7 個 SKU | 早鳥做成**限時活動頁**，非常駐選項（§3） |
| **5** | 授權為軟性、可被破解 | 已接受（[BRD-03 §6](BRD-03_授權與Free-Pro邊界.md)）。護城河是商標 + 持續更新，不是 DRM |

## 8. 被拒絕的替代方案

| ❌ 方案 | 為什麼拒絕 |
|---|---|
| 純本地、放棄成長 | 定位最純，但市場天花板與護城河過低 |
| 全面轉雲端 SaaS / 強制帳號 | 成長最大，但直接摧毀隱私品牌與既有信任 |
| 把 ISO27001/SOC2/醫療當並列 edition 開發 | 誤把合規 regime 當 codebase（§2.1） |
| Runtime 第三方插件市集 | 授權/安全/QA 三重地獄，且「prompt 市集」已列入主動放棄清單 |
| 先重構 18 人天再變現 | 可逆性低，是單人團隊最容易死的走法（§4） |
| ~~分版乾淨 build 當作 Pro 的交付方式~~ | ⛔ **此項已於 2026-07-31 撤銷否決，改為採用。** 原否決理由是「不同 appId/userData scope → 機密卡解不開」，但**釘死兩個 build 共用同一組 `appId` + `productName`** 即可解除。改採雙 build，見 [BRD-02 §7.6](BRD-02_商業模式與定價.md) |
