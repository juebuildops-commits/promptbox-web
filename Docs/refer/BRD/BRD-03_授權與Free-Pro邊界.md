## 1. 三條護欄（硬規則，不可違反）

> 這三條凌駕於任何配額調整之上。改配額數字不需要改本節；違反本節需要重開一次商業決策。

| # | 護欄 | 內容 | 性質 |
|---|---|---|---|
| **G1** | **加密永久免費** | **全庫靜態加密（SQLCipher / safeStorage）永久免費、無限、絕不設限。** 付費牆只落在機密卡片的**張數配額**。對外口徑必須是「**加密永遠免費；Pro 賣的是規模與釋放護欄**」，不得讓人讀成「安全要加價」 | 品牌護欄 |
| **G2** | **配額只擋「新增 / 移入」，永不刪除或隱藏既有資料** | 任何情況下既有卡片一律 grandfather、可正常解鎖使用。若某情境出現超額（例如未來調降配額），一律保留、僅擋再加。**違反它＝懲罰最早的支持者** | **工程紅線** |
| **G3** | **gate 兩層** | renderer 只負責「藏 UI / 顯示 upsell」，**永不可信**；真正的能力閘門在 **main process**。未授權的能力，其 IPC handler / 上限檢查在 main 強制 | **工程紅線** |

> G2、G3 是工程紅線——**即使商業決策改變也不該動**。

### 2.0 45 張的計數口徑（2026-08-05 定案）

🔴 **45 是「卡片總數」，機密卡片與 chain 資料夾卡片都算在內。** 不是「45 張一般卡 + 3 張機密卡 + 5 張串聯卡 = 53」。

| 情境 | 結果 |
|---|---|
| 已有 3 機密 + 5 串聯 + 37 一般 = **45** | 🔒 **任何新卡都擋**（包含再開一張一般卡） |
| 已有 44 張、其中 0 張機密 | 可再開 1 張，**開完就滿**——即使機密卡配額還剩 3 張 |
| 已有 45 張、其中 2 張機密 | 機密配額還有 1 格，**但沒有卡可以升級成機密嗎？** → 可以，**把既有卡片設為機密不算新增**（見下） |

**兩個 gate 是獨立的維度，不是相加**：

- **45 = 卡片存不存在**（`prompts:create` 擋）
- **3 = 其中幾張可以是機密**（`prompts:set-secret` 擋）

所以「把第 46 張變機密」不可能發生（根本沒有第 46 張），而「把既有的第 40 張設為機密」只受 3 張配額約束，**不受 45 影響**——因為那不是新增卡片。實作時 `set-secret` **不得**再檢查總數，否則會出現「明明沒有新增卡片卻被擋」的荒謬行為。

**為什麼採總數而非分開計算**：使用者心智模型是「我有幾張卡」，不是「我有幾張一般卡、幾張機密卡、幾張串聯卡」。分開計算會讓「45」這個對外數字失真——講 45 卻實際能存 53，是[誠實紅線 C1](../ADR/ADR-000_索引與技術原則.md)不樂見的那種好聽版本。

⚠️ **這使 45 這道牆比原本估計的更早到**：一個用滿機密（3）與串聯（5）的使用者，實際只剩 37 張一般卡。**這一點必須納入 §8 R1 的重訪判斷**——若轉換率 <2%，第一個要檢查的仍是這道牆，而它的實際緊度是 37 而非 45。

### 2.1 為什麼付費牆的主軸是「機密卡片」而不是「卡片數量」

依狩野模型分類：

| 品質類型 | 對應功能 | 拿它當付費牆的後果 |
|---|---|---|
| **當然品質**（不給會憤怒） | 靜態加密 | 絕不可 gate → G1 |
| **一維品質**（越多越好，但沒有驚喜） | 卡片數量 | 篩的是「**使用時間**」而不是「**付費意願**」——對重度用戶第一週就撞到，對輕度用戶三個月才碰到 |
| **魅力品質**（給了會驚喜，沒有也不會抱怨） | **機密卡片** | ✅ **付費牆應該放這裡** |

**Free 給 3 張的關鍵理由**：如果 Free 完全沒有機密卡片，使用者永遠不知道自己缺什麼。給 3 張，讓他親手體驗「把 API key 鎖起來、AI 要用時彈出授權窗」的那一刻——**這一刻就是轉換發生的地方**。**第 4 張的升級動機遠強於第 46 張。**

### 2.2 釋放稽核為什麼記錄與檢視都免費

> **實作現況查證（2026-07-31）**：釋放稽核 **v3.1 FR-2 已完整實作**——
> `secret_release_audit` 表（append-only、只記 metadata、絕不記明文/密碼、存於加密 DB，[db.cjs:162](../../PromptBox/electron/db.cjs)）、
> MCP 釋放時寫入（[mcpServer.cjs:110](../../PromptBox/electron/mcpServer.cjs)）、
> 查詢 IPC `mcp:list-audit`（[promptHandlers.cjs:330](../../PromptBox/electron/handlers/promptHandlers.cjs)）、
> UI 清單（[McpModal.vue:284](../../PromptBox/src/components/McpModal.vue)）。**唯一沒有的是「匯出」。**

因此邊界這樣切：

- **記錄**：安全需求（誰在什麼時候拿走了哪張機密卡），不能因為沒付錢就不記 → **Free 有**
- **檢視**：是使用者自己的安全資料，藏起來會直接打到 G1 的品牌護欄 → **Free 有，且不設筆數上限**
- **匯出**：**尚未實作的純新功能**，收費零爭議，且少一個配額要測試與維護 → **Pro**

### 2.3 gate 機制為什麼分兩種

| 機制 | 用於 | 為什麼 |
|---|---|---|
| **配額**（卡數 / 機密卡 / chain / token） | 有「數量」語意的能力 | 免費**可以用**，撞上限時自然帶出升級提示。配額單位一律是「**整張卡 / 整個 token**」——乾淨、非半殘 |
| **布林隱藏**（強型別、稽核匯出） | 沒有「數量」語意的能力 | 免費**完全看不到這個詞**。**不做 per-variable 配額**——同卡內「有些變數設了型別、有些被鎖」的半殘狀態太醜。靠獨立升級頁讓人發現 |

### 2.4 ⚠️ 串聯配額：兩種 gate 都做得到，但語意不同

> **2026-07-31 查證程式碼後的更正。** 上游文件給了三個數（原始分析「2 層」／FP04「5 卡」／PRD「3 卡」）——**它們甚至不是同一種度量**。實際上**兩種注入點都已經存在**：

| 候選 gate | 注入點 | 限制的是什麼 |
|---|---|---|
| **A. chain 資料夾卡數**（**本冊採用**） | `folder_id = 'chain'` 計數（`CHAIN_FOLDER_ID = 'chain'`，v3.1 FR-4；單一真相寫在 `settings.chain_folder_id`） | 你**能放幾張卡**進串聯資料夾 |
| **B. 展開深度** | `schemaUtils.cjs` 的 `expandChains(text, { maxDepth })`——**已是 IPC 與 MCP 共用的純函式**，改一處兩邊生效 | 串聯**能疊幾層**（A→B→C 算幾層） |

**採 A 的理由**：配額單位是「整張卡」，使用者看得懂，且與其他配額（卡片數、機密卡、token）的單位一致。

**但實作前必須釐清兩件事**：

1. **`MAX_CHAIN_DEPTH = 5`（`schemaUtils.cjs:164`）是防無窮遞迴的技術安全閥，不是商業限制。**
   **不要把商業配額寫在同一個常數上**——兩種語意混在一起後，調商業配額會動到安全閥。數字剛好都是 5 更容易混淆。
2. **若改採 B**，「串 2 張卡」的語意要先定義：A 引用 B 算 1 層，還是 A→B→C 才算到底？

### 2.5 授權窗與閒置自動鎖為什麼不 gate（2026-08-20 補列）

> **v3.6.0 遺留的缺口。** 該版 PRD 寫過「若日後要把授權窗與閒置自動鎖收進 Pro，必須先改本節」——
> 但表上**根本沒有那兩列**，於是「不 gate」看起來像沒想過，而不是決定過。
> 🔴 **一張真相表最危險的不是寫錯，是缺列**：缺列讓「未決」與「已決不 gate」長得一模一樣。
> 2026-08-20 創辦人裁示補上，兩列皆為**不 gate**。

**理由**：

| # | 理由 |
|---|---|
| 1 | **兩者都是安全能力本身**，不是便利加值。授權窗是 consent 的**時效設計**，閒置自動鎖是明文的**存活上限**——把任何一邊收進 Pro，等於「付錢才能讓機密自動上鎖」，直接違反 [ADR-000 A2](../ADR/ADR-000_索引與技術原則.md)（安全能力永不成為付費牆）與本冊 §1 的 G1 |
| 2 | **收費會產生反向誘因**：Free 使用者為了少按幾次 consent，會傾向把機密卡改成一般卡——**付費牆把人推向更不安全的用法**，這是最糟的一種付費牆 |
| 3 | 它們**沒有「數量」語意**（§2.3），做成配額會是「每天可用 3 次授權窗」這種醜東西；做成布林隱藏又撞第 1 條 |

⚠️ **這兩列不是「AI 相關的一切都不 gate」的意思。** 日後若要把**無頭模式 / CLI 釋放**（使用者不必回到 App 就能完成釋放）收進付費，
🔴 **那要動的是另一列，不是這兩列**——賣的是**自動化與便利**（少切一次視窗），不是安全：
consent 那條路在 Free 版永遠完整、無限、不限次數。**立那一列時必須把這個區分寫在同一格裡**，否則下一個人會直接拿無頭模式來改這兩列。

### 2.6 兩列變更（2026-08-23，[v3.7.0 變數替換規則](../PRD/v3.7.0_PRD_VariableSubstitutionRules.md)）

#### ① 新增「變數替換」開關 —— **不 gate**

| 決定 | 內容 |
|---|---|
| **是什麼** | `preferenceStore.enableAdvancedFeatures` 改名為「**變數替換**」，決定 `{{變數}}` 是否代入使用者填的值 |
| **為什麼要補這一列** | v3.7.0 起它**同時控制 AI 路徑**（MCP）。真相表上沒有這一列，「不 gate」就只是「沒想過」而不是「決定過」——**與 §2.5 補授權窗兩列是同一個理由** |
| 🔴 **為什麼不 gate** | 表上已有「每卡變數數｜無限｜不 gate」。**這個開關就是變數功能本身的總閘門**——gate 它等於 gate 變數，與既有決定直接矛盾 |
| 📌 **歷史提醒** | v3.4.0 已特意把強型別移出這個旗標，理由白紙黑字在 `preferenceStore.js`：「**不拆的話，Free 版關掉強型別會連帶關掉變數**」。**別再把它們綁回去** |

⚠️ **它只管一般卡。機密卡兩條路徑（GUI 解鎖後複製、MCP）一律替換、不看這個開關**——分界線是「有沒有密碼」。
這是**技術決定不是商業決定**，寫在這裡只是提醒：**不要因為它叫「開關」就以為它是可以拿來賣的東西。**

#### ② 強型別：v3.7.0 起**全面停用**（🔴 這是動 Pro 權益）

| 決定 | 內容 |
|---|---|
| **停用範圍** | Free 與 Pro **皆不可用**。既有卡的 `schema_definition` 資料**保留不動**，重做時可直接復活 |
| **為什麼** | v3.7.0 拍板「AI 傳的 `arguments` 一律忽略」，而強型別的 `inputSchema` 帶 `required` / `enum` / 型別約束——**兩者直接打架**。三條路（弱型別化／強型別例外／停用）之中選停用：**一條軸、可逆、不留矛盾** |
| **成本評估** | 依 [WL-037 §5.5](../Wishlist/037.vX.X_WL_機密卡變數預設值加密_WL.md) 記載，創辦人 2026-08-20 確認**產品尚未有實際使用者** ⇒ 回收成本估為零。<br>🔴 **這個前提會過期。** 首發之後再停用任何 Pro 能力，就是**回收已售出的權益**，性質完全不同 |
| **對外口徑** | §9 第 3 條「Pro 賣的是**更多機密卡片 + 稽核匯出 + 強型別 + 解除配額**」⇒ 停用期間**不得再提強型別**。升級頁與行銷文案一併移除 |

🔴 **這一列是本表少數「Pro 欄位變差」的變更**，必須留下痕跡而不是靜靜改掉——
下一個人看到「強型別曾經是 Pro 賣點」時，要能一次讀到它為什麼消失、以及**它是暫時停用不是永久刪除**。

## 3. 四個付費觸發點與 MCP 依賴度

> 這是刻意的風險對沖設計，理由見 §3.1。

| 觸發點 | 依賴 MCP？ | 對誰有效 |
|---|---|---|
| **機密卡第 4 張** | 部分（純本機也有「把 key 鎖起來」的價值；「AI 要用時彈出授權」那一刻需要 MCP） | **主鉤子**，有接 MCP 者轉換最強 |
| **chain 資料夾第 6 卡** | ❌ 不依賴 | 重度使用者（SEO 寫手正是串聯重用者） |
| **強型別（完全隱藏）** | ❌ 不依賴 | 開發者 / n8n 圈（[BRD-01](BRD-01_定位與市場.md) 的第二圈擴散器） |
| **第 46 張一般卡片** | ❌ 不依賴 | 重度累積者 |
| **第 3 個 MCP token** | ✅ 完全依賴 | 已接上 MCP 的進階用戶 |

### 3.1 為什麼要對沖

原始的商業分析裡有一個自我矛盾：它把「MCP 設定門檻」列為第 1 號風險——「你的付費鉤子是機密卡片，而機密卡片的價值要透過 MCP 才展現。但最容易的使用者（SEO 寫手）最不可能自己設定 MCP，**這會讓付費牆變成一道沒人走到的門**」，並主張若做不到 MCP 一鍵化就要下修價格。**但它同時把主付費牆放在機密卡片上。**

**對沖方案**：上表的五個觸發點中，**三個完全不依賴 MCP**。

> **結論：即使 MCP 一鍵化做不到，$39 也不需要下修**（風險已被對沖）。
> 但 **MCP 一鍵接入仍決定主鉤子的強度**，也決定 in-app 密鑰偵測觸發能否兌現 → 已決議**要做**（見 §7）。

## 4. Upsell 呈現規則

| 規則 | 內容 |
|---|---|
| 受限處 | 顯示 👑 標記，**不阻擋操作** |
| 撞上限時 | 輕量 Modal 說明價值 + 「立即升級」開**系統瀏覽器**到官網／金流頁（不在 App 內嵌任何追蹤） |
| **視覺克制** | **勿太顯眼** |
| **可關閉** | 使用者可在設定中**關閉 upsell 提示**。關閉後配額仍然生效，只是不再主動提醒 |

> 「可關閉」這條與信任定位同向：一個保管密鑰的工具不應該在使用者臉上一直閃錢的訊號。

上表的三個未盡之處已拍板，供 PRD／實作直接引用：

| # | 決定 | 說明 |
|---|---|---|
| **a** | **Modal 主按鈕 = 「查看 Pro 方案」**（開系統瀏覽器），次要按鈕才是關閉 | 與上表「立即升級」一致。**撞牆當下的推銷不算噪音**——使用者的操作已被擋住，此刻不給出路才是壞體驗。§4「勿太顯眼／可關閉」約束的是**平時**，不是撞牆瞬間 |
| **b** ⚠️ 2026-08-06 修訂 | **接近上限時顯示配額橫幅**：卡片總數**超過 39 張**（即 40 起）時，於列表上方顯示橫幅，**門檻之上持續顯示**，只能在**設定**中關閉 | 給使用者整理空間的機會，也讓升級決策提前發生。⚠️ **門檻掛在卡片總數上**——機密卡 3 張規模太小，若讓它自己觸發預告，「剩 1 張」等於立刻提醒，那會變成真正的噪音 |
| **b-2** | 橫幅內容 = **三項卡片配額**：`卡片總數 42/45`、`機密卡片 2/3`、`卡片串聯 1/5` | 🔴 **第一項的標籤必須是「卡片總數」，不得寫成「一般卡片」**——45 是總數、含機密與串聯（§2.0）。寫成「一般卡片」會讓使用者把三個數字相加（42+2+1），以為還能開 8 張，實際只剩 3 張。那是會導致錯誤決策的誤導，撞 [ADR-000 C1](../ADR/ADR-000_索引與技術原則.md) |
| **b-3** | 橫幅上**不放關閉按鈕**，但**必須有一句「可在設定中關閉」的小字** | 拿掉關閉鈕之後，設定裡那顆 toggle 就沒有任何入口線索了。§4 上表的「可關閉」本意是給使用者出路，不是把出路藏起來——**一句小字讓橫幅自己當說明書** |
| **c** ⚠️ 2026-08-06 修訂 | **門檻之下不顯示任何配額數字**；門檻之上才出現（原文為「完全不顯示常駐計數」） | 修訂理由：原文擔心的是「持續的視覺壓力」，而壓力來自**無條件常駐**。掛上門檻後，離上限還遠的使用者完全看不到它，只有真的快滿的人才看得到——那時它是**有用的資訊**，不是推銷。⚠️ 仍**不做側欄／狀態列的常駐計數**，那條沒有變 |
| **d** ⚠️ 2026-08-06 修訂 | 🔴 **既有超額使用者（G2 grandfather）照實顯示真實張數**（例如 `卡片總數 80/45`）；新增被擋時仍說明「你目前有 N 張卡片，已超過 Free 版的 45 張上限；**現有卡片完整保留，不會被刪除或隱藏**」 | 這是 G2 在 UI 層的兌現。**不得顯示「45/45 已滿」**——那會隱瞞真實張數（撞 [ADR-000 C1](../ADR/ADR-000_索引與技術原則.md) 誠實紅線），而且使用者刪掉 30 張後仍顯示「已滿」，看起來像 bug。**顯示 80/45 正是 d 的本意**：數字真實、刪卡時會動 |

> **b 的實作提醒**：橫幅顯示與否**每次都依當下計數判斷**，不需要「已提示過」的持久化旗標——
> 唯一的持久化狀態是設定裡的 upsell 開關（§4.3）。
> ⚠️ 計數必須在**每次新增／刪除／設為機密／解除機密／移入或移出串聯資料夾**之後重新取得。
> 一個顯示錯數字的橫幅比沒有橫幅更糟，因為使用者會把它當成 bug。
>
> **d 的實作提醒**（2026-08-06 更正）：~~grandfather 使用者永遠不會觸發 b 的預告~~——
> 修訂後**反過來了**：他們是唯一永遠看得到橫幅的一群人（張數恆在門檻之上）。
> 這是預期行為。舊敘述已作廢，**不要照它把功能「修」掉**。

### 4.2 撞牆的**時機**：在動作開始時，不在提交時（2026-08-05 定案）

| # | 決定 | 說明 |
|---|---|---|
| **e** | **撞牆提示在使用者「按下該動作」的當下出現**，不是在他做完工作按儲存時 | 卡片總數 → 按「新增提示詞」就提示，不讓他寫完一整則 prompt 才說存不進去；機密卡 → 按「設為機密」就提示，不讓他輸入完密碼才失敗。**讓人做完白工才擋，不只是不便，是毀掉他剛做的東西。** |
| **f** | 這是**體驗前移，不是把鎖搬到前端** | renderer 的預檢**永遠只是提示**；`main` 的攔截點與錯誤碼一律保留，繞過 UI 直接呼叫 IPC 仍然擋得住（G3）。技術限制見 [TD §10](../Tech%20Design/v3.4.0_TD_FreeBuildGating.md) |
| **g** | **一律用 Modal 提示，不改按鈕狀態**（不 disable、不置灰） | 與上表「受限處顯示 👑 標記，**不阻擋操作**」一致。disable 按鈕會讓使用者不知道為什麼不能按，而且 renderer 的 disabled 從來就不是鎖 |

> **e 的副作用（已接受）**：擋在門口之後，使用者連編輯器都打不開，無法「先草擬、再回頭刪舊卡騰位置」。
> 對價是不會有人寫完才被丟掉。Modal 文案需引導出路（刪除或升級）。

### 4.3 「關閉 upsell 提示」的關閉範圍（2026-08-05 定案）

§4 上表的「可關閉」需要界定**關掉的是什麼**。定案如下：

| 提示 | 關閉後 | 理由 |
|---|---|---|
| 40/45 預告（b） | ✅ 不再出現 | 典型的「平時主動推銷」，正是「勿太顯眼」要管的東西 |
| 👑 標記（受限處） | ✅ 不再顯示 | 同上 |
| **機密卡撞牆 Modal** | ✅ 降級為**行內小文字**（仍然說明原因，只是不彈窗） | 見下方不對稱說明 |
| **卡片總數撞牆 Modal** | ❌ **仍然彈窗** | 同上 |

> 🔴 **為什麼兩道牆不對稱**——這不是隨手決定，理由必須寫下來，否則之後看的人會當成 bug 修掉：
>
> 採用 §4.2-e 的時機之後，兩者的**處境**不同了。
> **卡片總數牆**發生在使用者**還沒開始做事**的瞬間（剛按下「新增提示詞」），彈窗不打斷任何進行中的工作。
> **機密卡牆**發生在使用者**正在編輯器裡做到一半**，此時蓋一個全屏 Modal 上去，干擾程度高一階。
>
> 「關閉 upsell」的使用者已經表態不想被推銷，對他而言**編輯途中的全屏彈窗最接近噪音**——但**原因仍然必須說**，
> 否則就退化成 [PRD FR-6](../PRD/v3.4.0_PRD_FreeBuildGating.md) 要消滅的「壞掉的按鈕」。所以是降級為小文字，**不是靜音**。
>
> ⚠️ **關閉 upsell 永遠不等於關閉說明。** 任何被擋下的動作，都必須讓使用者知道為什麼。

### 4.1 ⚠️ 雙 build 下的調整（U5 定案後）

打包方式改為**雙 build**（[BRD-02 §7.6](BRD-02_商業模式與定價.md)）後，**Build A（Free）裡沒有金鑰輸入口**，因此：

- ❌ **「設定頁內的獨立升級頁」在 Build A 不存在** —— 那是 entitlement UI，依定義不編進 Build A
- ✅ **保留**：👑 標記、撞上限的輕量 Modal、一個開系統瀏覽器到官網的連結

> **一個連結不是 entitlement 程式碼。** 保留它不破壞「付費碼不在 binary 裡」的宣稱，卻是升級漏斗唯一的出口——
> 拿掉它，[BRD-05](BRD-05_行銷與獲客.md) 的整條轉換路徑會斷在 App 內。
>
> 🔴 **U7 結案後這條的份量升高了**（[BRD-00 §5.1](BRD-00_索引與決策狀態.md)）：App 內已無更新檢查，
> 這個官網連結（設定頁「相關連結 → 官方網站」，`shell.openExternal` 由使用者主動點擊）
> **是 App 內唯一通往外界的出口**，同時承擔升級漏斗與「哪裡拿新版」兩個任務。**不可移除。**

**Build B 才有**：設定頁的授權區塊（輸入框、👑 已啟動狀態、版本線、購買識別、啟動日期、管理授權連結）。

## 5. 授權機制（商業規則）

> 技術實作細節見 [PRD_Entitlement_Licensing](../Future%20plans/PRD_Entitlement_Licensing.md)；本節只定商業規則。

> **前提：本節全部只適用於 Build B。** Build A（Free）不含任何授權機制程式碼（[BRD-02 §7.6](BRD-02_商業模式與定價.md)）。

| 項目 | 定案 |
|---|---|
| **交付方式** | 購買 → 取得 **Build B 下載連結** + 授權碼（email 遞送）→ **覆蓋安裝**（userData 不動）→ 輸入授權碼解鎖 |
| **發放方式** | 由金流平台（Paddle）以 email 遞送授權碼。**App 端不呼叫平台 API** |
| **早鳥價格鎖定** | 由 **Paddle 處理，不進 token**——App 端完全不需要知道使用者付了多少錢 |
| **驗證方式** | **Ed25519 簽章 + App 內嵌公鑰 + main process 本地驗章**。**全程不聯網**，私鑰永不進 binary |
| **失敗行為** | 任何驗證失敗都是**安全退回免費版**（fail-safe），絕不當機、絕不鎖死既有本地資料 |
| **到期檢查** | **App runtime 永不檢查到期。** `updatesUntil` 僅為資訊欄位，由下載伺服器在使用者主動抓更新時驗 |
| **大版本槓桿** | **不採用 `maxVersion` 當收費槓桿**（會與更新權續訂重疊收費）。token 保留欄位但 v1 不啟用 |
| **商業授權** | 同一套 token 機制，`type: "commercial"`。**同樣不檢查到期**（榮譽制的定義） |
| **席次 enforcement** | 合約自報，`seats` 僅作文件用途。**不做技術性數人頭** |

## 6. 破解容忍度（誠實的威脅模型）

> **離線 ⊥ 防破解。這是數學事實，不是能力問題。**

| 事實 | 說明 |
|---|---|
| Electron 的 JS 打包進 `app.asar`，**使用者磁碟上就有，可解包讀** | 私有源碼擋不掉解包 patch |
| **簽章能擋偽造**（沒私鑰簽不出有效碼、改 token 欄位立刻失效） | 但**擋不掉**有心人把 `isEntitled` patch 掉 |
| 對策上限 | gate 放 main、bundle minify。必要時關鍵檢查塞 native 模組（**重，通常不值得**） |

**定案：走弱授權，接受一定比例被破解，不做硬 DRM、不做密碼狗、不做 node-lock。**

理由：
1. **為誠實使用者優化，別做 Denuvo。** 生產力小工具，大多數人不會為省 $39 去 patch asar。
2. 硬 DRM 已列入公開的「我們不做什麼」清單（[BRD-01 §4](BRD-01_定位與市場.md)）——這是定位聲明的一部分。
3. 真正的護城河是**商標 + 建置便利性 + 持續更新**，不是 DRM。詳見 [BRD-02 §7.5](BRD-02_商業模式與定價.md)。

## 7. 連帶的產品決策

| # | 決策 | 為什麼在本冊 |
|---|---|---|
| **P1** | **MCP 一鍵接入要做**（匯出 Claude Desktop / Cursor 設定檔，不要求使用者手改 JSON） | 決定主鉤子強度；不做的話高轉換率的路徑會缺一段 |
| **P2** | **in-app 密鑰偵測觸發要做，優先度等同一個功能** | 見下方 |
| **P3** | **釋放稽核「匯出」是新功能，需排進 Pro 上線的工作項** | 它是 Pro 的兩個布林能力之一，沒做就少一個賣點 |
| **P4** | **AI 包移出首發 Pro** | 中立性（不綁任何 AI 廠商）是要大幅拉高的差異化來源，AI 包即使自帶 key 也稀釋它 |

### P2：in-app 密鑰偵測觸發

> **當使用者第一次在卡片內容裡貼上疑似 API key 的字串時**，跳出：
> 「偵測到看起來像密鑰的內容。要不要把它變成機密卡片？AI 需要時會先問過你。」

這一句話同時完成三件事：**功能教學 + 痛點喚起 + 付費鉤子展示**。而且**完全在本機判斷**，一個位元組都不外傳，不違背隱私定位。

它是「機密卡片當主付費牆」能不能生效的關鍵——**沒有它，使用者可能永遠不知道自己缺什麼**。所以優先度拉到與一個功能同級，而不是當作行銷素材排在後面。

## 8. 重訪條件

> 配額數字不是永恆的。下列情況出現時，回來重看本冊。

| # | 觸發條件 | 要重看什麼 |
|---|---|---|
| **R1** | **轉換率 < 2%** | **第一個要檢查的是 45 張卡片總數上限**（⚠️ 依 §2.0 定案，該數含機密卡與串聯卡——重度使用者的實際一般卡空間可能只有 **37** 張，這道牆比帳面更緊）。這道牆篩的是「使用時間」不是「付費意願」（§2.1），是本表最可能過早把人推走的一格。原始商業分析明確反對用卡片數當付費牆，本冊採用 45 是刻意的取捨——若數據不支持，這是第一個該鬆的配額。**先查文案與鉤子，再調配額，最後才考慮降價** |
| **R2** | 轉換率 > 10% | 定價偏低，走 [BRD-02 §6.5](BRD-02_商業模式與定價.md) 的 A/B |
| **R3** | H1 受眾假設被推翻（見 [BRD-01 §3](BRD-01_定位與市場.md)） | 若實際使用者是**開發者** → 強型別完全隱藏是錯的；若是 **n8n 玩家** → 主鉤子應改為 MCP 相關配額 |
| **R4** | 觀察到破解互傳氾濫 | 才考慮升級授權強度（token 已預留 `machineId` 欄位，**升級不重做**）。在那之前不做 |

## 9. 對外措辭規則（誠實邊界）

> 承接 [ADR-006](../ADR/ADR-006_機密卡片變數預設值以明文儲存.md) 的硬規則並延伸到付費文案。

| # | 規則 |
|---|---|
| 1 | **不得在任何介面暗示變數預設值受加密保護。** 機密卡片的 `variables` 是**明文 JSON**，與卡片密碼完全無關 |
| 2 | **升級頁與行銷文案同樣受此約束。** 不得出現「Pro 讓你的所有資料受加密保護」之類的措辭——**變數預設值在 Free 與 Pro 都是明文** |
| 3 | 正確口徑：Pro 賣的是「**更多機密卡片 + 稽核匯出 + 強型別 + 解除配額**」，**不是「更強的加密」** |
| 4 | 只能說「**核心開源**（open core）」，**不能說「PromptBox 是開源軟體」** |
| **5** | ✅ **「完全不連網」可以講**（2026-08-05 解除限制）。v3.3.0 移除 App 內所有更新檢查，v3.3.1 完成字型本地化，[ADR-000 A5](../ADR/ADR-000_索引與技術原則.md) 已無例外。<br>**能講的**：「完全不連網」「零主動外連」「不做更新檢查、不做遙測、不回報任何使用資料、你的卡片一個位元組都不外傳」。<br>⚠️ **但講的時候要一併說明規則 6 的 MCP 本機 listener**，否則仍會被抓語病。<br>⚠️ 使用者**明確點擊**才開啟的外部連結（官網、回報表單）走系統瀏覽器，不屬於「App 連網」，但**若對方追問要照實說**——這是可驗證性的一部分，不是漏洞 |
| **6** | **內建 MCP 伺服器是本機 listener**（`127.0.0.1`）。講「不連網」時若不一併說明，會被技術使用者抓到語病——**主動說反而加分**（可驗證性） |
| **7** | 🔴 **不得暗示機密卡片的「參數名稱」受密碼保護**（v3.7.0 起）。名字會出現在 MCP `tools/list`，也以明文存在 DB 的快照欄位。<br>**能講的**：「內容需要你按下允許才會交給 AI，一次都不能少」。<br>**不能講的**：「設了密碼，這張卡的一切都藏起來了」。<br>📌 這一層的暴露程度由使用者自己控制——變數名是他自己取的（`{{key1}}` 與 `{{aws_secret_key}}` 差很多），文案可以這樣說明，但**不能拿它來迴避揭露**。見 [ADR-003 §3.1.1](../ADR/ADR-003-soul.md)、[ADR-000 C2 ⑤](../ADR/ADR-000_索引與技術原則.md) |

> **為什麼這條在商業文件裡**：裂變機制放棄了利益誘因，改用「**可驗證性**」降低推薦者的背書成本（[BRD-05](BRD-05_行銷與獲客.md)）。**在付費文案上說謊，會直接砸掉這個機制。** 誠實標示邊界不是保守，是這個商業模式的必要條件。
