## 1. 這個資料夾是什麼

`Doc/BRD/` 收 PromptBox 的**商業決策**：定位、定價、付費邊界、版本時序、獲客。

`Doc/ADR/` 與 `Doc/Future plans/` 只收**技術決策**。兩者過去混在一起，同一件事在不同檔案有不同答案（定價有三個版本、付費牆有三種切法、開源與閉源互相矛盾），已於 2026-07-31 分離。

## 3. 一頁速查

### 3.1 定位

| 項目 | 定案 |
|---|---|
| 市場定義 | **非技術 AI 重度使用者的本機機密 context 保險庫** |
| 主打語句 | 「AI 時代的密碼管理器——但存的是你的 prompt、設定與密鑰。」 |
| 副標 | 「你的 context，存在你自己的電腦；任何 AI 都能用，任何廠商都拿不走。」 |
| 主對標 | Notion / NotebookLM / 記事本（**不是** PromptHub） |
| 第一圈受眾 | SEO 寫手、AI 影像／文案創作者 ⚠️ **H1 未驗證假設** |
| 北極星 | **12 個月內驗證出可重複的付費轉換**（裝機量不是北極星） |

### 3.2 價格

| SKU | 價格 | 語意 |
|---|---|---|
| Free | $0 | 永久免費基底 |
| **Pro 首購** | **US$39** | 永久可用當前版本 + 12 個月更新權 |
| 更新權續訂 | **US$27 / 年**（首購 7 折） | 不續訂＝停在最後版本永久用 |
| 永久更新權 | **US$149 一次性**（發表期階梯 $109→$129→$149，各 50 名，見 [BRD-02 §5.4](BRD-02_商業模式與定價.md)） | 永久授權 + 永久更新（≤30% 累計營收紅線，**階梯就是它的限量機制**）。🔴 網站正式上線前全站隱藏 |
| 商業授權（榮譽制） | **US$54 / 人 / 年** | 純年費、功能同 Pro、App 不檢查到期 |
| **早鳥**（兩批） | 前 150 名 **$19/年**／151–300 名 **$25/年** | **永久鎖價**：續訂永遠是該價格 |

**無月付。** **App runtime 永不檢查到期。** **不採用 `maxVersion` 大版本收費槓桿。** 金流：**Paddle + Payoneer**。

### 3.2.1 打包方式：雙 build

| Build | 內容 |
|---|---|
| **Build A（Free）** | 配額寫死 free 值；**不含 entitlement / Ed25519 / 金鑰輸入 UI** |
| **Build B（Paid）** | 含金鑰輸入口；貼 Ed25519 token → main 離線驗章 → 解除配額 + 開啟 Pro 能力 |

**兩個 build 共用同一組 `appId` + `productName`**（🔴 資料連續性紅線，見 [BRD-02 §7.6](BRD-02_商業模式與定價.md)）。升級 = 下載 Build B 覆蓋安裝，userData 原地不動。

### 3.3 Free / Pro 邊界

| 項目 | Free | Pro |
|---|---|---|
| 一般卡片數 | **45 張** | 無限 |
| 資料夾數 / 每卡變數數 | 無限 | 無限 |
| **機密卡片** | **3 張** ← 主付費牆 | 無限 |
| 卡片串聯 | chain 資料夾 ≤ **5 張卡** | 無限 |
| MCP Token | **2 個** | 無限 |
| 強型別 | ❌ 完全隱藏 | ~~✅~~ ❌ **v3.7.0 起全面停用、首發不含**（[BRD-03 §2.6 ②](BRD-03_授權與Free-Pro邊界.md)） |
| 全庫靜態加密 | ✅ **永不 gate** | ✅ |
| 釋放稽核 記錄 + 檢視 | ✅ **不 gate** | ✅ |
| 釋放稽核 匯出 | ❌ | ✅ |

**三條護欄**：G1 加密永久免費／G2 配額只擋新增、永不刪除既有資料／G3 gate 兩層（main 才是真鎖）。

### 3.4 時序

**首發菜單只有本地四檔。** 雲端 / 團隊 / 企業地端 / 合規 / AI 包 **全部後置、不定價、不設計**。
**先收錢，不先重構**（Hybrid）。第一波公開版 = **Build A**，`pro` 為編譯期常數 `false`，授權機制完全不編進去。

### 3.5 財務

| 指標 | 值 |
|---|---|
| 固定現金成本 | $1,500 / 年 |
| **M1–M3 里程碑** | **79 個早鳥付費用戶**（79 × $19 = $1,501） |
| 標準價覆蓋成本 | 39 個 Pro 新購 |
| CLV / CAC 上限 | ≈ $57 / **≈ $19 每付費用戶**（≈ $0.95 每免費用戶） |
| **續訂率預期**（事先寫下） | **40%** |
| **轉換率預期**（事先寫下） | **3–5%**（健康區間 3–8%） |

> **付費廣告在數學上不成立。成長必須是零付費獲客。**

### U3 的結案理由（不採用 `maxVersion`）

`maxVersion` 是買斷模型裡的**第二個可選收費槓桿**：token 寫 `maxVersion: 3` 代表只解鎖到 v3.x，發 v4 時舊 token 驗成 Free，使用者要再買一次。

**但這與更新權續訂重疊收費**——一個每年付 $27 續訂的人，發 v4 時還要再買一次，那續訂費是買什麼的？

**定案：經常性收入只靠更新權續訂。** token **保留** `maxVersion` 欄位（未來要用不必重做接縫），但 **v1 不啟用**。

### U6：Free build 要多乾淨（連動 U5）

雙 build 定案後浮現的新問題（[WL-022 §5.3 / §5.9-3](../Wishlist/022.vfree_WL_切割版本順序.md)）：

| 做法 | 優點 | 代價 |
|---|---|---|
| **編譯期完全排除**強型別相關程式碼 | 「乾淨」宣稱最硬 | 成本高；且 **Paid → Free 降級會出事**（帶 `schema_definition` 的卡片在 Free build 讀不到處理路徑） |
| **保留讀取路徑、只關 UI + main 拒寫** | Free ↔ Paid 雙向都安全：升級舊卡直接能加 schema（免遷移）、降級靜默退回弱推導（**資料不掉**） | 程式碼還在 binary 裡，「乾淨」宣稱較弱 |

> **✅ 2026-08-05 拍板：採用上述中間解。**
> **編譯期排除的是「entitlement / Ed25519 / 金鑰輸入 UI」**（這才是雙 build 的價值所在——付費碼不在 binary 裡，可驗證）；
> **強型別則保留讀取路徑、只關 UI 與寫入**（換到 WL-022 §5.3 的雙向相容紅利）。
> 兩者不衝突：前者是「授權機制不存在」，後者是「功能被關掉但資料安全」。

#### 拍板理由（2026-08-05）

**「乾淨」這個宣稱的對象是授權機制，不是功能程式碼。** 使用者與推薦者要驗證的是「付費碼不在 binary 裡」——反組譯找不到 Ed25519 公鑰、找不到金鑰輸入口。強型別的讀取路徑留著，不影響這句話成不成立。

**而排除強型別的代價是不對稱的**（[WL-022 §5.3](../Wishlist/022.vfree_WL_切割版本順序.md)）：

| | 保留讀取路徑（採用） | 編譯期完全排除 |
|---|---|---|
| Free → Pro 升級 | 舊卡直接能加 schema，**零遷移** | 需處理既有資料 |
| Pro → Free 降級 | 強型別卡**靜默退回弱推導，資料不掉** | 🔴 帶 `schema_definition` 的卡片在 Free build **讀不到處理路徑** |
| 「乾淨」宣稱 | 不受影響（授權碼仍不在 binary 裡） | 略強，但強在沒人會驗的地方 |
| 實作成本 | 改顯示條件 + main 端拒寫 | 高 |

**降級那格是關鍵**：它直接撞 [BRD-03 G2](BRD-03_授權與Free-Pro邊界.md)「配額只擋新增，永不刪除或隱藏既有資料」。編譯期排除會讓 G2 在技術上無法天然成立，得另外寫遷移或相容碼——**為了一個沒人會驗的「更乾淨」，去換一條工程紅線的實作難度，不划算**。

**技術前提已實測成立**：`schemaUtils.cjs` 的 `getEffectiveSchema()` 本來就有三分支優雅降級，Free 版只要不寫入 `schema_definition`，讀取路徑完全不用動（[WL-022 §5.3](../Wishlist/022.vfree_WL_切割版本順序.md)）。**這個決定不需要新增任何後端程式碼。**

### U7 的結案（2026-08-04）：App 內更新檢查**完全移除**

**定案：走上述選項 2 的最強版本——App 不做任何更新檢查，新版本以 email 通知，使用者自行到官網下載覆蓋安裝。**

#### 為什麼不是「保留 auto-update」

查證程式碼時發現一件事：v3.0 FR-7 的「手動更新」**只把下載與安裝改成手動，檢查本身仍是自動的**。
`src/App.vue` 在 `onMounted` 無條件呼叫 `checkForUpdates()` 去抓 GitHub 的 `latest.yml`——**使用者沒有按任何東西**。

這讓 [BRD-02 §2.1](BRD-02_商業模式與定價.md) 的「『不打電話回家』成立（唯一的伺服器接觸 = 使用者**自願**下載更新）」**當時是一句假話**。
對一個把「可驗證性」當作唯一背書機制的產品（[BRD-05 §4](BRD-05_行銷與獲客.md)），這是不能留的。

#### 落地內容（v3.3.0）

| 項目 | 處置 |
|---|---|
| `electron-updater` 依賴、`autoUpdater.cjs`、`updaterAPI`、`UpdateModal.vue`、`dev-app-update.yml` | **全數刪除** |
| 側邊欄「有新版本可用」橫幅、設定頁紅點、`hasUpdate` state | 全數刪除 |
| CSP `connect-src` | 由 `'self' + api.github.com + github.com + githubusercontent.com` 收緊為 **`'self'`** |
| `package.json` 的 `build.publish` | **保留**——那是 electron-builder 上傳產物用，與 App 內檢查是兩回事 |
| 升級漏斗出口 | 設定頁「相關連結 → 官方網站」（`shell.openExternal`，使用者主動點擊）+ footer「新版本將以 email 通知」 |

### U8：公開 repo 怎麼產生（2026-08-07 提出）

[BRD-02 §7.3](BRD-02_商業模式與定價.md) 已寫過兩個選項（private submodule／兩個 repo 且 app 依賴 core），但實際討論時浮現第三種想法：**手工維護一份「精簡過的副本」**。這三者不等價，必須擇一定案。

| 方式 | 兩份東西的關係 | 漂移風險 |
|---|---|---|
| private submodule | commit SHA 綁定 | 機械保證 |
| 兩個 repo，app 依賴 core | 版本號綁定 | 機械保證 |
| **手工精簡副本** | **只有人的記性** | 🔴 **無任何保證** |

🔴 **為什麼手工副本會漂移**：兩份沒有機械關係的東西，每次改動都要做兩次，漏一次就分岔；而**沒有任何東西會告訴你它們不一致**——漂移不報錯、不變紅，通常是外面的人先發現。

這正是本專案自己寫過的原則，只是規模放大：[v3.4.0 TD §4.2](../Tech%20Design/v3.4.0_TD_FreeBuildGating.md) 拒絕把配額值同時放在 main 與 renderer，理由是「**第一次調配額就會有人只改一邊**」。同樣的失效模式，從一個數字放大到整個 codebase。

**最容易漂移、且傷害最大的四項**（依序）：

1. 🔴 **`appId` / `productName`** —— 兩邊 build 設定分岔 → 既有使用者資料變孤兒（[ADR-000 B5](../ADR/ADR-000_索引與技術原則.md)）。v3.4.0 已加護欄測試釘住，**但護欄在私有 repo，公開 repo 的 build 不受它保護**
2. 🔴 **安全修補** —— 修在私有、忘了同步 → 公開版本持續帶洞，**而那正是別人下載的那顆**
3. **`package-lock.json`** —— 依賴版本分岔 → binary 不同 → 「你讀的原始碼」對不上「你跑的執行檔」
4. **CSP / `index.html`** —— A5 零外連的地基；公開版被加回一個外部資源，宣稱當場失效

**⚠️ 附帶定案建議：測試要留在公開 repo。**
[README](../../README.md) 已對外承諾「專案內有一支護欄測試 `no-outbound.test.js`，7 條斷言」——公開 repo 若沒有測試，這句話變成查無此檔，正中 [§7.2](BRD-02_商業模式與定價.md)「**答不出來時比從來沒開源還糟**」。
且 [BRD-05 §4.2](BRD-05_行銷與獲客.md) 的可驗證性靠「core 源碼可讀」，而**測試是源碼裡投報率最高的部分**：要驗證「不連網」，讀 `main.cjs` 要很久，讀 `no-outbound.test.js` 一眼就懂。第三方稽核者拿到 repo 的第一件事也是看測試。

**真正該排除的是 `Doc/`（定價論證、獲客數學）、`.claude/`、個人筆記——那些都不是 code**，排除它們對可驗證表面的漂移風險趨近於零。

> **無論選哪一種，「排除清單」本身要進 BRD**：它決定了可驗證性宣稱涵蓋到哪裡，那是商業前提，不是工程細節。

### U9：🔴 §7.1 與 §7.3 互相衝突（2026-08-07 提出）

[BRD-02 §7.1](BRD-02_商業模式與定價.md) 的界線表寫：

> **entitlement 驗章 + 配額判定邏輯** → **閉源**（理由：不提供「刪掉這 12 行就好」的現成地圖給 fork）
> 配額數字本身（3/45/5/2）→ **開源**（藏數字沒意義，藏**判定**才有）

但同章 [§7.3](BRD-02_商業模式與定價.md) 又寫：

> Pro 模組不存在時 core 要能正常建置與跑——這正是 **Build A 的定義**，等於**首發那一版就是開源版的雛形**

**兩條同時成立不了。** v3.4.0 已把配額**判定**邏輯實作為 `electron/platform/quota.cjs`，而它**就在 Build A 裡**：

- 若 Build A = 開源版雛形（§7.3）⇒ `quota.cjs` 會公開
- 但 §7.1 說判定邏輯要閉源

**三種可能的解法**（待創辦人擇一）：

| 解法 | 代價 |
|---|---|
| **(a) 判定邏輯改為開源**，修訂 §7.1 | 承認「刪掉這幾行就解鎖」——但 Build A 本來就沒有付費碼可解鎖，且 [BRD-03 §6](BRD-03_授權與Free-Pro邊界.md) 已定案「弱授權、接受被破解」。**與既有定案最一致** |
| **(b) `quota.cjs` 移出開源範圍**，Build A ≠ 開源版雛形 | §7.3「零額外成本」的論證失效；且要另外維護一份 core 能跑的替身 |
| **(c) 重畫界線**：數字與計數開源、**只有 entitlement 驗章閉源** | 最接近 §7.1 原意（「藏判定才有意義」指的是**資格**判定，不是**計數**）。需修訂 §7.1 措辭 |

> **我方傾向 (c)**：§7.1 的理由是「不提供刪掉 12 行的地圖」，而那 12 行指的是**驗章**——Build A 裡的 `quota.cjs` 只是 `COUNT(*)` 跟常數比大小，沒有任何東西可以「刪掉就解鎖」，因為根本沒有鎖。
> 但這是商業判斷，需創辦人裁示。
