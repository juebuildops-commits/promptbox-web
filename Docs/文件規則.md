# 文件規則（怎麼寫、什麼時候寫）

> **這份管「怎麼做」**：什麼時候該開一份新文件、什麼時候不該；檔頭要寫什麼；狀態詞彙怎麼統一；副本怎麼標。
> **[README.md](README.md) 管「東西在哪」**：四個資料夾的定義、要動 X 先看 Y 的對照表。兩份不重複。
> **最後更新**：2026-08-29

---

## 1. 🔴 最重要的一條：不是每件事都要寫文件

App repo 的流程（PRD → Tech Design → ADR）掛在一個叫「**一版**」的單位上：
每個產物都由「發一次 binary」這個動作串起來。**官網沒有這個單位** —— 它連續部署、沒有版本號、
沒有安裝檔、沒有使用者資料。把那套流程照抄過來，等於抄了儀式但沒抄那根軸。

**官網的判準是：文件量跟著「會靜默壞掉的東西」走。**
這和 `check:content` / `check:i18n` 兩支護欄是同一個原則——把靜默壞掉變成建置失敗。

### 動手之前先問這一題

> **這件事，動手之前有沒有東西需要「先決定」？**

| 答案                                                                     | 做法                                                                     |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------ |
| **沒有**（已經知道要蓋什麼）                                             | **不開檔。** 直接做，做完照 §2 回寫                                      |
| **有**（要不要連出去、放哪個位置、深色模式怎麼處理、要不要接第三方服務） | 在 `webplan/` **開一份**，寫清楚「決定了什麼、放棄了什麼」，做完標記狀態 |

**必開檔的三種情況**（不必問上面那題，直接開）：

1. **新增路由、新增 server route、接新的外部服務、新增環境變數** —— 這四件事會改變整個站的形狀
2. **需要 App 那邊也動、或需要 App 那邊為真** —— 開在 `appsync/`，不是 `webplan/`
3. **新增一句對外主張** —— 不是開檔，是去 [webspec/主張與依據.md](webspec/主張與依據.md) 加一列，**而且依據欄要填得出來**

### 反過來，這些**不要**開檔

改文案、改價格數字、加一則 FAQ、加一篇 changelog、調間距顏色、補 i18n key。
這些的失效模式（翻譯不對稱、價格散落、MDC 吃掉 `{{ }}`）**已經有機器在擋**，再加一層文件只會腐化。

> **為什麼要把這條寫死**：一條明知道會被跳過、卻寫成無條件的規則，跳三次就會被訓練成背景噪音。
> 到那時候，真正該寫文件的那次也不會寫。

## 2. 回寫義務：`webspec/` 是唯一「做完要回頭改」的資料夾

`webspec/` 裝的是**現在的樣子**（竣工圖），不是計畫。它有兩份，而且**是同一個動作的兩半**：

| 改了什麼                                        | 回寫哪裡                                                                                               |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 頁面新增／刪除區塊、改變連結去向                | [webspec/PageDescription/](webspec/PageDescription/) 對應那一頁的 **§2 核心內容映射**、**§3 連結拓樸** |
| 新增或改變一句對外主張                          | [webspec/主張與依據.md](webspec/主張與依據.md) 的對應列                                                |
| 動到 design token（色、間距、圓角、陰影、字體） | [webspec/systemV2.md](webspec/systemV2.md)                                                             |

🔴 **兩份一起更新，不要只改一份。** 分開改的下場是其中一份靜默腐化，
而 `PageDescription` 的「核心內容映射」正是「主張與依據」的主張來源清單——
上游沒更新，下游就漏掉一條沒有依據的主張。

> `webspec/PageDescription/` 的體例是逆向分析報告（【事實提取】／【推論分類】／【價值判斷】），
> 讀起來像一次性產物，但**它是這個網站唯一的架構記錄，正本只有這一份**。
> 回寫時只需要動 §2 與 §3，§1 §4 幾乎不會變。

## 3. 檔頭格式：四個資料夾各不相同

### `webplan/` —— 要做什麼

```
> 狀態：⬜ 未動工 ／ 🟡 進行中（缺哪塊）／ ✅ 已上線 ／ ⛔ 已取代（被誰）／ 🚫 主動放棄
> 建立：YYYY-MM-DD　·　最後查核：YYYY-MM-DD
```

**官網沒有版本號**，所以實作進度寫「已上線」而不是「已出貨 vX.Y.Z」。

### `webspec/` —— 現在是什麼

```
> 來源：<它鏡射的程式碼路徑>
> 最後查核：YYYY-MM-DD
```

不需要「狀態」欄——竣工圖只有一個狀態，就是「現行」。**如果它不是現行的，那是 bug，去修它，不是去標它。**

### `appsync/` —— 要跟 App 對上的

```
> 契約對象：App repo（j:/desktopp/githut/PromptBox）
> 正本在：本 repo ／ App repo（路徑）
> 性質：🔒 一次凍結（凍結事件：<哪個動作之後就不能改>）
>       📈 版本化（版本號在 <payload 的哪個欄位>，不在本文件）
>       📋 單向依賴（官網依賴 App 的事實，官網不能改）
> 最後同步：YYYY-MM-DD ← App 端對應 vX.Y.Z
```

🔴 **版本號要長在被交換的東西上，不是長在描述它的文件上。**
授權憑證格式會演進（v2 加欄位、App 要能同時驗 v1 和 v2）⇒ 版本號放憑證 payload 的 `v` 欄位，
文件只記錄「v1 長這樣、v2 加了什麼、App 從哪版開始支援」。
而 [身分字串凍結清單](appsync/身分字串凍結清單.md) **不該有版本號**——
它的全部意義是「過了發 binary 那條線就永遠不能改」，給它 v1.1 等於暗示可以疊代，剛好違背它存在的理由。

### `refer/` —— 唯讀，可疑就回正本

```
> ⚠️ App repo 的副本，快照日 YYYY-MM-DD。
> 正本：j:/desktopp/githut/PromptBox/Doc/　·　它不會跟著正本更新，引用前請先確認正本沒有變動。
> 官網保留它的理由：<一句話。寫不出來的就該移出專案>
```

## 4. 文件狀態詞彙（全類型通用）

### 三個獨立的欄位（不可合併）

#### 4.1 方向有效性 —— 「這份文件描述的方向現在還成立嗎？」

**最重要的一欄。** 任何人（或 AI）打開文件的前 5 秒就該看到它。

| 標記             | 意思                                       | 該怎麼讀               |
| ---------------- | ------------------------------------------ | ---------------------- |
| ✅ **現行**      | 方向成立，可直接當依據                     | 正常讀                 |
| ⚠️ **部分過期**  | 部分章節失效，**必須註明是哪些、被誰取代** | 先看失效清單再讀       |
| ⛔ **已取代**    | 整份方向被新決策取代（Superseded by X）    | 只為追溯而讀           |
| 💤 **待命**      | 方向仍成立，但決定暫不執行                 | 要動手時才讀           |
| 🚫 **主動放棄**  | 評估後決定不做（Won't Do）                 | 只為「為什麼不做」而讀 |
| ⚰️ **Tombstone** | 內容已搬走，只剩指路碑                     | 不要讀，照指路碑走     |

#### 4.2 決策狀態 —— 「這個決定生效了嗎？」

`提議中` / `已拍板` / `已取代`

**「已拍板」＝決策在效力內，與有沒有寫完 code 無關。** 官網的已拍板決策收在
[webplan/待討論問題.md](webplan/待討論問題.md) 的 D1–D31。

#### 4.3 實作進度 —— 「蓋到哪了？」

`⬜ 未動工` / `🟡 部分（說明缺哪塊）` / `✅ 已上線`

> **⚠️ 4.2、4.3 不可合併。** 把「還沒蓋完」寫成「還沒決定」，等於邀請別人重開已結案的辯論。
> 官網踩過反例：階段五六**已規劃、已拍板、刻意暫緩**——三件事同時成立，合併寫就會被讀成「還沒想清楚」。

## 5. 最後查核日期 —— 防止靜默腐化

檔頭附 `最後查核：YYYY-MM-DD`。

**理由**：上面三欄都要有人「做了決定」才會更新，但文件最常見的死法是**沒有任何決定，現實自己走掉了**。

> **實例**：App repo 的 FP05 於 2026-07-06 成文，兩個月後檔案清單一半不存在，沒人發現，
> 因為沒有任何機制會提醒。**這個 repo 已經有一次同型事故**——`Docs/README.md` 在 08-28 被改寫成
> Docs 索引，但根 `README.md` 有三處仍寫著「`Docs/README.md` 是 App 本體說明書」，
> 沒有任何決定出錯，只是現實走掉了。

超過 **3 個月**未查核者，至少開檔確認基準路徑與檔案清單還在。
`webspec/` 的三份**上限縮短到 1 個月**——它們鏡射的是天天在動的程式碼。

## 6. 副本規則

**判準不是「用得到 / 用不到」，是「這裡是正本，還是副本」。**

副本的問題不是佔空間，是**它會過期，而引用它的人不會知道**。

1. **副本一律進 `refer/`**，並標快照日、正本位置、以及「官網為什麼留著它」
2. **正本永遠不要有兩份。** 需要 App 的事實時，抄成 [appsync/App事實依據.md](appsync/App事實依據.md) 那種
   「單向依賴紀錄 + 查核方式」，不要抄成第二份 ADR
3. 🔴 **「零引用」不等於「沒用到」** —— 設計系統、定價表、產品定位這類文件是被**做事的人**消費，
   不被決策記錄引用。`systemV2.md`、`BRD-02`、`ADR-003` 都是這樣被誤判過的例子。
   **引用計數只是線索，不是判決。**

## 7. 資料夾給預設值，檔頭標記可覆寫

用資料夾表達狀態有個上限：**一個檔案只能待在一個資料夾，所以三個軸只能表達一個。**

**規則：資料夾給預設值，檔頭標記可覆寫，兩者不一致時以檔頭為準。**
好處是不必替每份「狀態就是資料夾預設值」的文件加樣板噪音，只有例外才需要標。

各資料夾的預設值：

| 資料夾     | 預設                         |
| ---------- | ---------------------------- |
| `webplan/` | 方向 ✅ 現行、進度 ⬜ 未動工 |
| `webspec/` | ✅ 現行（沒有別的可能）      |
| `appsync/` | ✅ 現行、⏳ 待與 App 對帳    |
| `refer/`   | ⚠️ 副本，可能已過期          |

**搬移的門檻：整份失效才搬；部分失效一律就地標記。**
資料夾位置擋不住誤讀——grep、直接開檔、整包丟進 AI context 都不看資料夾。**真正有效的是檔頭那一行。**

整份死掉時：**直接刪**。這個 repo 不開 `_archive/`——
官網沒有版本號，沒有「當時是怎麼想的」需要追溯的場景，留著只會多一份會被誤讀的東西。
（已執行的例子：`PRD_Entitlement_Licensing.md` 於 2026-08-29 刪除，其內容已由 ADR-008 取代。）

## 8. 命名

| 資料夾     | 命名                                                                |
| ---------- | ------------------------------------------------------------------- |
| `webplan/` | `PRD_<主題>.md`（成階段的）／`<主題>.md`（單點的）                  |
| `webspec/` | `PageDescription/NN_<路由名>.md`；其餘直接用主題名                  |
| `appsync/` | `<主題>.md`。ADR-008 保留原編號是因為 App repo 那邊用同一個號碼指它 |
| `refer/`   | **保持與正本相同的檔名**，方便對帳                                  |

- 🔴 **資料夾與檔名不要有空格。** 舊的 `Future plans/` 害得所有連結都要寫 `Future%20plans`，難讀且容易打錯。
- 官網**沒有版本號**，所以檔名裡不要出現 `vX.X`——那是 App repo 的體例。
