## 一、🔴 兩條回報：不用等你回答，但照現況做下去會出事

### 1.1　W3 的前提有誤 —— 強型別不是 Free/Pro 邊界，是**兩邊都停用**

[App 側回覆](App側回覆.md) W3 寫：

> Free 的邊界不只四項數字配額，還有布林能力 `strongTyping: false`（`limits.cjs:26-28`，硬性 false 無開關）

**`limits.cjs` 的觀察是對的，但推論反了。** 那個 `false` 不是「Free 沒有、Pro 有」，
而是 **Free 和 Pro 都沒有**：

| | 內容 |
| --- | --- |
| **正本** | [BRD-03 §2.6 ②](../refer/BRD/BRD-03_授權與Free-Pro邊界.md)：強型別 **v3.7.0 起全面停用，Free / Pro 皆不可用** |
| **兩條獨立理由** | ① **技術**：v3.7.0 拍板「AI 傳的 `arguments` 一律忽略」，與強型別 `inputSchema` 的 `required` / `enum` / 型別約束直接打架<br>② **時程**（創辦人 2026-09-01 補記）：**重做強型別會拖到上線時間** ⇒ **首發不給，之後版本更新再補** |
| **資料** | `schema_definition` **保留不動**，復出時可直接復活。這是**暫時停用，不是永久刪除** |
| **對外口徑** | 停用期間**不得再提強型別**。現行正確口徑：「更多機密卡片 + 稽核匯出 + 解除配額」 |

🔴 **為什麼這條要回報而不是默默改掉**：照 W3 的字面去做，會做出「Free 隱藏、Pro 開啟強型別」
——**那正好是 BRD 說不要做的那件事**，而且做完之後首發就會延期。
W3 的原意（提醒官網定價頁別漏列邊界）是好的，只是結論要反過來。

**W3 的正確答案**：官網定價頁**沒有列**強型別（已於 2026-09-01 查核，`Src/` 全域無此詞），
**而且不要加**。這是符合 BRD 的狀態，不是漏掉。

### 1.2　BRD 正本在哪，還沒有唯一答案

這條是 [App 側回覆](App側回覆.md) §五 對 ADR-008 提出的同一個要求，方向相反：

| 來源 | 說法 |
| --- | --- |
| 官網 `CLAUDE.md` 紅線 3 | 🔴 **2026-08-30 創辦人確認**：官網 `Docs/refer/BRD/` 六冊**就是 BRD 正本**，改配額、價格、Free/Pro 邊界時以它為準，不必再回 App repo 取 |
| 官網 `Docs/refer/BRD/BRD-02` 檔頭 | **正本**：App repo `Doc/`　·　它不會跟著正本更新，引用前請先確認正本沒有變動 |

**兩者互相矛盾，而且已經產生實際後果**：2026-09-01 官網依創辦人裁示在 BRD 改了 **11 處**（見 §四）。
**如果 App repo 還存在一份 `Doc/BRD/`，那 11 處只改了一邊**，而下一個讀 App repo 那份的人
會看到「Pro 賣點含強型別」——正是 §1.1 要擋的那件事。

**要確認的**：App repo 的 `Doc/BRD/` 現在是什麼狀態？
- 若已刪除或已改成指路存根 ⇒ 官網把 BRD-02 檔頭那句改掉即可，本條結案
- 若仍存在完整六冊 ⇒ 需要一次「正本歸屬」的拍板，並把非正本那一邊改成存根

## 二、要 App 側答的三個問題

### 2.1　v3.7.2 什麼時候出貨？

**這是四件事共同的觸發條件**，而官網現在完全不知道：

| 等它的事 | 為什麼不能提早做 |
| --- | --- |
| **W1** `promptbox.db` → `vault.db` | 提早改＝對還在跑 v3.7.1 的使用者說謊 |
| **W2** `mcpServers` 鍵名 → `vault` | 同上，而且會讓使用者的 IDE 接不上 |
| **W5** [App 事實依據](App事實依據.md) §三「護欄只釘住兩個身分字串」 | App 側自己標註「提早改會提前說謊」 |
| **BRD 5 處**「userData 路徑由 `productName` 決定」 | **現在是真的**，出貨後才變成假的 |

不需要精確日期，**一個條件就夠**（例：「比賽用 Free build 出貨的同一天」）。
沒有它，官網只能反覆回來問。

### 2.2　NSIS `guid` 明設固定 UUID 之後，§1.3 的推導鏈斷了

[身分字串凍結清單](身分字串凍結清單.md) A-1「附帶」欄的邏輯是：

> `guid` 若未明設，electron-builder 以 appId 做 UUID v5 推導 ⇒ **凍結 appId 就一併凍結了它**

[App 側回覆](App側回覆.md) §1.3 拿這條來論證「`productName` 已不是身分字串」：

> NSIS 的升級判定與『程式集裡只有一個』**都由 `appId` 推導的 GUID 決定**

**但 §1.2 同時決定要「明設固定 UUID」。** 一旦明設，`guid` 就與 `appId` 脫鉤：

| | 未明設（現況） | 明設固定 UUID（v3.7.2 決定） |
| --- | --- | --- |
| `guid` 從哪來 | 由 `appId` 推導 | **獨立的字面值** |
| 凍結幾個東西 | 凍 `appId` ⇒ 兩個都凍住 | **要凍兩個**：`appId` **和** `guid` |
| §1.3 的論證 | 成立 | **前提消失** |

**結論（`productName` 自由）很可能仍然對** —— 升級判定改由明設的 `guid` 決定，
`productName` 一樣不參與。但**理由要換一句話**，而且：

- 🔴 **`guid` 要進凍結表**，成為第三個獨立凍結的身分字串（現在表裡只寫「明設固定 UUID」，**沒有值**）
- 護欄測試要多釘一條

### 2.3　憑證裡有三個帶品牌名的字串，驗證端在 App

ADR-008 暫緩沒有問題，但這三個字串的**定案機制和身分字串完全一樣**：

| 字串 | 出處 | 為什麼是「發出去就回不去」 |
| --- | --- | --- |
| `iss: "promptbox.app"` | [ADR-008 §二](ADR-008_授權憑證格式與離線驗證契約.md) | §四 步驟 5 要求**逐字相符**才通過。改它 ＝ 已簽出的憑證全部驗不過 |
| `kid: "PB2026A"` | [ADR-008 §一／§五](ADR-008_授權憑證格式與離線驗證契約.md) | §五 明訂**舊 kid 永不移除**（移除 ＝ 一次撤銷所有用它簽過的憑證） |
| `typ: "pbent+jws"` | [ADR-008 §一](ADR-008_授權憑證格式與離線驗證契約.md) | 進簽章基底，同上 |

**時間壓力確實低於身分字串**（一份憑證都還沒簽出，現在改成本為零），
但**第一份憑證簽出的那一刻就永久定案**，和「發出比賽用 Free build」是同一種門檻。

而且它與 §三 3.1 連動：如果產品改名，`iss` 會變成一個**指向不存在網域的簽發者識別**。

**建議的處理方式**：不必現在拍板值，但把這三個字串**加進 [身分字串凍結清單](身分字串凍結清單.md)**
（清單目前完全沒有這三格），觸發條件寫「第一份憑證簽出之前」。這樣它就不會再掉出去。

## 三、要創辦人拍板、而且**同時擋著雙方**的三件事

### 3.1　🔴 產品名 —— 四條線的共同根，而且已逾期

[App 側回覆](App側回覆.md) §1.2 把 `productName` 定為「**不凍結，隨品牌走**」。
這在身分字串的層面是對的解法，**但它把問題移交給了一個還沒有答案的東西**：

```
產品名拍板 ── 未定，「預計下週處理」寫於 2026-08-27（今天 2026-09-01）
   │
   ├─▶ 官網階段五六（暫緩理由之一就是「等改名定案」）
   ├─▶ P6 網域 ──▶ P7 SPF/DKIM（DNS 生效有等待時間）
   ├─▶ 官網全站 A 類品牌字串替換
   └─▶ ADR-008 的 iss（見 §2.3）
```

公司身分已於 2026-08-28 拍板（覺構 / JueBuild），**但那是公司名不是產品名**，
所以 8/31 的身分字串拍板**沒有連帶解決它**。詳見 [上線前置鏈](../webplan/上線前置鏈.md) P6／P7。

### 3.2　`app.setName()` 的最終值

[App 側回覆](App側回覆.md) §1.2 表裡填 `Vault`，緊接著自己標 ⚠️ 可能要改成 `EYChen Vault`，
並註明**必須在發出第一個 mac build 之前決定**。

**但它沒有被列進 §二 動作清單，也沒有列進 §四 暫緩區** —— 它不屬於任何一張表。

這是**唯一會出現在使用者眼前的身分字串**（macOS 鑰匙圈授權對話框），
所以它的取捨和 userData 路徑不同：路徑對不上只是觀感，
這一格是**使用者被要求授權時看到的名字**。

### 3.3　下載檔案放哪（[金流接縫](官網金流與授權發放接縫.md) §9 前置 #4）
