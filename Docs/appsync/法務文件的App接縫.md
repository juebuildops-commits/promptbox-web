## 1. 為什麼 App 端會出現法務缺口

**App 完全不連網**（[App 事實依據](App事實依據.md) A5）。
條款、隱私政策、開源授權聲明**全部只存在官網**。

⇒ 一個從 zip 拿到 App、從來沒開過官網的使用者，**看不到任何一份法務文件**。

這不是理論上的邊角：下載頁同時提供 NSIS 安裝檔與**免安裝 zip**，後者連安裝流程都沒有。

> 🔴 **這個縫是零連網換來的，不是 bug。**
> 但它讓「條款對使用者有沒有拘束力」變得很薄 —— 使用者從未被呈現過條款，
> 事後主張他同意過就很勉強。**§3 要裁的就是這件事。**

## 2. L17　第三方開源授權聲明

### 2.1 性質：這是義務，不是選配

MIT / BSD / Apache-2.0 幾乎都要求**散布時保留著作權聲明與授權全文**。
「散布」＝**發出安裝檔**。

⇒ 這項義務**從第一個對外 build 起就成立**，與收不收費、有沒有公司登記、有沒有上線都無關。
換句話說：**它現在就已經欠著了**，不是等 Pro 上架才需要處理。

### 2.2 目前狀態（2026-09-09 實查，App v3.8.1）

`PromptBox/package.json` 的 **runtime 依賴 11 項**（會被打包進出貨物），另加 Electron 本體：

| 套件 | 授權（抽查） |
| --- | --- |
| `electron` | MIT |
| `@modelcontextprotocol/sdk` | 未查 |
| `better-sqlite3-multiple-ciphers` | **MIT**（見 §2.3） |
| `express` | MIT |
| `markdown-it` | MIT |
| `highlight.js` | **BSD-3-Clause** |
| `@tailwindcss/typography`、`ajv`、`pinia`、`uuid`、`vue`、`vue-i18n` | 未查 |

⚠️ **上表是抽查不是盤點。** 真正要交付的是**含遞移依賴的完整清單**——
直接依賴只有 12 個，但 `node_modules` 實際會有數百個，**每一個都可能帶自己的條款**。

**目前 App 與官網兩邊都沒有任何 NOTICE 檔案。**

### 2.3 🔴 SQLCipher 那條待辦：實查結果與 BRD 的擔心不同

> 📌 **2026-09-18 補**：App 實際使用的加密方案是 SQLite3MultipleCiphers 的 **`chacha20`**，**不是 SQLCipher 方案**
> （App `electron/platform/dbCipher.cjs` 明設；以 `sqlcipher` 方案重開同一檔會失敗。創辦人同日查核確認，官網全站已改口，見 [WL-006 §2-5](../Wishlist/006.WL_mac暫停下載與Windows換新版.md)）。
> ⇒「擔心的方向可能錯了」多一個佐證。🔴 **但本節仍未結案**：血緣問的是**編進去的整個函式庫**有沒有引用 Zetetic 的程式碼，
> 而不是「用了哪一個方案」—— SQLCipher 相容的實作照樣在 binary 裡。T2 照原流程查。

[BRD-02 §9](../refer/BRD/BRD-02_商業模式與定價.md) 有一條躺著沒動的待辦：
「依賴授權盤點（**特別是 SQLCipher 的商用條款**）」。

**實查**：`better-sqlite3-multiple-ciphers` 的 `package.json` 宣告 **MIT**。
它底層用的是 **SQLite3MultipleCiphers** —— 那是一個**獨立實作**，
不是 Zetetic 的 SQLCipher 原始碼 ⇒ **Zetetic 的商業授權條款很可能不適用。**

> ⚠️ **但這只查到 npm 套件宣告的那一層。**
> 要真的結案，必須對上游專案確認「SQLCipher 相容的頁級加密是自行實作，還是引用了 Zetetic 的程式碼」。
> 🔴 **不要憑本檔把 BRD 那條待辦劃掉**——本節的價值是「擔心的方向可能錯了」，不是「已經沒事了」。

### 2.4 誰做什麼

| 動作 | 歸誰 | 為什麼 |
| --- | --- | --- |
| **盤點**（跑工具、產生含遞移依賴的清單） | **App repo** | 清單由 `package.json` / `node_modules` 決定，而那只存在 App repo |
| **確認 §2.3 的 SQLCipher 血緣** | **App repo** | 同上，且需要看實際編譯進去的東西 |
| **產出 NOTICE 檔** | **App repo** | 它要隨 build 打包 |
| **官網 `/licenses` 頁** | **官網 repo** | 呈現同一份內容（L18 已定：開這條路由） |
| **決定正本歸屬** | 見 §2.6 | |

### 2.5 產出物形狀（建議）

- 一份 `THIRD-PARTY-NOTICES.txt`（純文字，含每個套件的名稱、版本、授權名稱、著作權聲明與全文）
- **隨 build 打包**進安裝目錄（zip 版也拿得到）
- 官網 `/licenses` 放**同一份內容**

> 🔴 **兩邊必須是同一份。** 這正是 [文件規則 §6](../文件規則.md)「正本永遠不要有兩份」的場景 ——
> 一份會過期的授權聲明比沒有更糟，因為它看起來像已經盡到義務了。

### 2.6 正本歸屬：建議放 **App repo**

**理由**：清單的事實來源是 `package.json`，而那在 App repo。官網放的是鏡像。

> 📌 **這與 BRD 正本在官網 repo 是相反方向，而且是刻意的**：
> **正本跟著事實走，不跟著文件體系走。**
> BRD 的事實是商業決策（創辦人在官網 repo 拍板）⇒ 正本在官網；
> 授權清單的事實是依賴樹（只存在 App repo）⇒ 正本在 App。

⇒ 官網這一側要在 `/licenses` 頁標明「本頁鏡像自 App repo，快照日 YYYY-MM-DD，對應 vX.Y.Z」，
並在 App 發版 SOP 加一步：**依賴有增減時，官網那份要重抓**。

## 3. L21　條款怎麼觸達到 App 使用者（🔴 待裁）

### 3.1 三個選項

| 選項 | 做什麼 | 成本 | 效果 | 風險 |
| --- | --- | --- | --- | --- |
| **A** 安裝器授權同意頁 | NSIS 安裝流程加一頁「我接受條款」 | **低**（見 §3.2） | 最接近「使用者確實被呈現過條款」 | 多一個安裝步驟；**zip 版完全繞過**；條款改版時安裝檔裡那份會過期 |
| **B** App 內「關於／開源授權」 | 設定頁加一節，放版本、授權聲明、條款連結 | 中（要做 UI + i18n 三語） | 隨時查得到；zip 版也有 | 使用者不會主動去看；條款全文塞不進 App，只能放連結，而**點連結會開系統瀏覽器**（那是使用者在連網，不違反 A5） |
| **C** 只在下載頁註明 | 官網下載頁加一句「下載即表示你已閱讀條款」 | **極低** | 至少有一個呈現點 | 拿到 zip 的人（轉寄、內部分享）從來沒經過下載頁 |

### 3.2 🔴 選項 A 與凍結清單的關係：不衝突

實查 App `package.json` 的 `build.nsis`：

```
"nsis": { "oneClick": false, "perMachine": false,
          "allowToChangeInstallationDirectory": true, "guid": "bf70f23a-..." }
```

`oneClick: false` ⇒ 是 **assisted installer**，electron-builder 的 `nsis.license` 在這個模式下有效
⇒ **技術上是加一個設定鍵 + 一個檔案，不是改安裝器。**

[身分字串凍結清單](身分字串凍結清單.md) 管的是 `appId`（`com.eychen.vault`）、`productName`、
NSIS `guid`、userData 路徑 —— **`nsis.license` 不碰其中任何一個。**

> ⚠️ **但要確認一件事**：加了授權頁會讓安裝流程多一步，
> 而 v3.7.2 的 Windows 驗收是**照步驟數走的**。要一併確認驗收腳本不會因此失敗。

### 3.3 建議：**B + C，A 先不做**

- **C 現在就能做**，成本近乎零，而且 L18 的 `/terms` 一上線就順手加。
- **B 是真正解決問題的那個**——它同時裝下 §2 的 NOTICE 與條款連結，且 zip 版也涵蓋。
- **A 的效果被 zip 版稀釋掉一大半**，而且「安裝檔裡的條款會過期」是一個沒有護欄在守的新腐化點。
  🔴 **等到真的有錢進來（Pro 開賣）再評估**——那時「使用者是否同意過條款」才有實質意義。

> 📌 **B 有一個附帶好處**：目前 App 內沒有任何地方顯示版本號以外的產品資訊。
> 「關於」頁順便解決了「使用者怎麼知道自己在用哪一版、去哪裡找手冊」。

## 6. 一句話

**§2 是欠著的義務，§3 是還沒決定的形式。**
兩者的共同前提是同一件事：**App 完全不連網，所以任何法務文件都不會自己走到使用者面前。**
