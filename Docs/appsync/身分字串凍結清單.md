# 身分字串凍結清單（Identity Freeze Checklist）

> **用途**：在**發出任何安裝檔之前**，把一批「使用者看不到、但決定他們的資料還在不在」的字串一次定死。
> **觸發原因**：產品即將因商標問題改名，同時要在比賽釋出 Free 版。
> **建立**：2026-08-27　**狀態**：⏳ 待執行，**且必須在發 binary 之前**
> **範圍**：主要在 App repo（`PromptBox`）。官網只受 A 類影響。

---

## 為什麼有這份清單

改名影響的東西分成兩類，而它們的風險差了好幾個數量級：

| | A 類：品牌字串 | B 類：身分字串 |
| --- | --- | --- |
| 例 | 官網文案、視窗標題、關於視窗 | `appId`、Keychain service 名稱、DB 檔名 |
| 使用者看得到嗎 | 看得到 | **看不到** |
| 改了會怎樣 | 沒事 | **既有使用者的資料變孤兒，或永久解不開** |
| 怎麼改 | `sed 's/PromptBox/新名字/g'`，一行 | **不改。永遠不改** |

A 類**不需要任何預留設計**。`PromptBox` 是個獨特的專有名詞，全域取代不會誤傷；為它做參數化只會讓語系檔變難讀。

B 類是這份清單的全部內容。

> **一句話**：品牌名字可以換，身分字串不能。
> Firefox 的設定檔路徑到今天還寫著 `Mozilla` —— 那不是遺留問題，那是正確做法。

## 🔴 步驟 0：先確認你在哪一條分支

這決定後面所有動作：

- [ ] **外面有沒有已經安裝並且有資料的使用者？**（包含你自己、測試機、給朋友試用的）

| 答案 | 分支 |
| --- | --- |
| **有** | 走 **§A 凍結分支** —— 現值就是永久值，逐項抄下來，一個字都不能動 |
| **完全沒有** | 走 **§B 重選分支** —— 這是你**最後一次**可以自由決定這些字串的機會。改名之後就沒有了 |

> README 記載版本歷程從 v1.0 到 v3.7.1，因此**預設假設是「有」**。
> 只有在你能確定「這些安裝全部可以整台重來、資料丟掉沒關係」時，才走 §B。

## §A 凍結分支：逐項抄下現值

每一項都：**先印出現值 → 抄進表格 → 在程式碼裡寫死 → 加進護欄測試**。

| | |
| --- | --- |
| 在哪 | `electron-builder` 設定的 `build.appId` |

#### 🔴 這一項有個衝突，必須正面處理

`productName` 同時是**安裝程式顯示名稱**和**userData 目錄名稱**。
你會想讓安裝程式顯示新名字 —— 但那會動到目錄名稱。

**解法：把 userData 路徑從「推導」改成「寫死」，之後 `productName` 就自由了。**

```js
// main.cjs / main.js —— 必須在【任何】 app.getPath('userData') 呼叫之前，
// 包含被 import 的模組的 top-level 程式碼。放在檔案最上方、require 之後第一行。
//
// 🔴 這個字串是 2026 年改名前的 productName，【永遠不要改】。
//    它與品牌名稱無關，它唯一的工作是讓既有使用者的資料留在原地。
app.setPath('userData', path.join(app.getPath('appData'), 'PromptBox'))
```

驗證方式：在**改動之前**先跑一次 `console.log(app.getPath('userData'))`，
把輸出逐字抄進上面那行。兩者必須完全相同，包含大小寫。

- [ ] 已印出改動前的 userData 路徑並逐字抄錄
- [ ] `app.setPath` 位置確認在所有 `getPath('userData')` 之前

### A-3　🔴 加密金鑰的儲存識別（最致命的一項）

SQLCipher 的金鑰存在 OS 金鑰庫裡。**識別字串一改，既有資料庫就永久解不開** ——
這不是「資料變孤兒」（還找得到、還能救），是**資料真的沒了**。

先確認你用的是哪一種：

| 實作 | macOS 上的識別 | 改名的風險 |
| --- | --- | --- |
| Electron `safeStorage` | Keychain 項目名為 **`{app.getName()} Safe Storage`** | 🔴 **極高**。名稱直接由 `getName()` 推導 ⇒ 改名即失效。A-2 的 `app.setName()` / 路徑寫死**不一定**擋得住這條，需另外確認 |
| `keytar` / 自寫 | 程式碼裡的字面字串（service / account） | 中。字串是明寫的，找到並標註「不可改」即可 |

- [ ] 確認實作方式：`________________________`
- [ ] 找到識別字串現值：`________________________`
- [ ] 已在該處加上「🔴 永不變更」註解並說明後果

> 若是 `safeStorage`：在 `app.whenReady()` 之前呼叫 `app.setName('<改名前的名稱>')`，

## §B 重選分支：完全沒有既有安裝時

這是最後一次自由選擇的機會，選了就變成 §A。

建議原則：

1. **身分字串用一個中性、不會再改的識別**，不要用品牌名。
   例如 `com.<你的網域>.app` 這種形式 —— 但網域也可能改，所以更保險的是一個**你確定永遠屬於你**的字串。
2. **一次選好，同一天寫進護欄測試**，不要留到「之後再說」。
3. A-4 的檔名可以順勢改成中性名（例如 `vault.db`），這樣未來任何改名都不會碰到它。

## 護欄：擴充 `ADR-000 B5`

App repo 已有一條**五行護欄測試釘住 `appId` 與 `productName`**，README 明載它擋的正是
「日後做雙 build 時產物要能區分」這個很合理的動機。

現在有第二個很合理的動機（改名），而且它的破壞力更大。**擴充同一條測試**：

```
既有：appId、productName
新增：userData 路徑（A-2）
      金鑰庫識別字串（A-3）      ← 最重要
      DB 檔名 × 2（A-4）
      MCP server 識別（A-5）
```

- [ ] 護欄測試已擴充至上述全部項目
- [ ] 測試的失敗訊息有寫清楚「改這個會弄壞既有使用者的資料，看 Docs/身分字串凍結清單.md」

> 護欄的價值不在阻止你，在於**六個月後的你會看到那句話**，而那時候你已經忘記為什麼了。

## 🔴 驗收：唯一能證明沒弄壞的方法

程式碼審查證明不了這件事。**必須實機跑一次**：

1. 用**改名前**的建置安裝
2. 建立一些資料：普通卡片、**一張有密碼的機密卡**、一個 MCP Token
3. 完全關閉
4. 用**改名後**的建置**覆蓋安裝**（不是先解除安裝）
5. 開啟，確認：
   - [ ] 卡片全在，數量一致
   - [ ] 🔴 **機密卡能用原密碼解開**（這一步證明 A-3 沒破）
   - [ ] MCP Token 還在，IDE 連得上
   - [ ] 設定（主題、變數替換開關）保留
   - [ ] 「程式集 / 應用程式」裡**只有一個**，不是兩個（這一步證明 A-1 沒破）

Windows 與 macOS **各跑一次**。兩邊的失敗模式不同，過了一邊不代表另一邊沒事。
