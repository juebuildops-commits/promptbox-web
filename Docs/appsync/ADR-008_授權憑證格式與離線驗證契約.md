# ADR-008: 授權憑證格式與離線驗證契約（Entitlement Format & Offline Verification Contract）

## 狀態

提議中 (Proposed) - 2026-08-27

> 本 ADR 把官網重構期間拍板的 D9–D25（見 `promptbox-web/Src/docs/待討論問題.md`）中
> **涉及 App 端行為**的部分固化為契約。上承 App repo ADR-002（買斷、地端優先、不自建後端）
> 與 App repo ADR-005 §四/§七（乾淨 build／信任邊界／離線弱授權）。
>
> **取代** PRD_Entitlement_Licensing（已刪除，內容由 ADR-008 取代） **§6.1 / §6.2 / §6.3 / §6.5**
> ——那份草稿（2026-06-16）成文於金流選型與雙 build 決策之前，其 token 結構
> （含 `updatesUntil` / `maxVersion`）與儲存位置（`safeStorage` + electron-store）
> 已被本 ADR 推翻。該 PRD 的**其餘部分仍然有效**，見 §7。

> **一句話**：憑證是一份**綁 email、永不過期、離線可驗**的簽章聲明；
> 「誰有 Pro」由它回答，「什麼時候能拿新版」由**官網的下載閘門**回答，
> 兩者永不在同一個地方判斷。

---

## 背景

雙 build（D15）定案後，授權模型從「一個 binary + runtime 旗標」變成兩道各司其職的鎖：

| 鎖 | 管什麼 | 在哪裡執行 | 有期限嗎 |
| :-- | :-- | :-- | :-- |
| **binary 閘門** | **什麼時候**（更新權） | 官網的 Pro 下載頁 | 有 |
| **entitlement** | **誰**（Pro 資格） | App main process，離線 | **永遠沒有** |

這個分離是 [§六 對外已公開的承諾](../webplan/待討論問題.md)裡兩條最硬的話唯一的實作方式：

> - 🔴 App runtime 內從不檢查到期日、永不 time-bomb
> - 🔴 更新權到期後，已安裝版本永久正常運作，絕不會被鎖住或降級

只要有效期出現在憑證裡，這兩句就守不住 —— 不是因為會有人故意去讀它，
而是因為**只要那個欄位存在，遲早有人會加一行 `if`**。

---

## 決策總綱

**憑證為 Ed25519 簽章的 compact JWS，綁 email、不含任何時間性欄位；
App 以內建公鑰表離線驗簽，驗證僅在 main process 進行，任何失敗一律安全退回 Free。**

---

### 一、格式：compact JWS，不是自訂 JSON + 附檔簽章

- **決策**：憑證是一個 **compact JWS 字串**（`header.payload.signature`，三段 base64url）。

  ```
  eyJhbGciOiJFZERTQSIsInR5cCI6InBiZW50K2p3cyIsImtpZCI6IlBCMjAyNkEifQ.
  eyJ2IjoxLCJpc3MiOiJwcm9tcHRib3guYXBwIiwic3ViIjoiYnV5ZXJAZXhhbXBsZS5jb20iLC4uLn0.
  <64 bytes base64url>
  ```

- **理由**：`PRD_Entitlement_Licensing` §6.1 寫的是「簽 `canonical(payload)`」——
  那需要一個雙方同意的 JSON 正規化規則（JCS / RFC 8785）。**這是離線驗簽最容易出錯的一環**：
  簽發端與驗證端只要對鍵序、Unicode 正規化或數字表示法有一點分歧，簽章就會無故失效，
  而且**只在某些憑證上失效**，極難重現。

  compact JWS 直接繞過它：簽的是 **base64url 編碼後的位元組**，驗的也是同一串位元組，
  中間沒有任何解析。payload 怎麼序列化都無所謂，因為根本不重新序列化。

- **`typ` 刻意不是 `JWT`**：用 `pbent+jws`。憑證**沒有 `exp`**（見 §三），
  而任何一個通用 JWT 函式庫看到 `typ: "JWT"` 都會傾向「檢查／要求／補上」到期時間。
  換一個 `typ` 是為了讓「這不是 session token」在**型別層面**就講清楚。

---

### 二、payload：綁 email，不綁機器

- **決策**：

  ```jsonc
  {
    "v": 1,                          // 憑證格式版本；bump = App 必須更新才認得
    "iss": "promptbox.app",          // 簽發者，驗證時必須逐字相符
    "sub": "buyer@example.com",      // D12：綁 email，小寫正規化
    "plan": "pro",                   // "pro" | "lifetime" | "commercial"
    "seat": 1,                       // D23：商業授權買 4 送 1，各席次 1..5
    "order": "polar_ord_xxx",        // D10：購買憑證溯源，App 不解讀
    "jti": "5f1c…",                  // 唯一識別，供客服比對與重發判重
    "iat": 1787443200                // 簽發時間（Unix 秒）——僅供顯示與客服
  }
  ```

- **`plan` 是純顯示欄位**（D13）：`commercial` 與 `pro` 的**配額邏輯完全共用**。
  App 端不得出現 `if (plan === 'commercial')` 這種能力分支 ——
  商業授權賣的是合規與支持，不是功能。

- **`sub` 是 email 而不是機器指紋**（D12、B3）：綁機器需要啟用流程、換機補發與客服，
  而它擋不住的正是最常見的分享行為（同一個人多台機器）。綁 email 是**社交嚇阻**：
  憑證上有你的信箱，分享出去等於把自己的信箱貼在網路上。

- **`iat` 只用於顯示**：設定頁可以寫「啟用於 2026-08-27」。
  🔴 **不得用於任何判定** —— 一旦有人拿它算「已經過了幾天」，就變成 time-bomb 了。

---

### 三、🔴 刻意不存在的欄位（本 ADR 最重要的一節）

以下欄位**永遠不得出現在憑證裡**。它們不是「還沒做」，是**被禁止**：

| 禁止欄位 | 為什麼禁止 |
| :-- | :-- |
| `exp` / `nbf` | 有效期進了憑證，App 就有能力（也遲早會）據此鎖功能。直接違反 §六 兩條公開承諾 |
| `updatesUntil` | `PRD_Entitlement_Licensing` §6.1 有這個欄位，並註明「僅資訊欄位」。**「僅資訊」是撐不住的**——一個看得到的日期加上一次「順手做一下」的 code review，就會變成一行 `if`。更新權屬於官網下載閘門，App 不需要知道它存在 |
| `maxVersion` | 同上。大版本升級費若日後要做，做法是**發一個新的產品線 build**，不是讓舊 binary 拒絕舊憑證 |
| `machineId` | 綁機器需要啟用流程與換機客服，換到的是抓不到的東西（B1） |

> **驗證端的對應要求**：若未來憑證出現未知欄位，App **一律忽略**（前向相容）。
> 但 `exp` / `nbf` 這幾個名字**不得被實作讀取**——連讀出來記 log 都不行。
> 它們不存在，所以也不會有人「剛好看到」。

---

### 四、驗證契約（App，main process）

- **決策**：驗證步驟固定為以下順序，任何一步失敗即 **`Free`**：

  ```
  1. 從 SQLCipher settings 讀出憑證字串；沒有 ⇒ Free
  2. 切成三段；段數不對 ⇒ Free
  3. 解 header：
       alg 必須【逐字等於】"EdDSA"        ⇒ 否則 Free
       🔴 alg 只用來【比對】，永遠不用來【選擇】驗章演算法
       kid 必須命中內建公鑰表              ⇒ 否則 Free
  4. Ed25519 驗簽 base64url(header) + "." + base64url(payload)
                                          ⇒ 失敗 Free
  5. 解 payload：v === 1、iss === "promptbox.app"、plan ∈ 已知集合
                                          ⇒ 否則 Free
  6. 通過 ⇒ Pro（解除全部配額；plan 僅供顯示）

  ※ 全程【不讀取任何日期】，也不做任何網路請求
  ```

- **步驟 3 的兩條紅線**都是 JWT 生態的經典破法：

  - **alg confusion**：實作若用 `alg` 去*挑選*驗章函式，攻擊者送 `alg: "none"`
    或 `alg: "HS256"`（拿公鑰當 HMAC 金鑰）就能自簽。本專案只有一種演算法，
    因此 `alg` 只是一個必須符合的常數，不是一個開關。
  - **kid 路徑穿越**：`kid` 只能查**編譯進 binary 的固定表**，
    永不用來組檔案路徑或查詢外部資源。

- **失敗一律 fail-safe 退回 Free**（App repo ADR-002 §1）：
  不當機、不 fail-open、不靜默、**不刪除或隱藏任何既有資料**。
  超額使用者的卡片完整保留（與 v3.4.0 配額只擋新增的既有行為一致）。

- **驗證只在 main process**（App repo ADR-005 §七、v3.4.0 五個攔截點）：
  renderer 僅顯示「已啟用 Pro（授權給 xxx@example.com）」。
  renderer 的 store 永不可信，不得作為能力判定。

### 五、金鑰輪替：公鑰是一張**表**，不是一把金鑰

- **決策**：binary 內建 `{ kid → publicKey }` 對照表。簽發端一律用**最新的 kid**簽。

  ```js
  const PUBLIC_KEYS = {
    PB2026A: '...',   // 2026-08 起使用
    // 之後新增的 kid 往下加；【舊的永遠不刪】
  }
  ```

- **🔴 舊 kid 永不移除**：移除一個 kid ＝ **一次撤銷所有用它簽過的憑證**。
  而憑證是不可撤銷的（B2），也就是說移除舊 kid 會讓一批**付過錢的使用者**在
  某次更新後突然變回 Free —— 這是本設計裡最容易造成災難的一個動作。
  金鑰洩漏時的正解是「發新 kid + 停用舊 kid **簽發**」，不是停用舊 kid **驗證**。

- 私鑰保管見 D21（Vercel 環境變數，僅 Production，另配測試金鑰給 Preview）。
  變數名帶 kid（`LICENSE_SK_PB2026A`），輪替時新增變數而非覆寫。

### 六、儲存與雙 build 的互動

- **儲存**（D24）：SQLCipher 加密 DB 的 `settings` 表，鍵 `license.entitlement`，
  值就是 compact JWS 字串本身。

  - **不用 OS Keychain**：Keychain 是給「洩漏就完蛋」的秘密用的（例如 DB 金鑰）。
    憑證**不是秘密**——它是一份帶簽章、防竄改的公開聲明。
  - **不用獨立明文檔**：會產生第二個真相來源，而且使用者會去手改。
  - **前例**：v3.7.0 把變數替換開關從 `localStorage` 搬進 `settings`，
    理由是 MCP 跑在 main process、讀不到 renderer 的 localStorage。**完全相同的論證**。

- **🔴 NQ1（跨 repo 前置）**：兩個 build 必須共用同一組 `appId` / `productName`。
  `ADR-000 B5` 的五行護欄測試釘的就是這個，README 明載它擋的正是
  「做雙 build 時產物要能區分」這個很合理的動機 —— 它會**讓既有使用者的資料變孤兒**。

  護欄**不必拆，要改寫語意**：從「只有一個 build」改成「**所有 build 共用同一組 identity**」。
  這樣 Free 使用者買了 Pro、下載 Pro build 直接覆蓋安裝，**資料原地保留**，
  憑證也還在 `settings` 表裡。**此項必須在階段五之前完成。**

- **NQ2：Pro build 拿不到有效憑證時**
  ⇒ **降級為 Free 行為並明示原因**。不 crash、不 fail-open、不靜默。
  Pro 的安裝檔一旦流出就會被分享，這是預期中的情況，不是異常。

- **NQ3：Free build 持續發佈新版** ⇒ **是**。
  Pro 是獨立 build，Free 持續更新不會洩漏 Pro —— 這正是雙 build 的好處。

## 後果

### 好的

- 更新權從「結構上不可執行」變成**真的可執行**（舊 B2 消滅），且 App runtime 完全不必知道任何日期。
- 驗證是**純函式**：輸入一個字串與一張公鑰表，輸出 Pro / Free。可完全單元測試，無 I/O、無時鐘、無網路。
- 憑證沒有時間性，因此**永遠不會因為系統時間被調整而行為改變** —— 訂閱制最怕的那個攻擊在這裡不存在。

### 要付的代價（有意識的取捨，非未竟工作）

比照 `ADR-000 C2` 的體例：

| # | 邊界 |
| :-- | :-- |
| **B1** | 憑證檔可被複製到多台裝置或分享給他人 —— **技術上抓不到** |
| **B2** | 已簽發的憑證**無法撤銷**，退款後仍然有效 |
| **B3** | 綁 email 只是**社交嚇阻**，不是技術管制 |

這三條與「App 不連網」是同一件事的一體兩面。
**不應為了消除它們而犧牲 A5** —— 那是拿核心賣點去換一個本來就抓不到的東西。

B2 的實務緩解不是技術性的：退款時**同時撤銷更新權**（官網側，可執行），
使用者保有當下版本 —— 這與「不續訂」的結果完全一致，也正是我們公開承諾的行為。

## 八、唯一的未決項

**Q12：憑證交付給使用者的外觀。**

格式（compact JWS 字串）已由本 ADR 定死，未決的只有「使用者拿到的是什麼」：

| 選項 | 說明 |
| :-- | :-- |
| **A. 純字串複製貼上（建議）** | 下載頁直接顯示可複製的字串，App 設定頁貼上。**沒有檔案就沒有副檔名問題**，也沒有「檔案存到哪去了」的客服 |
| B. `.promptbox-license` 檔 | 明確歸屬，但要處理雙擊開啟的檔案關聯與作業系統差異 |
| C. `.license` 檔 | 泛用副檔名，容易與其他軟體打架 |

建議 A：憑證是一份**聲明**，不是資產。它的自然形態是文字，
而且 D17 已定「Pro 下載連結與授權碼放在同一頁」—— 使用者本來就會在那一頁複製它。

> **發出去就改不了**，因此在階段五實作前需要你拍板。
> 選 A 的話，本 ADR 不需要任何修改。
