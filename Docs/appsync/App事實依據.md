## 二、🔴 誠實紅線：管的是官網「可以寫什麼」

這兩條與上面六條性質不同——**上面六條是「App 做了什麼」，這兩條是「官網被允許怎麼說」**。
它們是 [主張與依據](../webspec/主張與依據.md) 這份文件存在的上位原因。

### C1　不得在任何介面或文案暗示超出實際的保護

例：不得暗示機密卡片「解鎖後所有欄位皆受保護」、不得說「Pro 讓你的資料受加密保護」（加密在 Free 就是完整的，說成 Pro 特性等於兩頭都不誠實）。

### C2　已知邊界必須明列，不得模糊

**目前五條**（2026-09-06 更新：第 1 條範圍收窄、新增第 5 條）：

1. ~~機密卡片的~~ **一般卡片（沒有設密碼的）的變數預設值是明文**<br>🔴 **2026-09-05（App v3.8.0）範圍收窄**：機密卡的變數名稱與預設值、型別定義已一併加密（FR-2／FR-3）。這是本專案少數真的把邊界**拿掉**、而不是「更誠實地標示它」的一次。<br>⚠️ **但對一般卡它是永久邊界，不是待辦** —— 沒有密碼就沒有金鑰。官網講的時候必須照實說，不得用「還沒做」帶過。
2. `safeStorage` 不可用時**退回明文開庫**
3. **離線 ⊥ 防破解**（見 B6）
4. **main 無法保證 renderer 的明文被抹掉** —— 人類側解鎖的明文活在 renderer，main 只能「請求」它清理；對照 AI 側授權窗完全由 main 持有、wipe 是確定的。**兩側保證強度不同，文案不得混為一談**
5. **解鎖後切換視窗不再上鎖** —— blur 自 App v3.8.0（FR-8／ADR-009）起不再是機密解鎖態的失效條件，⇒ 解鎖後切到別的視窗，**明文會留在記憶體與被遮住的螢幕上最長 10 分鐘**（idle 逾時）。仍然有效的失效條件：idle（10 分鐘）／鎖屏／睡眠／手動撤銷。<br>📌 App 側自己記帳為「相對 v3.6.0～v3.7.2 是**真實的防護下降**」，理由是 blur 三次被證明是錯的代理指標（v3.6.0 殺死 AI 授權窗、FR-1 清空一般卡填值、FR-4 清空進行中的存檔流程），前兩次都是開例外——三個例外會住在三個檔案，屆時沒有人能一眼說出 blur 到底會清什麼，而**說不清楚的規則無法對使用者誠實陳述**。<br>⇒ 官網不得只講「閒置自動鎖」而略過這一條。

> **為什麼誠實是紅線而不是美德**（App repo ADR-000 §3.3 原文的理由）：
> 產品的獲客放棄了利益誘因型裂變，改押在「**可驗證性**」上降低推薦者的背書成本。
> **在文案上說謊會直接砸掉這個機制**，而它是這個產品唯一的推薦背書路徑。
>
> 官網這一端的具體後果：下載頁 `notes.n4` 主動承認「Windows 會顯示無法辨識的應用程式」、
> mac 卡片顯示「即將推出」而不給假的下載鈕、GA4 未設定時隱私頁誠實說「本站目前未設定任何分析工具」
> —— 這些都不是文案風格選擇，是 C2 的執行。

## 三、B5 護欄測試：2026-09-02 實測結果（v3.7.2 出貨後改寫，W5 結案）

> ✅ **W5 已完成 2026-09-06。** 原本這一節寫「護欄只釘住兩個身分字串」，並標明它會在
> App v3.7.2 出貨後過期、在那之前**不要提早改**（提早改等於提前說謊，誠實紅線 C2）。
> **v3.7.2 已於 2026-09-02 出貨**，觸發條件成就，本節依實況改寫。
> 📌 **舊結論保留在下方對照表**，因為官網那句「升級覆蓋安裝、資料原地保留」的**依據強度變了**，
> 下一個人要看得到它從哪裡變到哪裡。

App v3.7.2 新增 `electron/identity.cjs`，把十個身分字串收斂成單一真相
（appId / userData 兩層目錄 / `app.setName` 值 / DB 與備份檔名 / keystore 檔名 /
MCP server name 與 URI scheme / NSIS GUID）。護欄同步從 **5 條擴充到 19 條**，
每條失敗訊息都寫出後果與出處。

| 項目 | v3.7.1（舊結論） | v3.7.2（現況） |
| --- | --- | --- |
| 護欄條數 | 5 | **19** |
| `build.appId` | `com.promptbox.app` | **`com.eychen.vault`** |
| userData 路徑 | 由 `productName` 推導（**該前提本身是錯的**，見 §一 B5） | **`app.setPath` 寫死為 `{appData}/EYChen/Vault`** |
| DB 檔名 | `promptbox.db` | **`vault.db`** |
| v2 明文備份 | `promptbox.db.plain.bak` | **`vault.db.plain.bak`** |
| MCP server name / URI scheme | `PromptBox` / — | **`vault` / `vault://`** |
| 金鑰庫檔名 | `keystore.bin` | `keystore.bin`（**刻意不改，已中性**） |
| NSIS `guid` | 由 `appId` 推導 | **明設 `bf70f23a-…`**（等於 electron-builder 今天會推導出的值，對產物零行為變更） |
| userData 路徑有護欄嗎 | ❌ 沒有斷言 | ✅ 有（含「`getPath('appData')` 只准在 `main.cjs`」與讀取點清單） |
| 金鑰庫識別有護欄嗎 | ❌ 沒有斷言 | ✅ 有 |

🔬 **突變測試抓到一個真漏洞**：第 4 條護欄原本掃原始碼字串，把 `app.setPath` 那一行
**註解掉它依然是綠的** —— 一條抓不到「功能被關掉」的護欄，比沒有護欄更危險。修法是先剝註解。

✅ **實機覆蓋安裝驗收通過**：改頂層 `name`（`promptbox` → `renamed-app`）重新建置並覆蓋安裝，
沒有出現 `%APPDATA%\renamed-app\`，`vault.db` 與 `keystore.bin` 雜湊逐位元未動，
機密卡以原密碼解開，程式集只有一個。**在 v3.7.2 之前，這一格必然失敗。**

**對官網的意義**：下載頁「升級覆蓋安裝、資料原地保留」這句話，
**依據強度已從「只有一半有護欄」變成「六項身分字串全部有斷言 + 一次實機覆蓋安裝驗收」**。
⚠️ **但 macOS 仍未驗**（無 build）：`app.setName` 對 Keychain 的保護要等第一個 mac build 才驗得到，
在那之前**不得宣稱已驗過**。下載頁的 mac 卡片維持「即將推出」正是這一條的執行。
