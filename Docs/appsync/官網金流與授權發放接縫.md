## 2. 本文件回答的一個問題

**如何在「App 永不連網、憑證不可撤銷、私鑰只有一把」這三個約束下，
建立一條能自動把付款轉成合法憑證、而且出錯時人救得回來的發放流程？**

「出錯時人救得回來」是重點。憑證不可撤銷（B2）、私鑰遺失就再也簽不出新的（D21），
這條流程的**每一個失敗模式都是不可逆的**，因此設計重心在冪等與可重放，不在吞吐量。

## 3. 兩層分離：本文件的骨架

D14 把「你買了什麼」拆成兩件**必須存在不同地方**的東西：

| | Pro 資格 | 更新權 |
|---|---|---|
| **是什麼** | 你有沒有 Pro | 你能不能下載**之後**發布的版本 |
| **載體** | entitlement（JWS 字串） | 官網帳號上的一個到期日 |
| **有效期** | **永久** | 有期限，可續訂 |
| **執行點** | App main process，離線 | **官網的 Pro 下載連結**（D18） |
| **可撤銷嗎** | ❌ 不行（B2） | ✅ 可以（改資料庫一個欄位） |

> 🔴 **這兩者永不合併。** 更新權的日期一旦進了憑證，App 就有能力據此鎖功能，
> 直接違反 §六 兩條公開承諾。見 [ADR-008 §三](ADR-008_授權憑證格式與離線驗證契約.md)。

退款的處理也落在這條線上：**撤更新權，不撤憑證**。
結果與「不續訂」完全一致 —— 保有當下版本、拿不到新版 —— 這正是我們公開講過的行為。

## 4. 端到端流程

```
┌────────┐   ①下單    ┌───────┐  ②webhook  ┌──────────────────┐
│ 使用者 │ ─────────▶ │ Polar │ ─────────▶ │ 官網 /api/polar/  │
└────────┘            │ (MoR) │            │      webhook      │
     ▲                └───────┘            └────────┬─────────┘
     │                                              │
     │                              ③驗簽 → 冪等檢查 → 用 Ed25519 私鑰簽
     │                                              │
     │                                              ▼
     │                                   ┌──────────────────────┐
     │      ⑤登入後在同一頁看到          │ Supabase              │
     ├───────────────────────────────────│ entitlements_issued  │
     │      憑證字串 + Pro 下載連結       │ update_rights        │
     │                                   └──────────┬───────────┘
     │                                              │
     │            ④Buttondown 寄出「你的授權」信     │
     └──────────────────────────────────────────────┘
```

### ① 商品設定（Polar）

四個商品，對應官網 §六 已公開的數字：

| 商品 | 價格 | 類型 | 簽出的 `plan` |
|---|---|---|---|
| 個人版 Pro（早鳥） | $19 / 年 | 訂閱（更新權續訂） | `pro` |
| 個人版 Pro（標準） | $39 首購 + $27 / 年 | 訂閱 | `pro` |
| 永久更新權 | $109 一次 | 一次性 | `lifetime` |
| 商業授權 | $69 / 席 / 年 | 訂閱，數量 1..N | `commercial` |

**Polar 選型理由**（D9）：Merchant of Record —— 它是法律上的賣方，
代收代繳全球 VAT。對台灣的個人開發者，這省掉的是各國稅務登記，不是手續費。

**🔴 Polar 的 license key 功能不使用**（D10）：它的 `validate` / `activate` API
**永不由 App 呼叫**。Polar 給的 key 只是購買憑證，我們用它來**觸發自己的簽發**，
而不是讓 App 打電話回家。這條線一旦開了，「不連網」就不成立了。

**早鳥名額（D25）**：目前不收錢，只收 email。首批 150 名以**訂閱時間戳**為準 ——
時間戳的來源就是階段三已上線的 `/api/subscribe`（`early-bird` tag）。
金流開通時，以該名單為準發送早鳥購買連結。

### ② → ③ Webhook → 簽發

```
POST /api/polar/webhook
```

處理順序（**順序本身就是設計**）：

```
1. 驗 webhook 簽章               ⇒ 失敗回 401，不做任何事
2. 只處理已知事件類型             ⇒ 其餘回 200 忽略（別讓未知事件卡住重試佇列）
3. 以 event id 查冪等表           ⇒ 命中則【回 200 且不重簽】
4. 取出 buyer email → 小寫正規化
5. 商業授權：依 seat 數展開（D23，買 4 送 1 ⇒ 簽 5 份，各綁各自 email）
6. 用 LICENSE_SK_<kid> 簽出 compact JWS（ADR-008 §一、§二）
7. 寫入 entitlements_issued（含 jti / order / kid，供客服與重發）
8. 寫入／延長 update_rights
9. 觸發寄信（Buttondown transactional）
10. 回 200
```

**🔴 步驟 1 不可跳過。** 沒有驗簽的 webhook 端點 ＝ 一個**公開的、無認證的簽發器**：
任何人只要 POST 一段 JSON 就能拿到合法的永久授權。這是整條流程最大的單點風險。

> Polar 走 Standard Webhooks 規範（HMAC + timestamp）。
> **實作時必須對照 Polar 當下的文件確認標頭名稱與簽章基底字串**，
> 不要照抄本文件的敘述 —— 這是會隨版本變動的細節，而寫錯的後果是驗簽形同虛設。
> 一併檢查 timestamp 容忍窗（擋重放）與**常數時間比較**（擋計時側通道）。

**步驟 3 的冪等**同樣不可省：webhook 會重送（網路逾時、我方 500、平台重試）。
沒有冪等表的話，一次重送就是**多簽一份永久有效、無法撤銷的憑證**。
冪等鍵用 Polar 的 event id，不是 order id —— 同一筆訂單會有多個事件。

### ④ 交付

兩條路，**都要有**：

- **email**（Buttondown transactional）：憑證字串 + 下載頁連結。
  這是唯一會主動觸及使用者的管道。
- **官網帳號頁**（D16 / D17）：登入後，**Pro 下載連結與授權碼在同一頁**。
  信件遺失、進垃圾桶、換信箱都靠這裡救 —— email 是通知，不是唯一副本。

### ⑤ 下載閘門（D16 / D18）

- **所有下載一律需登入官網帳號**（含 Free）—— Supabase Auth 的 Google OAuth（D7）。
- **Pro build 的下載連結由 `update_rights` 把關**：到期且未續訂 ⇒ 拿不到新版，
  已下載的版本不受影響。這是更新權**唯一**的執行點。
- Free build 持續發佈新版（NQ3）。Pro 是獨立 build，Free 更新不會洩漏 Pro。

## 5. 資料模型（Supabase，官網階段六）

```sql
-- 簽出去的每一份憑證。🔴 只增不改：這是「我簽過什麼」的帳本
create table entitlements_issued (
  jti          uuid primary key,
  email        text not null,          -- 小寫正規化後
  plan         text not null,          -- pro | lifetime | commercial
  seat         int  not null default 1,
  kid          text not null,          -- 用哪把私鑰簽的（輪替後才知道怎麼查）
  order_ref    text not null,          -- Polar 訂單，供客服溯源
  jws          text not null,          -- 憑證字串本身，供重發
  issued_at    timestamptz not null default now()
);

-- 更新權。這張表【可以改】，退款與續訂都改這裡
create table update_rights (
  email        text primary key,
  until        timestamptz,            -- null = 永久（lifetime）
  source       text not null,          -- 最後一次變更的來源訂單
  updated_at   timestamptz not null default now()
);

-- webhook 冪等
create table webhook_events (
  event_id     text primary key,
  received_at  timestamptz not null default now()
);
```

**為什麼把 `jws` 整份存下來**：使用者信件遺失時要能**原樣重發**。
重簽會產生新的 `jti`，帳本上就多一份「不知道為什麼存在」的憑證 ——
而憑證不可撤銷，帳本對不上就永遠對不上了。

**為什麼 `update_rights` 以 email 為主鍵而非 user_id**：憑證綁 email（D12），
下載閘門必須跟它同一個維度，否則會出現「憑證是 A 信箱、更新權掛在 B 帳號」的錯位。

## 6. 私鑰保管（D21）

| | 決策 |
|---|---|
| 放哪 | **Vercel 環境變數**，base64 PKCS#8，變數名帶 kid（`LICENSE_SK_PB2026A`） |
| 🔴 環境 | **僅 Production**，標記 Sensitive。Preview / Development 另配**測試金鑰** |
| 備份 | 密碼管理器離線備份，**必須做** |
| 為什麼不用 KMS | 一把 Ed25519 金鑰、每天簽個位數次。KMS 帶來延遲、費用與第四個廠商，換到的安全性提升在這個威脅模型下接近零 |

**Preview 那條是硬要求，不是建議**：Vercel 的 preview 部署預設**任何人拿到網址就能存取**。
真金鑰若跟著上 preview，等於公開一個無認證的簽發端點 —— 與 §4 步驟 1 沒驗簽是同一級的災難。

**私鑰遺失不會讓已發出的憑證失效**（App 用公鑰驗，公鑰在 binary 裡），
但你將**再也簽不出新的**。輪替規則見 [ADR-008 §五](ADR-008_授權憑證格式與離線驗證契約.md)：
公鑰是一張**只增不刪**的表。

## 7. 失敗模式與人工救援

不可逆的流程要先寫好怎麼救。

| 失敗 | 症狀 | 處置 |
|---|---|---|
| Webhook 簽章驗證失敗 | 401，Polar 端顯示送達失敗 | **先查是不是我方 secret 設錯**，不要為了「先讓它動」而放寬驗證 |
| 簽發成功但寄信失敗 | 帳本有、使用者沒收到 | 帳號頁本來就看得到（D17）。另可從 `entitlements_issued` 原樣重發 |
| 使用者提供的 email 打錯 | 憑證簽在錯的信箱上 | 🔴 **不可撤銷**。只能對正確信箱補簽一份，並在帳本標註。**這是為什麼結帳頁的 email 必須要求二次確認** |
| Webhook 重送 | 潛在重複簽發 | §4 步驟 3 的冪等表；上線前必須以重放測試驗證 |
| Polar 停用 / 換金流 | 新訂單進不來 | 憑證格式與金流**無耦合**（ADR-008），換平台只需改 webhook 端點。已簽出的憑證完全不受影響 |
| 私鑰洩漏 | 有人能自簽永久授權 | 發新 kid、停用舊 kid **簽發**；🔴 **絕不停用舊 kid 的驗證**（會一次撤銷所有付費使用者） |

**沒有「人工簽發」路徑**（D13）：商業授權也走同一條自動流程。
開一個人工後門等於開一個沒有稽核、沒有冪等、只有一個人記得怎麼用的第二條簽發路徑。

## 8. 明確排除

- ❌ **App 呼叫任何金流 API**（D10）—— 包含 Polar 的 `validate` / `activate`。這條線一開，「不連網」就沒了
- ❌ **憑證撤銷機制** —— 需要 App 連網查黑名單，與 A5 直接衝突。退款走更新權（§3）
- ❌ **人工簽發後門**（D13）
- ❌ **把更新權日期寫進憑證**（D14 / ADR-008 §三）
- ❌ **自建金流／自行處理 VAT** —— 選 Polar 的全部理由

## 10. 成功條件

- 一筆真實付款 → 憑證自動簽出 → 使用者在 App 內離線啟用成功，**全程無人工介入**
- webhook 重放 10 次 → `entitlements_issued` 仍只有 1 筆
- 更新權到期 → 下載頁拿不到新版；**同一台機器上已安裝的版本行為完全不變**（§六 承諾的逐條驗證）
- 商業授權買 4 席 → 自動簽出 5 份，各綁各自 email（D23）
