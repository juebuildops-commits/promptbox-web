## 二、回答 §五 的六個問題

### Q2　v3.7.2 出貨時點 —— 給你一個**條件**，比日期更耐用

**現況**：`Doc/PRD/v3.7.2_PRD_IdentityFreeze.md` 狀態為「已採用／**未動工**」，8 個 FR，
其中 FR-8（實機覆蓋安裝驗收）是 §7 明訂的**硬性出貨 gate**。排期不是我能替創辦人決定的。

**但出貨順序不是排程問題，是被 PRD §1 決定的**：

> 發出比賽用 Free build 的那一刻，本版定下的每個值都永久定案。

⇒ **v3.7.2 必然是第一個對外 build 之前的最後一版。** 順序是強制的，不是偏好。

**因此建議**：把 W1／W2／G6-B 類的觸發條件從「v3.7.2 出貨」改寫為
**「App 發出第一個對外 Free build 時」**。

兩個好處：① 這個事件**官網自己看得到**（下載頁要掛檔案），不必再回來問；
② 它比版本號耐用 —— 萬一身分字串凍結被拆成 v3.7.2 + v3.7.3 兩版，「出貨」就失去唯一指涉，
而「第一個對外 build」不會。

⚠️ **唯一不適用這個條件的是 W5**。它的正確觸發是 **FR-7 進 main 的那一刻**
（護欄從 5 條擴充到 12 條以上，[App 事實依據](App事實依據.md) §三「只釘住兩個」當場失效），
這**可能早於發 build 數天**。

### Q3　產品名 —— 我不拍板，但要更正一件事實

官網 §3.1 把產品名畫成四條線的共同根。**App 這一端要更正：v3.7.2 出貨之後，App 沒有任何東西在等產品名。**

依據：v3.7.2 PRD §5 Out of Scope 第 1 項把 A 類改名整個排除在本版之外；
§9 明寫「本版做完之後，改名才是安全的 —— 順序不可顛倒」。

所以那張圖的四條線裡：**三條是官網的**（階段五六、P6→P7、A 類品牌字串替換），
**第四條是 ADR-008 的 `iss`**（見 Q5）。**App 的雙 build 不在其中。**

這可能改變排序：如果產品名唯一擋的是官網那三條，那它與 v3.7.2 **可以並行**，不必互等。

### Q4　NSIS `guid` —— 你的拆解正確，結論更強，而且值我算好了

官網 §2.2 的拆解成立：明設之後 `guid` 與 `appId` 脫鉤。
**但「脫鉤」是目的，不是副作用。** v3.7.2 PRD FR-6 的理由比 [App 側回覆](App側回覆.md) §1.3 完整：

> 兩個 codebase 各自 pin 不同 electron-builder 版本，只要推導方式在某個版本變了，
> GUID 就會**悄悄漂開**，然後 Pro 裝成第二份，而 `appId` 護欄全綠。

**`productName` 自由的正確理由**（請換掉 §1.3 那句）：
NSIS 的解除安裝登錄機碼是 `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\{guid}`，
升級時安裝位置從登錄檔讀回；`productName` 只決定**預設**安裝目錄與捷徑顯示名，**不參與升級判定**。
結論不變，明設之後反而更硬。

**「凍結表要多一列」——App repo 這邊已經有了**：`ADR-000 B5` 原文已含 NSIS `guid`，
v3.7.2 PRD 的 FR-6 與 FR-7 斷言 #11 也都在。**缺的只有值。**

**建議值**（我用專案內的 `builder-util-runtime` 實算，namespace 取自
`node_modules/app-builder-lib/out/targets/nsis/NsisTarget.js:26` 的 `50e065bc-3134-11e6-9bab-38c9862bdaf3`）：

| appId | electron-builder 會推導出的 GUID |
| --- | --- |
| `com.promptbox.app`（現值） | `d4c79fdf-9079-521a-bfd2-6a23af6fb5f7` |
| **`com.eychen.vault`（凍結值）** | **`bf70f23a-47a4-5ea7-955e-033630ff9234`** |

**建議直接把下面那個當明設值。** 好處是**明設這個動作對行為零影響**
（electron-builder 本來就會算出這個），純粹把工具的實作細節鎖成一個字面值 ——
完全是 FR-6 的原意，而且**不引入第四個「憑空選的」身分字串**。

### Q6　強型別 —— 你是對的，**W3 撤銷**，而且 App 側的錯比你指出的更深一層

你對 `limits.cjs` 的糾正成立。補一個更根本的理由：
該檔的常數叫 **`FREE_LIMITS` / `FREE_FEATURES`**，`getTier()` **硬回 `'free'`** ——
**這個檔案裡根本沒有 Pro 那一半**。從它推不出任何關於 Pro 的結論。
所以 W3 不只是「結論反了」，是**型別上的誤讀**：拿一個只描述 Free build 的模組去推論 Pro 的權益。

而且 **W3 是拿 App 的程式碼去推翻 App 自己的 BRD** —— `BRD-03` §2.6 ② 就寫在同一個 repo 裡。

**實作面查核（給你當依據）：停用已經做完，不是只寫在 BRD 裡**：

```

electron/mcpServer.cjs:390,404                 getEffectiveSchema 的強型別分支已吃 feature flag
```

最後一處正是 `BRD-03` §2.6 ② 註記「🔴 v3.7.0 起**再加一處**」要求的那一處，已落實。

🔴 **但 App 側有一句話要修**：`electron/platform/limits.cjs:67-69` 的註解寫
「**Free 的** `strongTyping` 是硬性 false」—— 語氣仍暗示「Pro 才有」。
**這句話正是 W3 誤讀的來源。** 它是註解不是行為，但下一個人還會再讀一次。已列入 §五。

**結論**：定價頁**不列**強型別是對的，**不要加**。W3 撤銷。

### A2 為什麼要提前（官網 §3.2 沒看到的一階）

v3.7.2 的 **FR-7 會把 `APP_NAME` 釘進護欄斷言**，而 `electron/__tests__/data-continuity.test.js`
第 3 行寫著「🔴 這條紅了不要改測試」；PRD FR-7 特別註明**本版是唯一一次被允許的換值**。

把 `app.setName()` 留到 mac build 再決定，**等於刻意再開一次那扇門**。

建議值 **`EYChen Vault`**：它與 `%APPDATA%\EYChen\Vault` 一致，
把凍結清單 §B 承認的「外觀不一致」取捨**補回一半**；
而單獨一個 `Vault` 在鑰匙圈對話框裡會跟 HashiCorp Vault、1Password 的 vault 概念糊在一起 ——
這是**唯一會出現在使用者眼前的身分字串**，模糊的成本比目錄名高。

### A7 為什麼可以從 🔴 降級

`package.json` 的 `build.publish` 現值是 provider `github` / owner `tsa206531` / repo `PromptBox`。
但 **v3.3.0 移除自動更新之後，它只剩「發版時把檔案傳到哪」，App runtime 一行都不讀**
（`no-outbound.test.js` 七條護欄擋著任何回加）。

所以它和「官網下載頁指到哪」是**可以分開決定的兩件事**：
`publish` 繼續傳 GitHub Release，官網從 Cloudflare R2 供檔，中間搬一次即可。

**原題目真正剩下的是「Pro build 放哪」** —— 那一個不能躺在公開 Release，
因為它要過 `update_rights` 閘門（金流接縫 §4 ⑤）。建議 G5 就重寫成這一句，它就不再是無主項。
