### 1.4 由我提出、待你否決的三項

以下三項是你授權我決定的，理由一併記錄，隨時可推翻。

#### D21　私鑰放 Vercel 環境變數

因為 D22 選了自動簽發，私鑰**必須在簽發程式跑得到的地方**，這就排除了「只放密碼管理器」。

- **不用 KMS**：一把 Ed25519 金鑰、每天簽個位數次，KMS 帶來的是延遲、費用與第四個廠商，換到的安全性提升在這個威脅模型下接近零
- 🔴 **只設在 Production 環境**，Preview / Development 另配一把**測試金鑰**。Vercel 的 preview 部署預設是**任何人拿到網址就能存取**——真金鑰若跟著上 preview，等於公開一個無認證的簽發端點
- 私鑰以 base64 PKCS#8 存放，變數名帶 `kid`（例如 `LICENSE_SK_PB2026A`），讓 §D 的金鑰輪替有位置可放
- **必須離線備份**：私鑰遺失不會讓已發出的憑證失效，但你將**再也簽不出新的**

#### D24　憑證存 SQLCipher 的 `settings` 表

- **已有前例**：v3.7.0 把「變數替換」開關從 `localStorage` 搬進 `settings` 表，理由是 **MCP 跑在 main process，讀不到 renderer 的 localStorage**。配額強制同樣在 main process（v3.4.0 五個攔截點），**完全相同的論證**
- **不用 OS Keychain**：Keychain 是給「洩漏就完蛋」的秘密用的（例如 DB 金鑰）。**授權憑證不是秘密**——它是一份帶簽章、防竄改的公開聲明。放 Keychain 會換來尺寸限制與平台專屬的失敗模式，零收益
- **不用獨立明文檔**：會產生第二個真相來源，而且使用者會去手改（改了會驗證失敗，無害，但製造客服雜訊）
- 存的是 compact JWS 字串本身，原始檔案不必保留
- 驗簽**只在 main process 做**，renderer 僅顯示「已啟用 Pro（授權給 xxx@example.com）」

#### D29　寄信服務選 Buttondown

- **可以完全關閉開信追蹤像素**。對一個核心賣點是「我們不追蹤你」的產品，能說出「連我們的電子報都不追蹤開信」是**一致且便宜的加分**
- API 直白、支援 Markdown、標籤（tag）模型剛好對應「更新通知 / Pro 早鳥」兩種名單
- 成本：100 位訂閱者以內免費，之後約 $9/月
- **替代方案 Kit(ConvertKit)**：免費到 1 萬訂閱者，成本上完勝，但**預設帶開信追蹤像素**，與品牌語氣有摩擦。若你認為成本優先於這個姿態，換過去也完全合理

> 🔴 **2026-08-30 更正：上面兩點擺在一起會誤導，實測後才發現。**
>
> **tag 從第 0 位訂閱者就要 Basic 方案**，不是「超過 100 人才要付費」。
> 免費方案帶 tags 送出會回 `403 feature_disabled`：
> `"Tags require a Basic plan or higher - please upgrade your account."`
>
> 也就是說 **選 Buttondown 的理由之一（tag 模型）在免費方案根本用不到**。
> 這不足以推翻 D29 —— 關閉開信追蹤才是決定性理由，那一項免費方案有 ——
> 但成本那一行原本的寫法會讓人以為免費方案功能完整，實際上不是。
>
> **已處理，不需付費**：`subscribe.post.ts` 撞到 403 會自動拿掉 tags 重送，
> 分群改由 `metadata.kind` 承擔（**免費方案可用，已實測**）。
> 升級 Basic 之後 tags 會自己恢復，程式一行都不用改。

## 二、雙 build 帶來的連動（新增，需處理）

D15 定案為兩個獨立 build 之後，有三件事變了：

### ✅ 更新權變成真的可執行

原先「單一 binary ⇒ 更新權結構上不可執行」的邊界（舊 B2）**已消滅**。Free 使用者拿不到 Pro build，過期的 Pro 使用者也下載不到新的 Pro build。這是雙 build 最大的收益。

### NQ1　`appId` / `productName` 必須在兩個 build 之間保持相同

> 🔴 **2026-08-28 校正：本節的前提需要修正，範圍比原本記錄的小。**
>
> 下方寫著「這條護欄不必拆，但要**改寫語意**」。但把 ADR-000 摘錄補進 repo 之後對照正本，
> **B5 已經是雙 build 的寫法了** —— 原文字面就是「不同 build（Free / Paid）**共用同一組
> `appId` + `productName`**；升級或降級絕不鎖死既有本地資料」。
>
> 也就是說**原則層面不需要改寫**，剩下的只有「確認那條五行護欄測試的斷言與失敗訊息是否也已更新」。
> 見 [ADR-000 技術紅線摘錄](../appsync/App事實依據.md) B5 段。
>
> 這正是「複製了葉子、把索引留在 App repo」造成的問題：官網的待辦是照著一份**過期的 B5 理解**排的。

App repo 的 `ADR-000 B5` 有一條**五行護欄測試釘住 `appId` 與 `productName`**，README 明載它擋的正是：

> 日後做雙 build 時「產物要能區分」這個很合理的動機——它會直接**讓既有使用者的資料變孤兒**

現在雙 build 真的要做了。**這條護欄不必拆，但要改寫語意**：從「只有一個 build」改成「**所有 build 共用同一組 `appId` / `productName`**」。

這樣 Free 使用者買了 Pro，下載 Pro build 直接覆蓋安裝，**資料原地保留**——與現行升級流程完全一致。

⚠️ 這是**跨 repo 的改動**，屬於 App repo，不在官網範圍內，但必須在階段五之前完成。

### NQ2　Pro build 拿不到有效 entitlement 時的行為？

Pro build 的安裝檔一旦流出就會被分享。**建議：降級為 Free 行為並明示原因**（fail-safe，與 ADR-008 的驗證規則一致），不 crash、不 fail-open、不靜默。

如此一來兩道鎖各司其職：

- **binary 閘門**管「什麼時候」（更新權，有期限）
- **entitlement** 管「誰」（永久，綁 email）

### NQ3　Free build 是否持續發佈新版？

推測為「是」（免費版該有更新）。因為 Pro 是獨立 build，Free 持續更新**不會洩漏 Pro**——這正是雙 build 的好處。需確認。

### ✅ Q15-b. 文案把「開源發布於 GitHub Releases」當事實在講（已解，2026-08-27）

首頁 FAQ、下載頁 hero 與安裝提示都寫著「安裝檔開源發布於 GitHub Releases，來源公開透明」。
D19 之後這是**對外的不實陳述** —— 壞連結只是點不到，這個是講了不成立的話。

⚠️ **階段三把行銷頁翻成英文之後，這句話現在也有英文版了**，曝險面從一種語言變成兩種。
zh-TW 與 en 各 3 處共 6 處，全部在語系檔裡，改一次即可：

- `home.faq.a3`、`download.hero.lead`、`download.notes.n1.body`

**做法：換證據，不是刪句子。** 那句話的工作是回答「我為什麼敢裝你的 exe」，
直接刪掉會讓下載頁的信任列塌掉一格。改成 **「官網直接發布 + 附 SHA-256 校驗碼」** ——
使用者真正要的保證（我拿到的＝你發的）原封不動，而且這次是真的。

### ✅ Q16. 安裝檔太大，放 `public/` 上不了線（已解，2026-08-28）

檔案已放進 `Src/public/dl/free/windows/`，本機 `npm run build` + preview 驗證通過（兩顆都 200）。
**但這條路走不到 Vercel**：

| 檔案 | 大小 |
| --- | --- |
| `PromptBox-Setup-3.7.1.exe` | **111 MB** |
| `promptbox.zip`（便攜版） | **153 MB** |

- **GitHub 硬擋 100 MiB 以上的單一檔案**（50 MiB 以上先警告）。兩顆都超過 ⇒
  **無法 push**，也就是 Vercel 的 Git 整合部署整條路直接不通（除非上 Git LFS）
- **Vercel CLI 部署**的來源檔上限是 **Hobby 100 MB / Pro 1 GB**。Hobby 連 `.exe` 那顆都放不下
- 另外兩件事：Hobby 方案**不允許商業用途**；全量下載一次 264 MB，
  流量會消耗得比想像中快

**選項**（需要你決定）：

| # | 做法 | 代價 |
| --- | --- | --- |
| A | 檔案改放物件儲存（Vercel Blob / Cloudflare R2 / S3），頁面連過去 | 多一個廠商；但這是**階段五閘門本來就要走的形狀**（簽 URL） |
| B | 升 Vercel Pro + 用 CLI 部署（1 GB 上限），檔案留在 `public/` | 要付費；流量仍算在 Vercel 帳上 |
| C | 只發便攜版或只發安裝版 | 少一顆，但**兩顆都超過 100 MB**，救不了 GitHub 那條路 |
| D | Git LFS | GitHub 免費額度只有 1 GB / 月流量，發幾次就爆 |

**裁決：A（Cloudflare R2）**，2026-08-28 完成。

```
https://pub-c877572083874aada08b285a742dce71.r2.dev/PromptBox-Setup-3.7.1.exe
https://pub-c877572083874aada08b285a742dce71.r2.dev/promptbox-v3.7.1.zip
```

- 安裝檔已移出 `Src/public/`，改放 repo 根的 `_artifacts/`（已 gitignore）。
  **建置產物從 294 MB 降到 30 MB**
- 已用 R2 的 **ETag（單段上傳 ⇒ 等於物件 MD5）**驗證線上檔案與本機建置產物**位元組相同**，
  因此頁面上公布的兩組 SHA-256 對使用者實際下載到的東西成立
- 新增 repo 根 `.gitignore`，明確擋掉 `*.exe` / `_artifacts/` / `Src/public/dl/` ——
  🔴 **它必須早於第一次 commit**：檔案一旦進 history，`git rm` 救不了

⚠️ **`pub-*.r2.dev` 是 Cloudflare 的公用開發網址**，官方不建議正式環境長期依賴。
網域到位後（前置鏈 P6）改綁自訂網域，一樣只動 `download.vue` 頂端那幾行。

##### 🔴 同日更正：原本的歸因是錯的

上面的修法是對的，**但當初判斷的原因是錯的，而且錯的部分寫進了對外文案**。

原始結論是「**含 `+` 的別名信箱**是常見原因」，依據是**一次**觀察 ——
測試時剛好用了一個 `+` 別名，它被擋了。文案因此寫成
「這個地址被寄信服務擋下了（含 + 的別名信箱常遇到）。請換一個信箱 ——
重送同一個不會有不同結果。」

當天稍後用 **不含 `+`** 的 `tsa206531@gmail.com` 測試，一樣被擋，假設當場崩掉。
後續又推翻了第二個假設（「刪除訂閱者會讓地址進抑制名單」）。

**真正的原因**，是從 Buttondown API 直接讀訂閱者記錄才看到的：

```json
"ip_address": "52.87.195.204",
"firewall_reasons": [
  { "code": "ip_address_datacenter",
    "reason": "That IP address belongs to a datacenter or VPN." }
]
```

`52.87.195.204` 是 AWS us-east-1 ＝ **Vercel serverless function 的出口 IP**。
我們是伺服器端轉發（那正是這支端點存在的理由），所以 **Buttondown 看到的永遠是機房 IP，
不是訪客的 IP** —— 而那是 list bombing 的典型特徵。

**跟 `+` 無關，跟地址本身也無關。這是架構的必然結果，每一個真實訪客都會帶著它。**

而當時帳號的防火牆設定是：Filtering **Aggressive**、IP address filtering **Enabled**、
Handling **Reject**、Attack mode **Enabled** —— 疊起來就是「機房 IP 一律硬拒絕、且不留記錄」。
（Attack mode 會在偵測到 unactivated 訂閱者激增時**自動**開啟前兩項，
而我們的端點送的正是 `type: 'unactivated'`，測試那一輪很可能就是觸發源。）

##### 為什麼查了四輪才查到

**因為證據被我們自己丟掉了。** 兩層遮蔽疊在一起：

| 層 | 狀況 |
| --- | --- |
| Buttondown | Handling 設 `Reject` ⇒ 被拒的請求**不建立任何記錄**，後台看不到 |
| 我方端點 | `blocked` 分支的 `return` 排在 `console.error` **之前** ⇒ 回應 body 直接丟棄 |

Buttondown 每一次都在 `firewall_reasons` 裡把原因講得清清楚楚，
**那句話從來沒有被寫下來過**。

> 🔴 **這是這條 F 最該記住的一課**：不是推理不夠好，是**唯一的直接證據沒有落地**。
> 現在 `blocked` 分支有 `console.error('[subscribe] Buttondown firewall', …)`，
> 只印 `code` / `detail` / `firewall_reasons`，**刻意不印 email**
> （隱私頁承諾 Vercel 只看得到「伺服器日誌層級的 IP 與 User-Agent」）。

##### 處置（2026-08-30）

**選了路線 B：不把訪客 IP 送給 Buttondown。**

Buttondown 官方的解法是「API 請求要自己帶上訪客 IP」，但那會讓送給第三方的個資
從「使用者主動提供的 email」擴大到「IP」，而
[隱私頁的第三方處理者矩陣](../webspec/PageDescription/06_privacy.md) 是對外承諾過的。
在一個主打「我們不追蹤你」的產品上，那是立場變更，不是實作細節。

改為關掉 Buttondown 端的 IP 檢查，**防濫用責任回到我方** ＝ F20 的限流。

🔴 **Buttondown 防火牆的目標設定（改動前請先讀 F17）**：

| 項目 | 值 | 為什麼 |
| --- | --- | --- |
| Firewall | **On** | 不要整個關掉，其餘檢查仍有價值 |
| Filtering | **Default** | Aggressive 會讓機房 IP 從扣分變成致命 |
| IP address filtering | **Disabled** | 🔴 我們不送訪客 IP（路線 B），開著等於必然誤判 |
| Attack mode | **Disabled** | 🔴 開著會**自動**把上面兩項改回去，等於白設 |
| Handling blocked subscribers | **Reject** | 改成 Accept 會讓端點收到 2xx 而回報 `ok`，**變成無聲的假成功**；要改的話程式得先會判讀 `firewall_reasons` |
| Exempt IP addresses | 不使用 | Vercel 標準方案的出口 IP **不固定**，加了也靠不住 |

> ⚠️ **Attack mode 關掉的代價要講清楚**：我們的端點送的是 `type: 'unactivated'`，
> 也就是**每一個真實訪客都是一筆 unactivated 訂閱者**。比賽曝光那波流量本來就會
> 長得像「unactivated 激增」—— 開著 Attack mode，收名單會**恰好在流量最高的那一刻**
> 靜默失效（Reject 不留記錄）。這正是 D30 收名單的目的所在，所以寧可自己扛限流。

#### ✅ F18　早鳥名單與授權碼之間的三個定義（已解，2026-08-30）

原始問題見上方 F 清單。三個缺口的裁示如下。

##### ① 用哪個識別綁授權碼 —— **早就定了，是 email**

這一格其實**不是待決問題**，只是沒有人把它跟早鳥名單接起來看。
[ADR-008](../appsync/ADR-008_授權憑證格式與離線驗證契約.md) 的 payload：

```json
"iss": "promptbox.app",          // 驗證時必須逐字相符
"sub": "buyer@example.com",      // D12：綁 email，小寫正規化
```

而且它是 **App 端的驗證契約** —— 改它要動 App repo 的驗簽程式碼。

##### ② 名單 email ≠ 會員帳號 email 時 —— **購買時由使用者確認**

**裁示：授權 email 由使用者在購買時確認，預設帶入他登記早鳥的那個信箱。**

關鍵是把三個角色拆開，它們**不必是同一個**：

| 角色 | 是什麼 | 誰決定 |
| --- | --- | --- |
| Google OAuth | 登入身分 —— 誰能打開帳號頁 | Google |
| 憑證 `sub` | 授權簽在哪個 email 上 | **使用者購買時指定** |
| 早鳥名單 email | 開賣通知寄到哪 | 訂閱時填的 |

這樣 ② 就消失了：不一致沒關係，購買當下確認即可。
訂閱表單「**這個信箱也是日後授權憑證上簽的那一個**」那句話在此設計下**成立**，
前提是購買流程要以它為預設值。

> 🔴 **這個裁示拉出一件會員區必須多做的事**：
> [接縫 §5](../appsync/官網金流與授權發放接縫.md) 的三張表裡
> **沒有任何一格把 `user_id` 對到授權 email**。而下載閘門在 Google 登入之後，
> 憑證與更新權卻掛在使用者指定的 email 上 —— 正是
> [接縫該節](../appsync/官網金流與授權發放接縫.md) 警告過的
> 「憑證是 A 信箱、更新權掛在 B 帳號」的錯位。**schema 要補這個對應**（已回寫接縫文件）。

##### ③ 會員區做好之前要不要開賣 —— **不開，等會員區**

**裁示：等會員區做好再開賣**（會員區預計 2026-09-04～09-06）。

但「做好」不等於「馬上賣」，兩者要分開排：

| 段 | 內容 | 卡在什麼 |
| --- | --- | --- |
| 會員區 | Supabase + Google OAuth + 帳號頁 | **不卡改名** —— 先用暫時網域註冊 redirect URI（見下） |
| 個人版 Pro 早鳥開賣 | Polar 接好 + 簽第一張憑證 | 🔴 **卡改名**（見下方紅字） |
| 商業授權開賣 | Polar 商品上架 | 公司登記（[P2](上線前置鏈.md)，以週計）＋ 送審 |

**會員區用暫時網域先做**（創辦人裁示）：先用現有 Vercel 網址註冊 OAuth redirect URI，
改名買到新網域之後**再重註冊一次**。成本是 OAuth 設定做兩次，
換到會員區不必等改名 —— 這個取捨是刻意的。

> 🔴 **但「賣早鳥」不能在改名之前，因為賣 ＝ 簽憑證。**
>
> 本檔 **§「這期間不要做的事」** 已列明：ADR-008 的 payload 有
> `"iss": "promptbox.app"`，而**憑證不可撤銷**（B2）。改名前簽出去的每一張
> 都會永遠帶著舊網域，而 App 的驗證是 `iss === "promptbox.app"` **逐字相符** ——
> 改名後就得永遠同時接受兩個發行者。而這批人正好是最早付錢的 150 位支持者。
>
> **可以先做**：接 Polar、webhook、冪等表、簽章流程、Ed25519 金鑰對、簽驗測試向量
> （後兩者本檔已明文列為不受改名影響）。整條金流可以建到「按下去就會賣」的前一刻。
> **不可以做**：第一筆真實銷售。
>
> 另外早鳥開賣通知要「依序寄信」，那需要 [P7](上線前置鏈.md) 的 SPF/DKIM/DMARC，
> 而那又需要網域。**所以賣早鳥的真正前置不是 Polar，是改名定案。**
