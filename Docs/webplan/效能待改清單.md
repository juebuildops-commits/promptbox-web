## E1　`icon.png` 是一張 2048×2048 的 JPEG ⬜

### 現象

```
Src/public/assets/icon.png   magic = ff d8 ff e0   ⇒ JPEG，不是 PNG
                             2048 × 2048            124 KB
```

它同時是三個角色：

| 用在哪 | 實際顯示尺寸 |
| --- | --- |
| [`AppHeader.vue`](../../Src/app/components/AppHeader.vue) 的 logo | 40 × 40 |
| [`AppFooter.vue`](../../Src/app/components/AppFooter.vue) 的 logo | 40 × 40 |
| [`nuxt.config.ts`](../../Src/nuxt.config.ts) 的 `rel="icon"` | 16 / 32 |

也就是**每個訪客、每一頁**都為了一顆 40px 的 logo 下載 2048px 的圖。
在首頁的非字型流量裡它大約佔三成，而且位置在 header ⇒ 跟 LCP 搶頻寬。

### 三個順帶的副作用

1. `<link rel="icon" type="image/png">` 的 MIME 宣告是錯的。瀏覽器靠 content sniffing 救回來，
   所以這件事**不會以任何形式報錯** —— 這正是它活到現在的原因。
2. **JPEG 沒有 alpha 通道** ⇒ logo 帶著一塊烘進去的底色，深色模式下看得出邊界。
3. 2048px 的 JPEG 當 favicon，瀏覽器每次都要解碼整張才畫得出 16px。

### 建議做法

出兩種尺寸：`80×80`（2× 給 header/footer 的 40px）與 `32×32` / `180×180`（favicon 與 apple-touch-icon），
格式用 PNG 或 WebP（要 alpha）。預期 **124 KB → 3～5 KB**。
順手把 `nuxt.config.ts` 的 `type` 改對。

⚠️ 檔名如果要換：它**不在**[身分字串凍結清單](../appsync/身分字串凍結清單.md)裡（那份管的是 App 認得的字串），
所以改檔名是安全的 —— 但 `AppHeader` / `AppFooter` / `nuxt.config.ts` 三處要一起改。

### 怎麼重新量

```bash
node -e "const b=require('fs').readFileSync('public/assets/icon.png');console.log(b.slice(0,4).toString('hex'), b.length)"
# ff d8 ff e0 = JPEG；89 50 4e 47 = PNG
```

## E2　四張圖的 `width`/`height` 全部對不上真實比例 ⬜

### 現象

| 檔案 | 真實尺寸 | 標記上宣告 | 差 |
| --- | --- | --- | --- |
| `ExImg/index-dark.png` | 1917 × 1017（1.885） | 1480 × 963（1.537） | 23% |
| `ExImg/encryption-status.webp` | 1462 × 910（1.606） | 1200 × 823（1.458） | 10% |
| `ExImg/MCP.webp` | **656 × 872（直式）** | 1200 × 823（**橫式**） | **方向相反** |
| `ExImg/chaining-demo.webp` | 1465 × 912（1.606） | 1200 × 823（1.458） | 10% |

四組宣告全部寫在 [`index.vue`](../../Src/app/pages/index.vue)。

### 為什麼這是問題

`width` / `height` 這兩個屬性在現代瀏覽器裡的用途，是讓它**在圖載入前先算出 aspect-ratio 佔位**。
現在四個都算錯 ⇒ 圖一到位，版面就跳一次。

🔴 **這兩個屬性目前是在製造 CLS，不是在防它。** 有寫比沒寫更糟 —— 它看起來像已經處理過了。

`MCP.webp` 最嚴重：預留了一個橫的框，來的是一張直的圖。

### 順帶一提的不一致

第 1、3 列的外層容器另外鎖了 `aspect-[16/10]`（1.6），第 2 列沒鎖。
1.6 跟這幾張圖的真實比例（1.606）其實很接近，**所以鎖的那兩列反而是對的** ——
問題是三列的處理方式不一致，而不一致遲早會被改壞。

### 建議做法

把四組數字改成真實尺寸，並統一三列容器的寫法。純改數字，零風險。

另外 `index-dark.png` 是 89 KB 的 PNG 且是首頁 LCP 候選 ——
轉 WebP（預期約 40 KB）並補 `fetchpriority="high"` 可以一起做。
下半頁三張已經有 `loading="lazy" decoding="async"`，
**hero 那張刻意不要加** —— 加了會延後 LCP。

### 怎麼重新量

```bash
node -e "
const fs=require('fs');
function dim(f){const b=fs.readFileSync(f);
 if(b[0]===0x89)return[b.readUInt32BE(16),b.readUInt32BE(20)];
 if(b.slice(8,12).toString()==='WEBP'&&b.slice(12,16).toString()==='VP8 ')
  return[b.readUInt16LE(26)&0x3fff,b.readUInt16LE(28)&0x3fff];
 return['?','?'];}
for(const f of fs.readdirSync('public/assets/ExImg'))
 console.log(f.padEnd(28), dim('public/assets/ExImg/'+f).join(' x '));"
```

## E3　changelog 把用不到的內文塞進 payload ⬜

[`changelog.vue`](../../Src/app/pages/changelog.vue) 是 `queryCollection('changelog').all()` ——
撈了所有欄位，含每一篇解析後的完整 body。

但 `legacy` 那批**只渲染 `summary`**，body 一個字都沒用到。


> ⚠️ 動到查詢就會動到對 [`content.config.ts`](../../Src/content.config.ts) schema 的依賴，
> 改完記得跑 `npm run check:content`。

### 怎麼重新量

```bash
ls -l .output/public/changelog/_payload.json
```

## E4　14 支 icon SVG 在 `public/`，Vite 碰不到 ⬜

### 現象

[`style.css`](../../Src/app/assets/css/style.css) 用 CSS mask 上色。
**這個設計本身是對的**，不引圖示元件庫是刻意的（見 [systemV2](../webspec/systemV2.md) 的圖示一節）。
問題只在檔案放的位置：

```css
.icon--lang { --icon: url('/assets/icon-lang.svg'); }
```

`Src/public/` 是**原封不動複製**到產物的，Vite 完全不處理它。
所以 14 支 SVG（261 B ～ 1.3 KB）全部是獨立 HTTP 請求，首頁大約用到 13 支。

### 建議做法

搬到 `Src/app/assets/icons/` 並改成相對路徑。
Vite 會自動把小於 4 KB 的資源 inline 成 data URI ——
**14 支全部低於 1.3 KB，會全部被 inline**。請求數歸零，CSS 大約多 4～5 KB (gz)。淨賺。

### 🔴 回寫義務

這條會動到 [systemV2.md](../webspec/systemV2.md) 的**兩個地方**：

1. 檔頭 `來源` 那一行列著 `Src/public/assets/*.svg`
2. 圖示一節的程式碼範例寫著 `url('/assets/icon-lock.svg')`

兩處都要跟著改，否則竣工圖就對不上程式碼了。

### 怎麼重新量

```bash
grep -o '/assets/[a-z-]*\.svg' .output/public/_nuxt/entry.*.css | sort -u | wc -l
# 目前：14
```

## E5　🔴 英文訪客會下載一整份中文語系檔（**待決**）

### 現象

[`i18n.config.ts`](../../Src/i18n/i18n.config.ts) 設了 `fallbackLocale: 'zh-TW'`，
建置產出的英文包因此**內含一份完整的中文包**：

```
_i18n/<hash>/en/messages.json      66 KB / gz 23 KB   內含 zh-TW=17.2KB + en=34.4KB
_i18n/<hash>/zh-TW/messages.json   32 KB / gz 12 KB   內含 zh-TW=17.2KB
```

這支檔案**是 hydration 時真的去抓的** —— entry chunk 裡有
`$fetch('/_i18n/<hash>/<locale>/messages.json')`。
所以每個英文訪客多付約 **11 KB (gz)**，下載他永遠看不到的中文。

### 為什麼不是直接砍掉就好

`i18n.config.ts` 自己的註解已經寫清楚了：

> 🔴 en 缺 key 時退回 zh-TW，而不是顯示 key 本身。
> 但這**不該發生** —— `npm run check:i18n` 會在建置前擋下缺 key。
> fallback 是安全網，不是工作流程的一部分。

[`check-i18n.mjs`](../../Src/scripts/check-i18n.mjs) 確實逐 key 比對且會讓建置失敗，
所以在**目前**的狀態下，fallback 是純成本。

但它是**日文上線那天風險最大的那張網** —— `SKELETON = new Set(['ja'])` 現在讓 ja 豁免檢查，
ja 真的出貨時那道豁免會被拿掉，而那正是最容易漏 key 的一次。

### 三個選項

| 選項 | 省到 | 代價 |
| --- | --- | --- |
| 維持現狀 | — | 每個英文訪客 11 KB (gz) |
| 拆掉 `fallbackLocale` | 11 KB (gz) | 安全網沒了，缺 key 會顯示 key 本身 |
| **只在 dev 保留 fallback** | 11 KB (gz) | 開發期仍有網、正式站沒有；多一行條件式 |

**建議第三個**，但這是取捨題不是技術題 ——
「機器已經在守」跟「萬一機器沒守到」之間要押哪邊，由創辦人決定。

### 怎麼重新量

```bash
node -e "
const fs=require('fs'),p=require('path');
const d=fs.readdirSync('.output/public/_i18n')[0];
for(const loc of fs.readdirSync(p.join('.output/public/_i18n',d))){
 const f=p.join('.output/public/_i18n',d,loc,'messages.json');
 const o=JSON.parse(fs.readFileSync(f,'utf8'));
 console.log(loc, fs.statSync(f).size, '內含:', Object.keys(o).join(','));}"
```

## E6　`Noto Sans TC` 載了四個字重（**待決**）

[`nuxt.config.ts`](../../Src/nuxt.config.ts) 的 Google Fonts 請求：

```
Big+Shoulders:wght@600;700
Inter:wght@400;500;700
Noto+Sans+TC:wght@400;500;700;900
```

**CJK 字型是全站最重的資源**，而 Noto Sans TC 開了四個字重，四個都真的有用到：

| 字重 | Tailwind class | 全站使用次數 |
| --- | --- | --- |
| 400 | `font-normal` | 30 |
| 500 | `font-medium` | 44 |
| 700 | `font-bold` | 211 |
| 900 | `font-black` | 26 |

砍掉一個字重是實打實的節省，但那是**設計決策**，不是效能決策 —— 需要創辦人拍板。
最可能的候選是 500（`font-medium`），把它併進 400 或 700。

### 一個查過但**不成立**的懷疑

`Inter` 宣告了 400/500/700，而 `font-ui font-medium`（500）全站零使用。
看起來像浪費，**但不是** ——
瀏覽器只會下載實際被文字命中的字面，未使用的字重不花流量，只多幾百 bytes 的 CSS。
**不值得動。**

> 寫下來是為了擋住下一個人（或下一個 AI）「發現」它，然後改一輪沒有收益的東西。

### 怎麼重新量

```bash
grep -rho "font-\(normal\|medium\|bold\|black\)" app/ | sort | uniq -c
```

真正的字型流量要用瀏覽器 DevTools 的 Network 面板看（過濾 `fonts.gstatic.com`），
指令量不出來 —— Google Fonts 是按 unicode-range 分片供應的。

## E7　2.09 MB 的 SQLite WASM 躺在部署產物裡（**待決**）

### 現象

```
sqlite3-BVKGSWc-.wasm              864,752   ┐ 位元組完全相同
sqlite3.BVKGSWc-.wasm              864,752   ┘ 只是檔名不同
sqlite3-worker1-*.js               213,453
<hash>.js（promiser）              215,569
sqlite3-opfs-async-proxy-*.js       32,289
                                 ─────────
                                   2.09 MB   ← 佔 3.8 MB 部署產物的 55%
```

那兩支 864 KB 的 wasm **是同一個檔案存了兩份**，純粹是打包產生的重複。

### 🟢 好消息：訪客載不到

`@nuxt/content` v3 的 client 端查詢路徑是
`executeContentQuery()` → 若在瀏覽器則 `import("@sqlite.org/sqlite-wasm")`。
但本站的 payload extraction 是開的（`docs/index.html` 裡有 `_payload.json` 的連結），
client-side 導覽讀的是 payload、**不會重新執行 `queryCollection`** ⇒ 不會觸發那個 import。
全站也沒有任何 client-side 的 content 查詢。

所以這是**部署負擔，不是使用者負擔**，優先度低。
但每次 push 都在搬 2.09 MB 的死重。

### 順帶：`better-sqlite3` 可以整個拿掉

這台是 Node **v22.15.1**，已經有內建的 `node:sqlite`。
設 `content.experimental.nativeSqlite: true` 就能拿掉 `better-sqlite3` 這個 native 相依 ——
連帶少掉安裝時的編譯步驟，以及 commit `615c738` 那次為了 peer range 降版的麻煩。

🔴 **這條要決定**：換連接器會動到建置期的資料庫後端。
雖然產物應該一樣，但它屬於「靜默壞掉」風險最高的那一類改動（建置成功、內容卻不對）。
換之後至少要人工確認 `/docs` 與 `/changelog` 兩頁的章節數與版本數沒有少。

### 怎麼重新量

```bash
du -sh .output/public .output/public/_nuxt
ls -la .output/public/_nuxt/*.wasm
```

確認 payload extraction 還開著（這是「訪客載不到」的前提）：

```bash
grep -o '_payload.json' .output/public/docs/index.html | head -1
```

## 已經做對的地方 —— 不要去「優化」它

免得下一個人（或下一個 AI）看到覺得是待辦：

| 東西 | 為什麼不要動 |
| --- | --- |
| `<head>` 裡的同步 inline 防 FOUC script | 改成 plugin 就會閃白底。`nuxt.config.ts` 的註解已寫明 |
| `gtag.initMode: 'manual'` + `analytics.client.ts` | 這是**產品立場**（退出者身上不下載 gtag.js），不是效能設定 |
| 下半頁三張圖的 `loading="lazy" decoding="async"` | 正確。**但 hero 那張不要加** |
| Google Fonts 的 `preconnect` ×2 + `display=swap` | 正確 |
| CSS mask 上色、不引圖示元件庫 | 正確（E4 只搬位置，不改機制） |
| 全站預繪 + payload extraction | 正確，而且正是它讓 E7 那 2.09 MB 沒有真的傷到人 |
| `/api/subscribe` 的模組層級限流 Map | 每次請求掃全表是 O(n)，但這個量級無感，而且它的極限已寫在程式註解裡 |

## 建議順序

1. **E1 ＋ E2** —— 成本近乎為零，收益最大（每訪客約 120 KB ＋ 修掉現有 CLS）
2. **E4 ＋ E3** —— 少 13 個請求、瘦一點 payload
3. **E5 / E6 / E7** —— 等創辦人拍板
