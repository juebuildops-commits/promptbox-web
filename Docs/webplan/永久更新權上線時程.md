## 三、恢復清單

> ⚠️ **順序有意義**：先決定（步驟 0）、再改數字（步驟 2）、最後才翻旗標（步驟 3）。
> 先翻旗標會讓一個還沒改成階梯的 `$109` 直接上線，那正是隱藏想避免的事。

### 步驟 0 —— 先把 BRD-02 §5.4 的三個未決結掉

| # | 未決 | 不結掉會怎樣 |
| --- | --- | --- |
| 1 | 第二批的觸發條件目前只有「第一批售罄」 | 第一批卡在 30/50 時沒有機制通知，第二批永遠不開。建議改成「售罄**或**某時間點，先到者為準」 |
| 2 | 兩條階梯（Pro 150/150、永久 50/50）並行，名額靠人工換連結 | 名額是印在頁面上的對外承諾。頁面寫「前 50 名 $109」而其實已售完 ＝ 踩誠實紅線 C1 |
| 3 | `$129` 沒有可推導的來歷 | 現在選的是「等距 +$20」。可推導的替代是「首購 + N 年續訂」N＝2/3/4 ⇒ $93/$120/$147。要換就趁還沒公告 |

上線那天在賣第一批（$109）還是第二批（$129）？這決定 `PRICES.lifetime` 指向哪一個。

## 五、為什麼不是直接把程式碼刪掉

刪掉最乾淨，但**刪掉的東西不會提醒任何人它曾經存在**。

旗標的價值不在於少打幾個字，而在於 `SHOW_LIFETIME` 這個名字會出現在
`pricing.ts`、`index.vue`、`pricing.vue` 三個檔案裡 —— 任何人為了別的事讀到那三處，
都會看到旗標與它指過來的這份文件。刪掉之後，唯一的線索就只剩 git log，
而沒有人會為了「這站有沒有少賣一個 SKU」去翻 git log。

同樣的理由，語系檔的 `pricing.lifetime.*`、`home.price.lifetime.*`、`pricing.faq.q4/a4`、
`pricing.compare.colLifetime` 等 key **全部保留原樣**：
`check:i18n` 不檢查 key 有沒有被用到，留著零成本，而刪掉就得在恢復時重新翻譯一次。
