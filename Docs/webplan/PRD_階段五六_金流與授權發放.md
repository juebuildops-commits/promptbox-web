## 0. 為什麼這份 PRD 現在是「暫緩」而不是「進行中」

官網要先出去（比賽曝光 + 釋出 Free 版），而且**產品即將改名**（商標問題）。
在這兩件事落定之前開始做階段五，會踩到三個不可逆的坑：

| 坑 | 說明 |
| --- | --- |
| `iss` 欄位帶著舊名字 | [ADR-008](../appsync/ADR-008_授權憑證格式與離線驗證契約.md) 的憑證 payload 有 `"iss": "promptbox.app"`。憑證**不可撤銷**（B2）—— 改名前簽出去的每一張，都會永遠帶著舊網域 |
| 網域買錯 | 現在買 = 買一個要丟掉的東西，還會留下要 301 的舊網址。目前**沒有任何網址被索引**，這個乾淨的起點不該浪費 |
| Polar 商品與寄件身分 | 商品名稱、Merchant of Record 的顯示名、Buttondown 寄件網域，全部帶名字 |

**因此這份 PRD 的定位是：現在寫清楚、暫不動工、解凍條件明確。**

### 🔓 解凍條件（全部滿足才開始）

- [ ] **改名定案**，且 [身分字串凍結清單](../appsync/身分字串凍結清單.md) 已執行完畢
- [ ] 網域已購買，DNS / SPF / DKIM / DMARC 已生效
- [ ] App repo 的**雙 build 已能產出兩個產物**，且 Pro build 已實作 [ADR-008 §四](../appsync/ADR-008_授權憑證格式與離線驗證契約.md) 的驗證
- [ ] Q12（憑證交付外觀）已拍板 —— 它決定 App 設定頁長什麼樣

### 現在就可以做、且不受改名影響的兩件事

1. **產生 Ed25519 金鑰對。** 金鑰沒有名字。而且**公鑰要編譯進 Pro build**，
   所以它是 App repo 那條長桿的前置 —— 晚生一天，那邊就多卡一天。
2. **做一份簽驗測試向量。** 一組已知的 `(payload, 私鑰, 預期 JWS)` 三元組，
   **兩個 repo 各存一份**當 fixture。官網負責簽、App 負責驗，是兩套獨立程式碼；
   沒有共用向量的話，第一個發現簽驗不合的人會是付了錢卻啟用不了的顧客。

## 1. 🔴 先修正一個規劃錯誤：五、六的順序是反的

原規劃：

| 階段 | 內容 |
| --- | --- |
| 五 | Polar 商品 + webhook + 簽發 endpoint + **登入** + **下載閘門** |
| 六 | Supabase（`entitlements_issued` / `update_rights`） |

但「登入」就是 Supabase Auth，「下載閘門」就是在讀 `update_rights` ——
**階段五的後半整個坐在階段六上面**。兩階不該分開。

**本 PRD 合併五、六，並依「可逆性」重新切成 5a / 5b：**

| | 內容 | 特性 |
| --- | --- | --- |
| **5a** | Supabase schema + Auth + 帳號頁（先只放 Free 下載） | **全程不碰錢**，做壞了沒有不可逆後果 |
| **5b** | Polar 商品 + webhook + 簽發 + Pro 下載閘門 | **每一步都不可逆**（憑證簽出去收不回來） |

5b 應等到 App 那邊能真的驗一張憑證再開始。

## 4. 功能需求

### FR-25　Supabase schema（原階段六）

三張表，定義見 [接縫文件 §5](../appsync/官網金流與授權發放接縫.md)：

| 表 | 性質 |
| --- | --- |
| `entitlements_issued` | 🔴 **只增不改**。這是「我簽過什麼」的帳本 |
| `update_rights` | **可以改**。退款與續訂都改這裡 |
| `webhook_events` | 冪等鍵 |

`entitlements_issued` 完整存下 `jws` 字串本身 —— 使用者信件遺失時要能**原樣重發**。
重簽會產生新的 `jti`，帳本上就多一份來歷不明的憑證，而憑證不可撤銷，帳本對不上就永遠對不上。

### FR-26　登入（D7 / D16）

Supabase Auth 的 Google OAuth。**不引入 Clerk**（D7）。

### FR-27　帳號頁（D17）

**Pro 下載連結與該帳號的授權碼放在同一頁。** email 是通知，不是唯一副本 ——
信件遺失、進垃圾桶、換信箱都靠這一頁救。

### FR-28　Polar 商品 + webhook（D9 / D10 / D22）

商品定義與處理順序見 [接縫文件 §4](../appsync/官網金流與授權發放接縫.md)。兩條紅線：

- 🔴 **驗 webhook 簽章不可跳過。** 沒驗簽的端點 ＝ 一個**公開的、無認證的簽發器**，
  任何人 POST 一段 JSON 就能拿到合法的永久授權
- 🔴 **冪等不可省。** webhook 會重送。沒有冪等表，一次重送就是**多簽一份永久有效、無法撤銷的憑證**。
  冪等鍵用 event id，不是 order id —— 同一筆訂單會有多個事件

**Polar 的 license key 功能不使用**（D10）：它的 `validate` / `activate` API 永不由 App 呼叫。

### FR-29　下載閘門（D16 / D18）

- 所有下載需登入（含 Free）
- Pro build 的連結由 `update_rights` 把關；到期未續訂 ⇒ 拿不到新版，已下載的不受影響
- Free build 持續發佈（NQ3）

#### ⚠️ 對 D16 的一項疑慮（記錄，非推翻）

「所有下載一律需登入，含 Free」讓 **Supabase Auth 變成整站單點故障** ——
Google OAuth 一出問題，連免費版都沒人載得到。Pro-only 的閘門則是優雅降級。

**建議：比賽 / 首次曝光期間先不上閘門**，Free 版直接開放下載。
等 Pro 真的存在了再上，那時閘門才有意義。若要維持 D16 原案，建議排一條可簽名短效直連當 fallback。

## 5. 🔴 三個原接縫文件低估的缺口

### 5.1 商業授權的席次收不到 email

D23：買 4 送 1，**各席次綁各自 email**。但結帳時你只有購買者一個信箱。

接縫文件 §4 步驟 5 寫「依 seat 數展開，各綁各自 email」—— **那是錯的**，
那個資訊在 webhook 當下並不存在。

**正確設計：簽發不是同步的。**

```
webhook → 建立 5 個【pending 席次】（只記數量與訂單，不簽）
                ↓
購買者登入帳號頁 → 逐一填入席次 email
                ↓
每填一個 → 簽一張 → 寫帳本 → 寄出
```

需要第四張表或 `entitlements_issued` 加一個 `status`（`pending` / `issued`）。
🔴 一旦簽出就不能改指派對象（不可撤銷），因此**填 email 的介面必須有二次確認**。

### 5.2 改 email 沒有出口

憑證綁 email（D12）且不可撤銷。顧客換信箱、或結帳時打錯字，
唯一的解是**對正確信箱補簽一份** —— 帳本上就會有兩張都有效、指向同一筆訂單的憑證。

**這不是異常，是正常會發生的事**，schema 與客服流程要先接受它：

- `entitlements_issued` 允許同一 `order_ref` 有多筆，加 `supersedes` 欄位標註
- 🔴 **結帳頁的 email 必須二次輸入確認**

### 5.3 Q12 現在卡到 App，不只卡官網

憑證是「複製一段字串」還是「載入一個檔案」，決定 App 設定頁長什麼樣。
它從「小事，下次討論」升級成**解凍條件之一**。

[ADR-008 §八](../appsync/ADR-008_授權憑證格式與離線驗證契約.md) 建議 **A：不做成檔案** ——
下載頁直接顯示可複製的字串（D17 已定「下載連結與授權碼同一頁」）。
沒有檔案就沒有副檔名問題，也沒有「檔案存到哪去了」的客服。

## 6. 私鑰保管（D21）

| | |
| --- | --- |
| 放哪 | Vercel 環境變數，base64 PKCS#8，變數名帶 kid |
| 🔴 環境 | **僅 Production**，標記 Sensitive。Preview / Development 另配**測試金鑰** |
| 備份 | 密碼管理器離線備份，**必須做** |

Preview 那條是硬要求：Vercel 的 preview 部署預設**任何人拿到網址就能存取**，
真金鑰跟著上 preview ＝ 公開一個無認證的簽發端點，與 FR-28 沒驗簽同一級。

輪替規則見 [ADR-008 §五](../appsync/ADR-008_授權憑證格式與離線驗證契約.md)：
公鑰是一張**只增不刪**的表。移除舊 kid ＝ 一次撤銷所有用它簽過的憑證。

## 7. 前置條件與依賴順序

**真正的長桿在 App repo，不在官網。** 官網把 webhook、簽發、閘門全做完之後，
若 App 那邊沒動，**還是沒有東西可以下載，也沒有 App 認得那張憑證**。

| # | 前置 | 歸屬 | 狀態 |
| --- | --- | --- | --- |
| 1 | 🔴 **身分字串凍結**（發 binary 前） | App repo | ⏳ [清單已備妥](../appsync/身分字串凍結清單.md) |
| 2 | 改名定案 | 產品 | ⏳ 預計下週 |
| 3 | Ed25519 金鑰對 + 測試向量 | 共用 | ⏳ **可現在做，不受改名影響** |
| 4 | NQ1：雙 build 共用 `appId` / `productName` | App repo | ⏳ 已納入凍結清單 |
| 5 | **雙 build 本身**（electron-builder 產出兩個產物） | App repo | ⏳ **原先沒有任何文件排它** |
| 6 | **ADR-008 §四 驗證實作 + 設定頁 UI** | App repo | ⏳ 同上 |
| 7 | 網域 + DNS + OAuth redirect URI | 官網 | ⏳ **改名定案後再買** |
| 8 | Q12 拍板 | 產品 | ⏳ 建議 A |
| 9 | 下載檔案實際放哪（F10 / Q15） | 產品 | ⏳ 比賽期間建議 Vercel `public/` |
| 10 | Buttondown 帳號 + transactional 寄信 | 官網 | ⏳ 收集端已上線，寄件待網域 |

### 建議動工順序（依前置時間排，不是依重要性）

```
可並行、不需等改名：
  ① Ed25519 金鑰對 + 測試向量
  ② App repo：雙 build + 驗證實作（只需要 ① 的公鑰）

等改名定案：
  ③ 身分字串凍結 + 發比賽用 Free build
  ④ 買網域 → DNS / DKIM 生效（有等待時間，越早越好）

5a（不碰錢）：
  ⑤ Supabase schema + Auth + 帳號頁

5b（不可逆）：
  ⑥ Polar 商品 → webhook + 簽發 → Pro 下載閘門
```

## 9. 明確排除

- ❌ **App 呼叫任何金流 API**（D10）—— 這條線一開，「不連網」就沒了
- ❌ **憑證撤銷機制** —— 需要 App 連網查黑名單，與 A5 直接衝突
- ❌ **人工簽發後門**（D13）—— 等於開一條沒有稽核、沒有冪等、只有一個人記得怎麼用的第二條路徑
- ❌ **把更新權日期寫進憑證**（D14 / [ADR-008 §三](../appsync/ADR-008_授權憑證格式與離線驗證契約.md)）
- ❌ **自建金流 / 自行處理 VAT** —— 選 Polar 的全部理由
